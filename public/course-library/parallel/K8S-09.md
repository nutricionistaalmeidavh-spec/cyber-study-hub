# K8S-09 — SecurityContext — UID, capabilities e filesystem

**Trilha paralela:** Cloud / Containers / Kubernetes  
**Acesso:** livre; prática somente em cluster local descartável.  
**Tempo sugerido:** 60–90 min

## 1. Problema: o processo só precisa servir HTTP

O servidor de notas escuta em 8080 e lê um token montado. Não precisa UID 0, capabilities Linux, gravar na imagem ou acessar credenciais Kubernetes. `securityContext` configura propriedades do processo/container/Pod; não é policy IAM nem RoleBinding. A intenção é transformar essas restrições em estado observável: UID efetivo, CapEff, NoNewPrivs, seccomp e escrita negada na raiz.

Objetivos: colocar cada campo no nível correto, distinguir proteção de processo de RBAC/rede e verificar que o caso legítimo continua funcionando depois do hardening.

## 2. Controles que atuam em mecanismos diferentes

| Campo | Nível usado | Efeito/limite |
|---|---|---|
| runAsUser/runAsGroup | Pod | UID/GID numéricos padrão dos containers |
| runAsNonRoot | Pod | Runtime recusa execução root incompatível |
| fsGroup | Pod | Grupo aplicado a volumes compatíveis; não concede acesso à API |
| seccompProfile: RuntimeDefault | Pod | Perfil seccomp do runtime, não bloqueio genérico de rede |
| capabilities.drop: ALL | Container | Remove capabilities Linux do processo |
| allowPrivilegeEscalation: false | Container | Impõe no_new_privs; não “conserta” todos os bugs do kernel |
| readOnlyRootFilesystem: true | Container | Raiz da imagem somente leitura; volumes podem continuar graváveis |
| automountServiceAccountToken: false | Pod | Evita montagem automática do token; é campo de spec, não securityContext |

Configurações de container prevalecem sobre equivalentes de Pod quando suportadas. Capabilities e filesystem readonly pertencem ao container; `fsGroup` pertence ao Pod. A imagem também define `USER 10001:10001`, mas a política do manifesto continua explicitando o contrato de execução. [Security context oficial](https://kubernetes.io/docs/tasks/configure-pod-container/security-context/).

## 3. Configuração aplicada ao servidor

Este é o trecho completo de Pod spec usado dentro do Deployment de [stack.yaml](/course-labs/phase16-platform/k8s/stack.yaml). Não é um documento aplicável isolado; use o arquivo completo, que inclui selector, labels e objetos associados.

```yaml
serviceAccountName: notes
automountServiceAccountToken: false
securityContext:
  runAsNonRoot: true
  runAsUser: 10001
  runAsGroup: 10001
  fsGroup: 10001
  seccompProfile:
    type: RuntimeDefault
containers:
  - name: notes
    image: course-notes:phase16
    imagePullPolicy: Never
    ports:
      - name: http
        containerPort: 8080
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: [ALL]
    resources:
      requests: {cpu: 50m, memory: 32Mi}
      limits: {cpu: 250m, memory: 96Mi}
    readinessProbe:
      httpGet: {path: /health, port: http}
      initialDelaySeconds: 1
      periodSeconds: 2
    livenessProbe:
      httpGet: {path: /health, port: http}
      initialDelaySeconds: 5
      periodSeconds: 10
    livenessProbe:
      httpGet: {path: /health, port: http}
      initialDelaySeconds: 5
      periodSeconds: 10
    volumeMounts:
      - {name: token, mountPath: /run/secrets, readOnly: true}
      - {name: tmp, mountPath: /tmp}
volumes:
  - name: token
    secret: {secretName: note-token, defaultMode: 288}
  - name: tmp
    emptyDir: {sizeLimit: 16Mi}
```

`288` em decimal corresponde a modo `0440`: leitura para owner/grupo. `fsGroup:10001` permite ler o volume Secret nesse grupo. O token é fictício. Base64 em Secret não é criptografia; a montagem readonly protege contra alteração pelo processo, não contra leitura por quem já tem permissão de secrets na API.

### Exemplo resolvido

O Python abre `/run/secrets/token`, escuta em 8080 e atende a nota: UID 10001 e zero capabilities bastam para essas operações. Tentativa de criar `/proof` falha porque a raiz está readonly; `/tmp/proof` pode funcionar porque `/tmp` é um volume separado gravável. A segunda escrita não refuta a primeira proteção: os mount points têm contratos diferentes.

## 4. Laboratório guiado

Pré-requisitos e setup completo estão no [README](/course-labs/phase16-platform/k8s/README.md). Se ainda não criou o cluster:

```bash
cd public/course-labs/phase16-platform/k8s
bash setup.sh
kubectl apply -f stack.yaml
kubectl -n course-platform rollout status deployment/notes --timeout=120s
kubectl -n course-platform wait --for=condition=Ready pod/client --timeout=120s
```

Observe primeiro o caso legítimo e o processo:

```bash
kubectl -n course-platform exec -i client -- python - allow < check.py
kubectl -n course-platform exec deployment/notes -- python -c 'import os,pathlib; print("uid",os.getuid(),"gid",os.getgid()); print(pathlib.Path("/proc/1/status").read_text())'
```

Esperado: HTTP 200; UID/GID 10001; `CapEff: 0000000000000000`, `NoNewPrivs: 1`, `Seccomp: 2`. O valor 2 indica modo de filtro seccomp; não mostra sozinho todas as regras específicas do perfil do runtime. Guarde versão do runtime/nó junto da evidência.

Teste negativo de filesystem, caso permitido e reteste:

```bash
kubectl -n course-platform exec -i deployment/notes -- python - < check_process.py
kubectl -n course-platform exec -i client -- python - allow < check.py
```

O [check_process.py](/course-labs/phase16-platform/k8s/check_process.py) exige `EROFS` ao criar `/app/rootfs-proof`, sucesso de escrita em `/tmp` e os asserts UID/GID/caps/seccomp. `/app` pertence ao UID da aplicação na imagem. Erro de permissão `EACCES`, ausência de Pod ou falha de conexão não passam como readonly. Esperado: `PASS UID/GID=10001 ... EROFS /tmp=gravável`, seguido de HTTP 200. O [run.sh](/course-labs/phase16-platform/k8s/run.sh) executa esse mesmo check no capstone.

**Checkpoint 1:** por que o sucesso da escrita em `/tmp` não exige mudar `readOnlyRootFilesystem` para false? Porque um volume gravável satisfaz a necessidade específica sem tornar a imagem inteira gravável.

## 5. Caso negativo de admissão

O namespace impõe Pod Security `restricted` versão v1.34. Verifique se a API rejeita um Pod declaradamente root sem enfraquecer workloads existentes:

```bash
kubectl -n course-platform run root-check --image=course-notes:phase16 --restart=Never --dry-run=server --overrides='{"spec":{"securityContext":{"runAsUser":0,"runAsNonRoot":false}}}'
```

Esperado: rejeição de admissão por violações de Pod Security; esse Pod também omite outros campos exigidos, então a mensagem pode listar várias violações. Não atribua todo o resultado apenas a UID. O dry-run não cria o Pod. **Checkpoint 2:** admissão decide se o objeto pode ser aceito; `/proc/1/status` verifica processo que realmente iniciou. São evidências complementares. [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/).

## 6. Troubleshooting e defesa

`CreateContainerConfigError` após `runAsNonRoot` pode indicar imagem sem UID numérico compatível. Token ilegível pede verificar modos, UID/GID e fsGroup antes de dar root. Aplicação que precisa cache/log em disco deve receber volume restrito, não raiz gravável. `Permission denied` ao bind em porta baixa deve ser comparado com a necessidade real: nosso servidor usa 8080 e dispensa `NET_BIND_SERVICE`.

`allowPrivilegeEscalation:false` não impede acesso permitido ao socket Docker montado: essa montagem nem existe aqui. RBAC restringe API Kubernetes; NetworkPolicy restringe tráfego selecionado; seccomp/capabilities restringem processo. Nenhum deles substitui autorização da aplicação. Uma conclusão de “container seguro” baseada apenas no manifesto é ampla demais.

Sem runtime Docker/K8S nesta edição, os checks de UID/caps/rootfs/admissão estão pendentes. Os seis testes HTTP/TCP Python do servidor e cliente confirmam somente esses componentes, não a execução containerizada. Cleanup do laboratório: `kind delete cluster --name course-phase16`.

## 7. Quiz

1. Onde configurar `capabilities.drop` neste manifesto?
A. Na RoleBinding.
B. No Service selector.
C. No securityContext do container.
D. Na stringData do Secret.

**Resposta:** C. Capabilities configuram o processo do container.

2. `/tmp/proof` foi criado com rootfs readonly. Qual explicação é coerente?
A. O kubelet ignorou todos os securityContexts.
B. `/tmp` é um volume separado autorizado para escrita.
C. fsGroup torna a raiz inteira gravável.
D. seccomp desativa readonly quando Python inicia.

**Resposta:** B. Raiz da imagem e volumes têm modos independentes.

3. `Seccomp: 2` em /proc prova o quê?
A. Que nenhuma syscall é permitida.
B. Que o Pod não pode acessar a internet.
C. Que a conta da API não lê secrets.
D. Que o processo usa modo filtro; o perfil exato exige evidência adicional.

**Resposta:** D. Seccomp não é uma verificação de RBAC/rede.

## 8. Flashcards

- **CapEff zerado** → processo sem capabilities efetivas; observar runtime, não só YAML.
- **NoNewPrivs=1** → impede adquirir novos privilégios por exec conforme mecanismo Linux.
- **fsGroup** → grupo para volumes compatíveis; não identidade IAM ou role Kubernetes.
- **Readonly + emptyDir** → raiz imutável com área de escrita deliberadamente delimitada.
- **Pod Security Admission** → validação na API, complementar à verificação do processo em execução.
