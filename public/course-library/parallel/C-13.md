## Problema e objetivo

Diagnostique um uso após free numa fixture de um único inteiro. Execute o caminho correto e, separadamente, o caminho intencionalmente defeituoso instrumentado por AddressSanitizer.

## Mecanismo e exemplo resolvido

malloc(sizeof *p) cria um int sem inicializar; *p=42 o inicializa. O caminho correto lê antes de liberar. No caminho defeituoso, alias copia o endereço; free(p) encerra o bloco e p=NULL não altera alias. Ler *alias depois disso é use-after-free: qualquer valor observado é consequência de comportamento indefinido, não resultado que possa ser previsto como 42.

O ASan deve apontar heap-use-after-free e apresentar pilhas de acesso, liberação e alocação. A primeira evidência útil é o acesso em printf após free, seguida pela origem do bloco. O caminho normal imprime antes de free=42 e encerra sem diagnóstico.

```c
#include <stdio.h>
#include <stdlib.h>
int main(int argc, char **argv) {
    (void)argv;
    int *p = malloc(sizeof *p);
    if (p == NULL) return 1;
    *p = 42;
    if (argc > 1) {
        int *alias = p;
        free(p);
        p = NULL; /* NÃO invalida o outro nome alias */
        printf("%d\n", *alias); /* fixture intencional: ASan deve apontar UAF */
        return 0;
    }
    printf("antes de free=%d\n", *p);
    free(p);     /* libera exatamente uma vez, depois do último uso */
    p = NULL;
    puts("ownership encerrado; nenhum acesso depois de free");
    return 0;
}
```

## Prática e autoexplicação

Parcial: indique a última linha segura para ler alias. Independente: corrija o ramo defeituoso para imprimir antes de free e remova qualquer acesso posterior; recompile com as mesmas flags. Autoexplicação: por que limpar somente p não basta quando existe alias?

## Solução comentada e checkpoints

A leitura precisa acontecer antes de free(p). Checkpoints: caminho normal tem exit 0; o defeituoso, execução separada com argumento falha, deve retornar status não zero e diagnóstico heap-use-after-free. A correção deve passar com ASan mantendo a impressão 42 antes da liberação.

## Robustez, reteste e diagnóstico

Use somente o programa descartável fornecido. Não reproduza UAF em processos reais. free(NULL) é permitido, mas free duplicado do mesmo endereço não é. Se não houver diagnóstico, confirme flags tanto na compilação quanto na ligação e execute o ramo com argumento. Reteste normal e corrigido; um teste limpo cobre apenas os caminhos executados.

Se o runtime emitir `LeakSanitizer has encountered a fatal error` por restrição de `/proc`/ptrace, isso não é diagnóstico de UAF nem de overflow. Neste contêiner, os caminhos saudáveis exigiram `ASAN_OPTIONS=detect_leaks=0 "./C-13". Repita também os casos defeituosos com a mesma opção: ASan ainda deve nomear o acesso inválido; UBSan ainda deve nomear overflow. Essa execução não verifica vazamentos de memória. Em máquina com suporte completo, preserve a detecção de leaks.

## Quiz

1. **p=NULL após free torna alias seguro?**
   - A) sim
   - B) não
   - C) sim, enquanto nenhuma outra alocação reutilizar o endereço

2. **Qual ordem é correta?**
   - A) malloc,free,ler
   - B) malloc,ler,free sem inicializar
   - C) malloc,inicializar,ler,free

3. **ASan associa o acesso inválido a:**
   - A) pilhas de alocação/liberação/acesso
   - B) apenas o acesso atual, sem relacioná-lo à liberação
   - C) apenas o retorno de malloc, sem localizar o acesso inválido

**Gabarito comentado:** 1: B — alias mantém endereço de bloco encerrado. 2: C — uso ocorre enquanto o objeto está vivo. 3: A — a causalidade depende da sequência de operações.
