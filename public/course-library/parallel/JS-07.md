## Problema e objetivo

Um cliente recebe cinco respostas diferentes de um serviço local: JSON válido, 404, JSON quebrado, demora e redirecionamento. Classifique cada resultado e depois observe a falha com o servidor desligado.

## Mecanismo e exemplo resolvido

fetch devolve uma Promise que pode resolver mesmo para status 404: o transporte HTTP funcionou, mas o recurso não existe. response.ok cobre 200–299. response.json lê e interpreta o corpo de forma assíncrona e pode falhar depois de fetch ter resolvido. AbortController aplica um prazo que permanece ativo até terminar a leitura do corpo. finally limpa o temporizador. redirect:error recusa redirecionamentos em vez de seguir outro destino automaticamente.

| Rota/estado | Situação | Classificação esperada |
|---|---|---|
| /ok | 200 e JSON válido | ok |
| /ausente | 404 | http com status 404 |
| /quebrado | 200, corpo {invalido | json |
| /lento | resposta em 250 ms, prazo 20 ms | timeout |
| /redireciona | 302 recusado | transporte-ou-redirecionamento |
| listener encerrado | nova conexão recusada | transporte-ou-redirecionamento |

```javascript
const response = await fetch(url, {signal: controller.signal, redirect: "error"});
if (!response.ok) return {tipo: "http", status: response.status};
// A leitura do corpo ainda pode falhar; o arquivo completo trata esse caminho.
const dados = await response.json();
```

## Prática e autoexplicação

Use Node.js 20 ou posterior; não há npm install. Parcial: explique por que /ausente não entra automaticamente no catch externo. Independente: acrescente /sem-conteudo com status 204; decida se o contrato aceita sucesso sem JSON e adapte o cliente com teste próprio. Autoexplicação: em qual etapa pode ocorrer um timeout após receber headers?

## Solução comentada e checkpoints

204 não tem corpo: chamar json gera falha de parsing. Uma adaptação válida retorna {tipo:"vazio"} antes de json para status 204. Checkpoints: seis linhas devem mostrar as categorias da tabela; a mensagem ação local preserva UTF-8. Erro de rede e redirect:error são TypeError nesta API; o exemplo mantém uma categoria conjunta porque a classe isolada não prova a causa.

## Robustez, reteste e diagnóstico

Não interprete TypeError como prova de DNS: no lab também representa política de redirect. Não faça retry infinito nem em qualquer método; operação mutável pode ser duplicada. Se /lento não expirar, confira prazo e timer; se o processo ficar aberto, confirme closeAllConnections e close do servidor. Reteste todas as rotas após modificar a leitura do corpo.

## Quiz

1. **fetch para um 404 normalmente:**
   - A) sempre rejeita
   - B) resolve com Response
   - C) resolve apenas se response.ok for verdadeiro

2. **Onde JSON inválido costuma falhar?**
   - A) no await fetch, antes de consumir o corpo
   - B) ao consultar response.status, sem ler o corpo
   - C) em response.json()

3. **Por que o timer dura até ler o corpo?**
   - A) headers podem chegar antes de um corpo lento
   - B) para fazer HTTP404 rejeitar automaticamente o fetch
   - C) porque headers só ficam disponíveis depois do corpo inteiro

**Gabarito comentado:** 1: B — o status HTTP precisa ser verificado. 2: C — o corpo é interpretado depois da resposta. 3: A — receber headers não conclui o download.
