# K8S-04 — Services — seleção de Pods e portas

**Trilha paralela:** Cloud / Containers / Kubernetes  
**Acesso:** livre; prática somente em cluster local descartável.  
**Tempo sugerido:** 60–90 min

## 1. O problema que um Service resolve

Um Pod reiniciado pode receber outro IP. Consumidores precisam de um endereço estável e de um conjunto atualizado de backends prontos. Um Service ClusterIP oferece nome/porta estáveis e seleciona Pods por labels. O controlador mantém EndpointSlices com endereços e portas; o dataplane do cluster encaminha conexões para endpoints elegíveis. DNS resolve o nome do Service, mas não comprova que existe algum backend saudável.

Nesta aula, o cliente chama `http://notes:8000/note`. O Service seleciona `app: notes`; seus backends escutam na porta 8080, nomeada `http`. A política IAM não participa desse encaminhamento. A autorização de aplicação continua sendo decisão do servidor depois da conexão.

Objetivos: relacionar selector/labels/readiness/EndpointSlice; distinguir `port` de `targetPort`; observar quebra por selector incorreto e retestar a correção.

## 2. Mecanismo e exemplo resolvido

| Objeto/campo | Valor do laboratório | Papel |
|---|---|---|
| Deployment template label | app=notes | Identifica Pods candidatos |
| readinessProbe | GET /health:8080 | Marca disponibilidade para tráfego |
| Service selector | app=notes | Seleciona Pods deste namespace |
| Service port | 8000 | Porta usada pelo cliente |
| Service targetPort | http | Resolve porta nomeada do container |
| containerPort name/http | 8080 | Nome → número para endpoints |
| EndpointSlice | IPs:8080 e ready | Estado efetivo do conjunto de backends |

Apenas declarar `containerPort:8080` não abre uma aplicação nessa porta: o processo Python precisa executar `listen` em 8080. Trocar `port` altera como o cliente acessa o Service; trocar `targetPort` altera o destino nos Pods. Um Service sem selector pode ser usado com endpoints geridos explicitamente, mas esse é outro contrato, não o do nosso exercício. [Services no Kubernetes](https://kubernetes.io/docs/concepts/services-networking/service/).

O fragmento abaixo é o recurso Service completo. [stack.yaml](/course-labs/phase16-platform/k8s/stack.yaml) inclui Namespace, Deployment, Secret fictício, ServiceAccount, RBAC, policy de rede e cliente para executá-lo.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: notes
  namespace: course-platform
spec:
  type: ClusterIP
  selector:
    app: notes
  ports:
    - name: http
      port: 8000
      targetPort: http
```

O pedido Alice/B do capítulo IAM não é um exemplo de Service. Aqui o defeito controlado é `selector: app=missing`: não há Pod correspondente. O DNS de `notes` pode continuar funcionando e o ClusterIP continuar existindo, enquanto o conjunto de endpoints fica vazio. A correção restaura o selector que corresponde aos Pods prontos.

## 4. Happy path, negativo, defesa e reteste

O cliente [check.py](/course-labs/phase16-platform/k8s/check.py) faz HTTP real dentro do Pod. `allow` envia apenas um token público de fixture; `unauth` omite o header.

```bash
kubectl -n course-platform exec -i client -- python - allow < check.py
kubectl -n course-platform exec -i client -- python - unauth < check.py
```

Resultados: `PASS HTTP 200 nota sintética`; depois `PASS HTTP 401...`. O 401 confirma que a rede chegou ao processo: não é falha de selector nem de DNS. A resposta HTTP só aparece depois de a conexão atravessar o Service.

Introduza uma única alteração:

```bash
kubectl -n course-platform patch service notes --type merge -p '{"spec":{"selector":{"app":"missing"}}}'
kubectl -n course-platform get endpointslices -l kubernetes.io/service-name=notes -o yaml
# Aguarde reconciliação até não haver endpoints prontos; então:
kubectl -n course-platform exec -i client -- python - deny-selector < check.py
kubectl -n course-platform patch service notes --type merge -p '{"spec":{"selector":{"app":"notes"}}}'
kubectl -n course-platform get endpointslices -l kubernetes.io/service-name=notes -o yaml
# Aguarde reaparecerem os dois endereços ready; reteste:
kubectl -n course-platform exec -i client -- python - allow < check.py
```

O erro negativo pode ser recusa ou timeout, dependendo do dataplane. Não exija um texto de erro específico. **Checkpoint 1:** a evidência causal combina mudança de selector, desaparecimento dos backends e falha HTTP; timeout sozinho também pode ser causado por CNI/firewall.

**Checkpoint 2:** se endpoints existem mas não estão prontos, examine readiness e logs. Não “corrija” desabilitando probes sem investigar por que `/health` falha.

## 5. Investigação e limites

Use `kubectl describe service notes`, `kubectl describe pod` e eventos para localizar namespace errado, label divergente e named port ausente. Se 8080 funciona direto no Pod mas 8000 no Service não, examine targetPort/selector/dataplane; se ambos falham, comece pelo processo e pela rede. Para testar nome versus rede, execute no cliente `python -c 'import socket; print(socket.getaddrinfo("notes",8000))'`; resolução não garante conexão.

NetworkPolicy pode bloquear conexões mesmo com endpoints prontos. ClusterIP define exposição de rede, não autenticação de usuário. Um port-forward é útil para diagnóstico, mas não substitui o teste Pod→Service da aula e não prova isolamento de NetworkPolicy.

Sem Docker/kubectl nesta edição, o app foi testado por HTTP real em loopback; Service/DNS/EndpointSlices continuam pendentes em runtime de cluster. Resultados descritos acima são esperados, não uma captura observada. Cleanup: `kind delete cluster --name course-phase16` remove só este laboratório.

## 6. Desafio

Mude a porta pública do Service para 9000 mantendo targetPort `http` e container 8080. Atualize apenas o cliente e preveja os endpoints. Demonstre por que os IPs/portas dos backends permanecem iguais, enquanto a porta de acesso muda. Restaure o manifesto e reteste 8000.

## 7. Quiz

1. O nome notes resolve, mas o selector não encontra Pods. O que é consistente?
A. DNS automaticamente recria o Deployment.
B. O Service pode existir sem backends prontos e a conexão falhar.
C. O ClusterIP passa a apontar para qualquer Pod no namespace.
D. IAM decide um novo IP de destino.

**Resposta:** B. DNS, seleção e disponibilidade dos backends são estados distintos.

2. O cliente deve usar qual porta neste lab?
A. 8080, pois containerPort sempre substitui port.
B. A porta do kube-apiserver.
C. 443, por usar token Bearer.
D. 8000; targetPort http resolve para 8080 nos Pods.

**Resposta:** D. A porta publicada pelo Service difere da porta do backend.

3. O cliente recebeu HTTP 401 sem token. O que foi demonstrado?
A. A conexão chegou ao servidor, que negou autenticação da aplicação.
B. A NetworkPolicy bloqueou o pacote antes do servidor.
C. O selector está vazio.
D. A resolução DNS falhou.

**Resposta:** A. Uma resposta HTTP do app evidencia conectividade até ele.

## 8. Flashcards

- **Selector** → cruza labels de Pods no namespace do Service.
- **EndpointSlice** → conjunto efetivo de endereços/portas e condições de prontidão.
- **port/targetPort** → entrada no Service versus destino nos Pods.
- **Readiness** → controla elegibilidade para receber tráfego normal pelos endpoints.
- **ClusterIP** → endereço virtual interno; não implementa login ou autorização de usuário.
