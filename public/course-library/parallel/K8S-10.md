# K8S-10 — Projeto Cloud/Containers/K8s: notas privadas no cluster local

**Trilha paralela:** Cloud / Containers / Kubernetes  
**Posição:** 30/30  
**Acesso:** livre; K8S-04 e K8S-09 são preparação recomendada, sem bloqueio.  
**Ambiente:** cluster kind próprio e descartável; nenhuma conta cloud.  
**Tempo sugerido:** 90–150 min, incluindo diagnóstico e relatório.

## 1. Missão e critérios de aceitação

Você recebe uma aplicação que atende `/note` e precisa entregar uma plataforma com duas réplicas. Um cliente autorizado deve ler a nota por `http://notes:8000/note`; um cliente com label diferente deve ser bloqueado antes do HTTP. Mesmo no cliente autorizado, omitir o token deve produzir HTTP 401. O processo precisa funcionar como UID 10001, sem capabilities, sem token automático da API e com a raiz somente leitura.

A entrega consiste em manifesto, imagem própria, execução dos casos abaixo e evidências de recuperação. Não basta mostrar Pods Running: isso não prova autorização da aplicação, seleção de backends, aplicação de NetworkPolicy ou restrições do processo.

O [laboratório completo](/course-labs/phase16-platform/k8s/README.md) inclui o servidor Python, Dockerfile, manifesto de todos os recursos e [capstone.sh](/course-labs/phase16-platform/k8s/capstone.sh), roteiro próprio desta unidade. Os componentes de Service e securityContext vêm de K8S-04/09; este projeto integra as decisões e demonstra falhas de camadas diferentes. Só há dados sintéticos, sem registry push, banco ou serviços externos em runtime.

## 2. Arquitetura: três identidades que não são intercambiáveis

| Elemento | Decisão que governa | Evidência esperada |
|---|---|---|
| Pod cliente com label `app=client` | Elegibilidade de rede pela NetworkPolicy | Conexão chega ao servidor |
| Token Bearer da fixture | Autenticação mínima no servidor Python | Token correto: 200; ausente: 401 |
| ServiceAccount `notes` | Permissões de API dadas por RoleBinding | Pode get pods/log; não get secrets |
| Service `notes`, port 8000 | Seleção e encaminhamento para porta nomeada `http` | Dois endpoints prontos na porta 8080 |
| Deployment `notes` | Duas réplicas e configuração dos processos | UID/GID 10001, CapEff zero, NoNewPrivs 1 |
| Secret `note-token` | Arquivo entregue ao Pod pelo kubelet | Processo lê token montado; não contém token no build |
| Volume `emptyDir` em `/tmp` | Área explicitamente gravável | Escrita em `/tmp` passa; em `/app` recebe EROFS |

O Bearer é público e fixo para tornar o teste repetível. Não é uma solução de identidade multiusuário nem proteção TLS: o HTTP circula em cluster local, e NetworkPolicy não criptografa tráfego. A nota não tem owner Alice/Bob; aqui a aplicação autoriza uma capacidade de leitura única. Não confunda este modelo com o isolamento por owner das aulas IAM, RLS ou Electron.

A NetworkPolicy seleciona os Pods `app=notes` e aceita origem `app=client` no mesmo namespace, porta TCP 8080. Não há regra de egress neste projeto. As policies aplicáveis se combinam por união: acrescentar uma policy ampla pode reabrir tráfego. Quem possui autorização para alterar labels/Pods pode modificar essa identidade de rede, por isso RBAC também precisa limitar operações de administração. Um Service ClusterIP não é uma barreira de autenticação. [Semântica de NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

## 3. Mecanismo do pedido e da falha

1. O DNS interno resolve `notes` para o ClusterIP do Service no namespace do cliente.
2. O Service seleciona Pods `app=notes`. O controlador publica os endereços/portas disponíveis em EndpointSlices; readiness determina quais podem receber tráfego normal.
3. O dataplane implementa o encaminhamento 8000 → 8080 e a política ingress. O modo exato de balanceamento depende da implementação; não presuma iptables ou um salto literal para cada objeto.
4. O servidor recebe `/note` e compara o header Authorization com a fixture. Rede permitida com token ausente termina em 401. Rede bloqueada termina antes da resposta HTTP.
5. O log do servidor mostra caminho/status, sem registrar Authorization. O cliente guarda resultado e erro; os estados do Service/endpoints explicam a camada que mudou.

**Exemplo resolvido:** troque apenas o selector do Service por `app=missing`. O DNS continua resolvendo, mas o Service fica sem backends prontos. A requisição pode expirar ou receber recusa de conexão. Restaure `app=notes`: os mesmos Pods voltam aos EndpointSlices e a leitura funciona. Mudar o token nessa etapa introduziria uma segunda causa e tornaria a prova ambígua.

**Checkpoint 1:** HTTP 401 permite culpar a NetworkPolicy por um bloqueio dessa requisição? Não: essa resposta confirma que a requisição chegou à aplicação. Ainda é possível haver outras falhas de rede, mas não foi um bloqueio pré-HTTP nesse pedido.

## 4. Preparação e baseline reproduzíveis

Pré-requisitos: Python 3.10+, Docker em execução, kind, kubectl compatível com o cluster e Helm 3.13+. É preciso rede na primeira resolução de imagens/chart, Linux nos containers e recursos para um control-plane e um worker. O namespace usa Pod Security `restricted` v1.34; utilize nó Kubernetes 1.34 ou mais recente compatível com o Cilium escolhido. Verifique a matriz do provedor antes de escolher versões diferentes.

```bash
cd public/course-labs/phase16-platform/k8s
python3 -m unittest -v test_server.py test_check.py
kind version
kubectl version --client
helm version --short
bash setup.sh
```

O setup cria apenas `course-phase16`, desabilita o CNI padrão do kind e instala Cilium chart 1.20.1; aguarda os nós e constrói `course-notes:phase16`. O [guia oficial Cilium/kind](https://docs.cilium.io/en/stable/installation/kind/) foi consultado em 2026-09-02. O manifesto usa `imagePullPolicy: Never`: `kind load docker-image` carrega a imagem nos nós sem publicá-la.

Guarde versões, digest efetivo de `python:3.13-alpine`, imagem dos nós, chart e SHA256 de `stack.yaml`, `server.py` e `Dockerfile`. Tags e a versão de nó escolhida pelo kind não formam um lock completo. Não declare reconstrução byte a byte apenas por conservar esses nomes.

Se o cluster já existe, confira que é o laboratório esperado e execute somente o roteiro de integração. `setup.sh` não apaga um cluster existente para tentar recriá-lo. Os scripts recusam contexto diferente de `kind-course-phase16`; o capstone também fixa esse contexto em cada operação. Não mude a guarda para executar em produção.

## 5. Executar o projeto e interpretar cada etapa

```bash
set -o pipefail
bash capstone.sh 2>&1 | tee capstone-evidence.log
# O pipeline preserva falhas do roteiro; sucesso do tee sozinho não aprova o lab.
```

O script aplica [stack.yaml](/course-labs/phase16-platform/k8s/stack.yaml), aguarda Deployment e cliente, testa contagem efetiva de endpoints e imprime checkpoints. A espera tem limite: falhar por timeout exige diagnóstico, não aumentar indefinidamente o limite. A imagem/projeto não implementa um simulador de Kubernetes; os comandos abaixo só produzem evidência se o cluster real estiver disponível.

| Etapa | Uma mudança controlada | Resultado esperado | Defesa e reteste |
|---|---|---|---|
| A: baseline | Nenhuma; token correto e depois ausente | 2 endpoints; 200 e 401 respectivamente | 200 continua disponível |
| B: selector | `app=notes` → `app=missing` no Service | 0 endpoints prontos; timeout/recusa | Restaurar selector; 2 endpoints e 200 |
| C: rede | Label do cliente `client` → `guest` | Timeout apesar de 2 endpoints prontos | Restaurar label; 200 |
| D: API | Mesma SA, mudar recurso de pods/log para secrets | `yes` para logs; `no` para secrets | Manter Role restrita |
| E: processo | Mesma imagem, escrita na raiz versus no volume | EROFS em `/app`; escrita em `/tmp` | HTTP 200 preservado |

O [check.py](/course-labs/phase16-platform/k8s/check.py) distingue `allow`, `unauth`, `deny-selector` e `deny-policy`. Não aceita erro DNS nem 404 como demonstração de bloqueio de rede. Para selector vazio aceita timeout ou recusa TCP; para o caso Cilium/guest exige timeout. Uma implantação de CNI com rejeição explícita pode produzir outro erro: registre essa diferença e investigue, sem classificar automaticamente todo exit não zero como controle aprovado.

A etapa C ainda não transforma timeout em prova isolada de policy: o roteiro compara baseline, uma label alterada, endpoints preservados e reteste após restauração. Em diagnóstico aprofundado, acrescente estado/fluxos do Cilium disponíveis no seu ambiente. Não há Hubble configurado por este projeto e o log HTTP não pode mostrar pedidos que nunca chegaram.

O [check_process.py](/course-labs/phase16-platform/k8s/check_process.py) roda dentro do container e exige UID/GID, CapEff, NoNewPrivs, seccomp modo filtro, ausência do token automático da SA, erro `EROFS` na raiz e sucesso no volume. Falha de `kubectl exec`, arquivo inexistente ou erro de permissão diferente não passam por hardening. O perfil exato de syscalls continua dependendo do runtime; `Seccomp:2` não é uma lista de regras.

O capstone restaura selector e label mesmo ao sair por erro. Ele não remove o namespace nem esconde uma falha de restauração. Após diagnosticar, execute novamente o mesmo comando e conserve tanto a falha quanto o reteste.

## 6. Evidência de API versus leitura do Secret montado

O teste RBAC usa `kubectl auth can-i --as=system:serviceaccount:course-platform:notes` com a identidade do administrador do cluster local autorizada a fazer impersonation. Isso consulta a autorização, mas não inicia uma sessão autenticada da ServiceAccount nem efetua uma leitura de Secret. O token automático permanece desabilitado.

Por que o servidor lê `/run/secrets/token` apesar de `can-i get secrets` retornar `no`? A montagem é realizada pela infraestrutura do nó a partir da configuração do Pod. A Role da aplicação não precisa conceder leitura arbitrária de secrets na API para que um Secret específico seja montado. São caminhos de acesso distintos. Base64 não criptografa Secret, e o arquivo fictício montado não demonstra gerenciamento seguro de credenciais reais. [RBAC oficial](https://kubernetes.io/docs/reference/access-authn-authz/rbac/).

**Checkpoint 2:** se você concedesse `get secrets` à SA, o acesso do cliente guest pela rede mudaria? Não: a decisão de API não altera automaticamente as labels selecionadas pela NetworkPolicy.

**Checkpoint 3:** uma leitura 200 e `CapEff=0` garantem isolamento entre notas de usuários diferentes? Não: o app não tem usuários/documentos com owners. Liste os controles observados sem aumentar a conclusão além do contrato.

## 7. Diagnóstico com hipótese e evidência

| Sintoma | Hipótese a testar | Próxima observação útil |
|---|---|---|
| Nó NotReady antes de Cilium | CNI ainda não instalado ou não saudável | Pods/rollout do Cilium, eventos do nó |
| `ErrImageNeverPull` | Imagem não foi carregada nos nós | Tag construída e `kind load docker-image` do setup |
| Pods Running, endpoints vazios | Selector divergente ou readiness falhou | Labels, EndpointSlices, `/health` e logs |
| 401 no baseline | Token não corresponde ao arquivo | Header no cliente e montagem; não imprimir credenciais reais |
| guest retorna 200 | CNI/policy não aplica restrição ou há outra policy permissiva | Policy aplicada, selectors, namespace e CNI |
| guest tem timeout e client também | Falha geral ainda possível | DNS/endpoints/rede; recuperar baseline antes de concluir |
| `EROFS` em `/tmp` | Volume ausente ou mount errado | VolumeMounts e spec real do Pod |
| EACCES na raiz | Permissão DAC, não prova de readonly | Owner do diretório/imagem e erro exato; reconstruir imagem atual |
| Erro de impersonation | Operador não pode realizar consulta em nome da SA | Contexto local e privilégios do operador, sem ampliar a Role notes |

Não faça rootfs gravável nem conceda cluster-admin para eliminar um erro de setup. Se o aplicativo precisar gravar cache, forneça volume limitado para o diretório necessário e repita os testes de rede e HTTP. O namespace `restricted` controla admissão; a aula K8S-09 demonstra também um dry-run rejeitado e separa esse resultado do processo em execução.

## 9. Desafio de revisão

Um colega propõe substituir a NetworkPolicy por uma regra que permite todo Pod do namespace, alegando que o Bearer já basta. Antes de mudar qualquer coisa, preveja qual linha da matriz deve falhar. Em uma cópia de laboratório, demonstre que guest deixa de ser bloqueado; restaure a policy original e repita guest e client. Explique por que possuir o token e satisfazer a regra de rede são condições independentes, e por que labels só são confiáveis quando a capacidade de alterá-las também é controlada.

## 10. Quiz

1. DNS resolve notes, endpoints passam de dois para zero após mudar selector. Qual correção atua na causa demonstrada?
A. Conceder get secrets à ServiceAccount.
B. Restaurar selector compatível com os Pods e aguardar endpoints prontos.
C. Retirar o header Authorization.
D. Ativar root no container.

**Resposta:** B. A mudança isolada rompeu a seleção dos backends, não a identidade do aplicativo.

2. Cliente guest dá timeout. Qual evidência adicional fortalece a atribuição à NetworkPolicy?
A. Apenas o nome do namespace.
B. Uma captura do manifesto sem aplicação.
C. Endpoints continuam prontos, só a label mudou, e restaurá-la recupera 200.
D. O teste JavaScript de Electron passou.

**Resposta:** C. Essa sequência discrimina a mudança de política de falhas gerais de disponibilidade.

3. SA não pode get secrets, mas Python lê o arquivo montado. Isso é contraditório?
A. Sim; o kubelet ignorou RBAC.
B. Sim; runAsNonRoot deveria impedir toda leitura.
C. Não; qualquer Pod sempre pode ler qualquer Secret.
D. Não; montagem pela infraestrutura e chamada de API pela SA são acessos distintos.

**Resposta:** D. O Pod recebe o Secret explicitamente configurado sem ganhar listagem/leitura arbitrária na API.

4. `kubectl exec` falhou porque não encontrou o Pod. Isso aprova o teste de raiz readonly?
A. Não; é preciso executar dentro do container e observar EROFS na operação prevista.
B. Sim; todo exit não zero demonstra hardening.
C. Sim; a ausência do Pod prova seccomp ativo.
D. Só se o terminal mostrar a palavra denied.

**Resposta:** A. A falha precisa estar na fronteira que o experimento pretende verificar.

## 11. Flashcards

- **Três identidades** → label para política de rede; Bearer para app; ServiceAccount para API.
- **2→0→2 endpoints** → seleção quebrada e recuperada; compare também HTTP.
- **Timeout correlacionado** → combine uma mudança, backends saudáveis e reteste; isoladamente é ambíguo.
- **Sem token SA montado** → reduz credenciais no Pod; não elimina a existência da ServiceAccount/RBAC.
- **Secret montado** → acesso ao arquivo concedido pelo Pod spec; não grant genérico na API.
- **EROFS versus EACCES** → filesystem readonly versus permissão de acesso; ambos falham, mas por mecanismos diferentes.
- **Aceitação do capstone** → happy path, negativos específicos e recuperação em runtime, com limites declarados.
