## Problema e objetivo

Duas falhas diferentes exigem evidências diferentes: gravar fora do heap e ultrapassar INT_MAX. Compile e ligue com ASan/UBSan, interprete cada diagnóstico e compare ao caminho corrigido.

## Mecanismo e exemplo resolvido

ASan acompanha acessos à memória e regiões inválidas; UBSan instrumenta operações cujo comportamento C é indefinido, como overflow signed. O programa escolhe um modo por argumento para que a primeira falha não esconda a segunda. -g preserva informações de fonte; -O0 facilita relacionar execução e linhas; -fno-omit-frame-pointer ajuda pilhas. -fno-sanitize-recover=all faz UBSan encerrar com status não zero.

asan: aloca 2 ints e escreve índice 2 → heap-buffer-overflow. ubsan: INT_MAX+1 → signed integer overflow. corrigido: usa índice 1 e testa o limite antes de incrementar → imprime limite recusado e ultimo=9, com status 0.

```c
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
int main(int argc, char **argv) {
    if (argc != 2) { fputs("use: asan | ubsan | corrigido\n",stderr); return 2; }
    if (strcmp(argv[1],"asan") == 0) {
        int *p = malloc(2 * sizeof *p);
        if (!p) return 1;
        volatile int indice = 2; /* índices válidos são 0 e 1 */
        p[indice] = 9;          /* erro intencional: heap-buffer-overflow */
        free(p);
    } else if (strcmp(argv[1],"ubsan") == 0) {
        volatile int maximo = INT_MAX;
        printf("%d\n", maximo + 1); /* overflow signed: comportamento indefinido */
    } else if (strcmp(argv[1],"corrigido") == 0) {
        int valores[2] = {0,9};
        int maximo = INT_MAX;
        if (maximo == INT_MAX) puts("incremento recusado: limite de int");
        printf("ultimo=%d\n",valores[1]);
    } else { return 2; }
    return 0;
}
```

## Prática e autoexplicação

Parcial: marque quais índices são válidos no modo asan. Independente: crie uma cópia corrigida que receba incremento=0 ou 1 e retorne erro quando não couber em int. Autoexplicação: por que executar somente corrigido não prova que os modos defeituosos são detectados?

## Solução comentada e checkpoints

Índices válidos 0 e 1. Para incremento não negativo, verifique maximo>INT_MAX−incremento antes da soma. Checkpoints: cada modo defeituoso é executado em processo separado, produz o diagnóstico correspondente e sai não zero; corrigido não contém runtime error nem ERROR: AddressSanitizer.

## Robustez, reteste e diagnóstico

Nunca trate overflow signed como wraparound garantido. Flags devem aparecer no comando que liga o binário, não só na produção do objeto. Se houver erro de runtime ASan indisponível, registre a limitação do compilador/ambiente em vez de declarar ausência de bug. Reteste os três modos; instrumentação não prova segurança de caminhos não executados.

Se o runtime emitir `LeakSanitizer has encountered a fatal error` por restrição de `/proc`/ptrace, isso não é diagnóstico de UAF nem de overflow. Neste contêiner, os caminhos saudáveis exigiram `ASAN_OPTIONS=detect_leaks=0 "./C-19" corrigido. Repita também os casos defeituosos com a mesma opção: ASan ainda deve nomear o acesso inválido; UBSan ainda deve nomear overflow. Essa execução não verifica vazamentos de memória. Em máquina com suporte completo, preserve a detecção de leaks.

## Quiz

1. **Qual ferramenta diagnostica INT_MAX+1?**
   - A) UBSan
   - B) ASan sozinho, por validar todo resultado aritmético
   - C) -Wall sozinho, por monitorar a soma durante a execução

2. **Por que separar os modos em processos?**
   - A) para que os modos compartilhem a mesma alocação
   - B) para que o modo corrigido apague o diagnóstico anterior
   - C) para uma falha não impedir a outra evidência

3. **Uma execução limpa significa:**
   - A) ausência de todos os bugs
   - B) nenhuma violação detectada naquele caminho
   - C) compilação sem warnings

**Gabarito comentado:** 1: A — é comportamento indefinido aritmético. 2: C — ASan pode encerrar imediatamente. 3: B — a cobertura é limitada ao que foi executado.
