## 2. Visão geral

Prototype pollution altera propriedades herdadas em JavaScript e pode modificar comportamento de objetos em toda a aplicação.

## 3. Aprofundamento: o que realmente está acontecendo

Em JavaScript, objetos normalmente herdam de protótipos. O risco aparece quando uma operação de merge/cópia permite que chaves especiais atinjam essa cadeia de herança e alterem propriedades vistas por objetos que nunca receberam aquele valor diretamente.

Prototype pollution explora a forma como objetos JavaScript herdam propriedades. O risco aparece quando dados externos são mesclados sem bloquear chaves especiais.

## 5. Conceitos fundamentais

### 1. __proto__
Acesso histórico ao protótipo que pode ser abusado em merges inseguros.
### 2. Prototype chain
Cadeia de herança usada para resolver propriedades.
### 3. Deep merge
Combinação recursiva de objetos que precisa filtrar chaves perigosas.
### 4. Own property
Propriedade que pertence diretamente ao objeto, sem herança.

## 6. Fluxo técnico

1. **Entrada externa vira objeto**
2. **Função de merge percorre chaves recursivamente**
3. **Chaves especiais alcançam prototype**
4. **Novos objetos herdam valores inesperados**
5. **A lógica da aplicação pode mudar sem alteração explícita do objeto**

## 7. Exemplo técnico — Merge defensivo

```ts
const BLOCKED = new Set(["__proto__", "prototype", "constructor"]);

function safeAssign(target: Record<string, unknown>, source: Record<string, unknown>) {
  for (const [key, value] of Object.entries(source)) {
    if (BLOCKED.has(key)) continue;
    target[key] = value;
  }
  return target;
}
```

## 8. Por que a vulnerabilidade/mecanismo acontece

Prototype pollution explora a forma como objetos JavaScript herdam propriedades. O risco aparece quando dados externos são mesclados sem bloquear chaves especiais.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 11. Como corrigir / reduzir risco

Bloqueie chaves especiais em merges, use Object.create(null) quando apropriado e atualize bibliotecas vulneráveis.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## Problema e competência verificável — AULA-048 (oficina A)

**Caso inédito:** Um configurador mescla preferências recebidas do cliente e encontra uma chave própria __proto__ junto de theme e density.

**Decisão crítica:** propriedades especiais de input não podem alterar o prototype de objetos de aplicação.

**Hipótese que precisa ser refutada:** campos aprovados criam objeto sem prototype; chave __proto__ é rejeitada.

**Evidência esperada:** safePreferencesMerge(theme=dark,density=compact) aceita; '__proto__' falha.

**Competência:** explicar a causa, prever observáveis, executar teste com entrada legítima e adversarial, selecionar a defesa e declarar os limites do teste.

### Mecanismo e exemplo resolvido

1. **Estado inicial:** Um configurador mescla preferências recebidas do cliente e encontra uma chave própria __proto__ junto de theme e density.
2. **Entrada e fronteira:** propriedades especiais de input não podem alterar o prototype de objetos de aplicação.
3. **Decisão:** Usar whitelist de esquema antes de merge, objetos sem prototype quando adequados e dependências atualizadas.
4. **Observação:** safePreferencesMerge(theme=dark,density=compact) aceita; '__proto__' falha.
5. **Interpretação:** campos aprovados criam objeto sem prototype; chave __proto__ é rejeitada. Não confunda a evidência de um modelo isolado com exploração ou comprovação em produto de terceiros.
