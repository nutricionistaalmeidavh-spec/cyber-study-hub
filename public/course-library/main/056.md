## 2. Visão geral

APIs falham quando autorizam objetos, funções ou campos de forma implícita. BOLA, BFLA e mass assignment exigem controles explícitos.

## 3. Aprofundamento: o que realmente está acontecendo

BOLA, BFLA e Mass Assignment atuam em camadas distintas: objeto, função e campos. Uma API pode corrigir uma camada e continuar vulnerável em outra.

BOLA, BFLA e Mass Assignment são falhas de autorização em camadas diferentes: objeto, função e campos alteráveis. Uma API segura precisa controlar as três.

## 5. Conceitos fundamentais

### 1. BOLA
Acesso indevido a objetos por falha de autorização no recurso.
### 2. BFLA
Acesso indevido a funções/ações por falha de autorização funcional.
### 3. Mass Assignment
Binding automático de campos que não deveriam ser alteráveis.
### 4. DTO
Estrutura explícita que limita campos aceitos na entrada.

## 6. Fluxo técnico

1. **Request autenticado chega à API**
2. **Rota define qual função pode ser usada**
3. **Objeto solicitado é checado contra o usuário**
4. **Campos recebidos são filtrados por esquema/allowlist**
5. **Camada de domínio persiste somente alterações autorizadas**

### Checkpoint 1

Descreva o fluxo acima sem usar o nome da técnica. Onde está a primeira decisão de segurança?

## 7. Exemplo técnico — Ownership + allowlist de campos

```ts
const allowedFields = ["displayName", "timezone"] as const;

async function updateProfile(userId: string, targetId: string, body: any) {
  if (userId !== targetId) throw new Error("Forbidden");

  const patch = Object.fromEntries(
    allowedFields.filter(k => k in body).map(k => [k, body[k]])
  );

  return db.user.update({ where: { id: targetId }, data: patch });
}
```

### Como ler o exemplo

Autorização do objeto e controle de campos são decisões distintas.

Ao revisar cada linha/bloco, marque:

- o dado de entrada;
- o estado confiável usado na decisão;
- a condição de rejeição;
- o efeito/log que você esperaria observar.

## 8. Por que a vulnerabilidade/mecanismo acontece

BOLA, BFLA e Mass Assignment são falhas de autorização em camadas diferentes: objeto, função e campos alteráveis. Uma API segura precisa controlar as três.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 9. Laboratório guiado — Matriz de autorização de uma API fictícia

**Modo:** Celular + PC

1. Crie três perfis: usuário, gerente e admin.
2. Liste rotas e operações possíveis para cada perfil.
3. Para cada rota, marque objeto permitido e campos alteráveis.
4. No PC, escreva testes que tentam acessar objeto alheio ou campo privilegiado.
5. Confirme retorno 403/404 conforme a política.

### Resultado esperado

Cada endpoint deve responder a: quem pode executar, em qual objeto e quais campos pode alterar.

### Checkpoint 2 — antes da correção

Qual evidência mínima demonstra a condição estudada sem ampliar impacto desnecessariamente?

### Checkpoint 3 — depois da correção

Repita o mesmo teste e registre a diferença. Se o cenário mudou, o reteste não é comparável.

## 10. Como detectar

Correlacione usuário, objeto, ação e campos alterados; alerte para mudanças de papel ou propriedade indevidas.

Transforme a frase acima em telemetria:

```text
quem?
onde?
qual ação?
qual recurso/destino?
qual resultado?
qual sequência temporal?
```

## 11. Como corrigir / reduzir risco

Autorize objeto e função, use DTOs/allowlists de campos e testes negativos de permissão.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 12. Troubleshooting

- Confirme versões, portas, identidade e estado inicial do laboratório.
- Colete baseline antes de mudar configuração.
- Se uma ferramenta “não encontrar”, verifique cobertura e fonte de dados antes de concluir ausência de risco.
- Se um finding aparecer, leia a evidência e a pré-condição antes de classificá-lo.
- Mantenha laboratório isolado e restaure snapshot quando a aula pedir mudança de configuração.

## 13. Erros comuns de raciocínio

- Confundir indicador com confirmação.
- Concluir vulnerabilidade pelo nome da ferramenta.
- Aplicar hardening sem testar impacto operacional.
- Não diferenciar prevenção de detecção.
- Fazer correção e esquecer o reteste.
