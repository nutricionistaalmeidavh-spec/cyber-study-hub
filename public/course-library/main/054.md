## 2. Visão geral

JWT é um formato de token assinado; segurança depende de validação de assinatura, algoritmo, claims, expiração e armazenamento.

## 3. Aprofundamento: o que realmente está acontecendo

JWT é um envelope assinado para claims; não é criptografia por padrão e não substitui uma estratégia de sessão/autorização. `decode` e `verify` respondem perguntas diferentes.

## 5. Conceitos fundamentais

### 1. Header
Parte do JWT que declara tipo e algoritmo.
### 2. Claims
Dados como sub, aud, iss e exp.
### 3. Signature
Prova de integridade/autenticidade do token.
### 4. Key rotation
Troca planejada de chaves com suporte a múltiplos kid válidos.

## 6. Fluxo técnico

1. **Servidor emite claims**
2. **Token é assinado**
3. **Cliente apresenta o token**
4. **Servidor valida assinatura e claims**
5. **Autorização usa claims confiáveis, não dados não verificados**

## 7. Exemplo técnico — Validação explícita de claims

```ts
const payload = await jwtVerify(token, publicKey, {
  algorithms: ["RS256"],
  issuer: "https://auth.exemplo.local",
  audience: "cyber-study-api"
});

if (!payload.payload.sub) {
  throw new Error("Token sem subject");
}
```

### Como ler o exemplo

Fixar algoritmo, issuer e audience reduz ambiguidades na validação.

## 8. Por que a vulnerabilidade/mecanismo acontece

JWT é um formato de token assinado, não uma sessão mágica. Segurança depende de validação de assinatura, algoritmo, issuer, audience, expiração e estratégia de revogação.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 11. Como corrigir / reduzir risco

Fixe algoritmos aceitos, valide iss/aud/exp, proteja chaves e implemente rotação/revogação conforme o risco.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 18. Oficina A — JWT Security

**Objetivo mensurável:** Explicar verificação criptográfica, chave permitida, algoritmo fixo, emissor, audiência, expiração e autorização por recurso.

### Situação profissional e pré-requisitos

A API da escola aceita JWTs do emissor `https://issuer.local`, para `aud=api-demo`, com `alg=HS256`. Ler base64 do payload é trivial e não prova que o emissor assinou as claims.

Para começar, identifique o ator, o dado controlável, o componente que decide, o recurso afetado e o resultado que realmente pode ser observado. Não atribua ao laboratório funções de produção. Refaça a distinção entre hipótese, evidência e interpretação antes de qualquer mudança no controle.

### Mecanismo: acompanhe o dado até a decisão

Um JWS possui header, payload e assinatura. O verificador deve escolher algoritmos aceitos por configuração confiável, nunca confiar em `alg` sozinho; validar assinatura antes de confiar em `sub`, `iss`, `aud`, `exp` e tipo do token; restringir chave por algoritmo e finalidade. JWT assinado não é criptografado.

**Exemplo resolvido.** `makeJwt` produz token fictício assinado por HMAC SHA-256; `verifyJwt` rejeita alteração de `sub` sem recalcular assinatura, `aud` errada, expiração e header `alg:none`. A chave está em memória de teste, não é credencial real.

**Questão de compreensão:** em qual momento a entrada deixa de ser mero dado e passa a interferir em uma decisão? Formule uma frase citando o objeto exato, a condição de falha e a observação esperada. Não confunda a explicação de mecanismo com uma prova de exploração.

5. Não modifique proteções do host nem use credenciais reais. Um resultado de teste automático não substitui teste end-to-end no navegador ou revisão de integração real.

**Resultado verificável:** Mesmo com assinatura válida, `aud=api-outro` deve falhar. Uma API não pode usar apenas `sub=aluno` para autorizar qualquer objeto: isso é outra camada de controle.

**Limites do experimento:** O demonstrador cobre HS256 e claims limitadas, sem JWKS, rotação de chaves, replay, revogação ou verificação de ID Token OIDC em produção; use bibliotecas maduras.
