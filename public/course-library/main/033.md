# Aula 033 — De Pista a Hipótese

**Trilha principal:** Pentest & Secure Development · **Duração sugerida:** 45–60 min · **Estado:** aprofundamento editorial A (IA) sujeito a registro SHA-256.  
**Ambiente:** Node.js 22+, sem Docker obrigatório, sem assinatura ou API paga. Testes só com dados fictícios, em memória ou serviço `127.0.0.1` criado pela suíte.

> Só execute técnicas ativas em ativos próprios ou autorizados explicitamente. O resultado de uma fixture local não se transfere automaticamente para sistemas externos. As atividades não requerem credenciais reais.

## Problema e objetivo mensurável

Um scanner identifica o cabeçalho `Server: http/1.1` e um link `/fatura/F001`. O primeiro é apenas informação. O segundo sugere examinar autorização por objeto, mas não prova vazamento. Só um teste fictício de duas identidades e mesmo objeto com repetição controlada pode sustentar uma falha.

**Competência observável:** Distinguir observação, hipótese testável e evidência reproduzível evitando falso positivo. Para demonstrá-la, o estudante deve prever a decisão, executar os casos positivos e negativos e explicar evidências, hipóteses alternativas e limites da simulação. Não basta nomear ferramentas.

## Fundamentos e pré-requisitos recomendados

Os pré-requisitos são recomendações, nunca bloqueio da aula: HTTP básico, diferença entre autenticação/autorização, lógica booleana e leitura de logs. Onde necessário, use o vocabulário abaixo antes de abrir o terminal.

1. **Conceito 1.** Sinal: observação bruta que ainda pode ter múltiplas explicações.

2. **Conceito 2.** Hipótese falsificável: previsão que pode ser derrubada por um teste controlado.

3. **Conceito 3.** Achado confirmado: efeito demonstrado com contexto, contraexemplo e repetição.

## Mecanismo técnico: entrada, fronteira, controle e resultado

Classificação depende da força causal da evidência: banner → INFO; resposta 200 isolada de outro usuário → HIPÓTESE; acesso indevido repetível com objeto existente e prova sintética → CONFIRMADO; requisição negada com acesso legítimo funcionando → CONTROLADO. Os rótulos são específicos deste laboratório, não um padrão universal de severidade. Uma requisição 500 ou o nome de uma biblioteca não constituem comprovação.

**Modelo de decisão:** estado inicial → entrada controlada → componente que decide → efeito observável → comparação com a política. Sempre diga onde mora a autoridade: aplicativo, navegador, banco, armazenamento ou processo de entrega. O nome de uma ferramenta não responde essa pergunta.

### Exemplo resolvido e comentado

```js
import { triageSignal } from './models.mjs';
const marker={kind:'object-access',differentUser:true,observed:200,baseline:200,repeatable:false};
console.log(triageSignal(marker)); // HIPOTESE
console.log(triageSignal({...marker,repeatable:true,proof:'OWN-LAB'})); // CONFIRMADO
```

> Este trecho é um recorte da fixture da aula; execute o teste completo pelo comando abaixo, a partir da raiz do projeto. A sintaxe de import acima representa o módulo do diretório de laboratório, e não uma dependência publicada.

**Evidência esperada:** INFO, HIPOTESE, CONFIRMADO e CONTROLADO aparecem somente quando critérios específicos mudam.

## Laboratório reproduzível — um positivo e um negativo

**Requisitos:** Node.js 22 ou superior, terminal local e repositório. O código e os testes estão em `/course-labs/a031-040/models.mjs` e `/course-labs/a031-040/lab.test.mjs`. O serviço HTTP criado na aula 032 e no capstone escuta exclusivamente `127.0.0.1` em porta aleatória, fecha ao terminar e não faz requisições a serviços externos.

```sh
# A partir da raiz do repositório
node --test public/course-labs/a031-040/lab.test.mjs
```

**Roteiro guiado com previsão e feedback:**

1. Classifique o banner sem usar CVE por associação de strings.
2. Preveja o rótulo quando a resposta de Bob é 200, mas ainda não existe repetição.
3. Faça a segunda comparação (mesmo objeto Alice/Bob) e explique por que o resultado muda a confiança, não necessariamente a severidade.

**Checkpoint A — antes:** anote qual resultado positivo preserva o uso legítimo.  
**Checkpoint B — depois:** anote o caso negativo, dado de entrada, controle que decidiu e resultado real.  
**Checkpoint C — interpretação:** declare uma hipótese alternativa e qual dado adicional seria necessário para descartá-la.

**O que deve aparecer:** INFO, HIPOTESE, CONFIRMADO e CONTROLADO aparecem somente quando critérios específicos mudam. Arquive somente o nome do teste e os valores de estado/decisão sintéticos; não adicione tokens ou dados pessoais. A suíte pode reportar também testes das outras nove aulas, mas cada assert está identificado pelo ID desta aula.

### Quando algo não funciona

Em um sistema real, ter duas respostas 200 não basta se os corpos são públicos ou objetos diferentes; confirme políticas e resultado antes de relatar.

Para recuperar: confira a versão `node --version`, inicie no diretório raiz, execute novamente uma única vez após corrigir a causa e compare os resultados; não modifique expectativas só para tornar os testes verdes.

## Detecção, prevenção e reteste

**Evidência a observar:** Colete identidade fictícia, recurso e decisão; mantenha hipótese e evidência em campos distintos no finding.

**Medida corretiva:** Rastreie causa, teste positivo e negativo, e não converta detecção genérica em incidente. Confirmação é separada de priorização.

**Critério de reteste:** o caminho originalmente indevido deve ser negado sob as mesmas pré-condições, enquanto o caminho legítimo continua funcionando. Documente casos não cobertos. Um caso rejeitado não é automaticamente prova de que todas as variações estão seguras.

## Prova final independente — competência aplicada

**Novo cenário, distinto da fixture:** Um relatório automatizado aponta 'biblioteca antiga' apenas pelo texto de um HTML armazenado em cache. Outra pessoa demonstra que a versão real foi atualizada, mas o banner segue antigo.

Responda *sem abrir o gabarito*, incluindo resultado previsto e ao menos uma limitação:

1. O que foi realmente observado, sem interpretar o banner como prova?
2. Formule duas hipóteses concorrentes para o banner antigo.
3. Qual evidência independente poderia discriminar cache antigo de dependência vulnerável?
4. Que classificação daria antes do teste e depois de confirmar apenas cache desatualizado?
5. Quando seria legítimo recomendar correção de dependência?
6. Como evitar que o caso altere indevidamente a métrica de vulnerabilidades confirmadas?

Após concluir, compare seu relatório com o [gabarito independente e rubrica](/course-labs/a031-040/answer-keys/AULA-033.md). A publicação do gabarito não substitui a tentativa independente.
