# Aula 205 — Tool / Agent Abuse

**Trilha:** AI / LLM Security  
**Profundidade:** P  
**Tempo sugerido:** 45–60 min  
**Escopo:** laboratório local, dados sintéticos e aplicações próprias/autorizadas.

> Modelos gerativos produzem texto; decisões de segurança continuam sendo responsabilidade de controles determinísticos, identidade, autorização, isolamento e observabilidade.

## 1. Conexão no roadmap

Anterior: **RAG Security**.  
Próxima: **Model & AI Supply Chain**.

Pré-requisitos são recomendados, nunca obrigatórios.

## 2. Objetivos

Ao final, você deve conseguir:

1. explicar Tool / Agent Abuse em termos de componentes e fronteiras de confiança;
2. diferenciar comportamento do modelo de decisão de política;
3. montar um teste reproduzível com dados fictícios;
4. registrar evidências e limitações;
5. aplicar mitigação no componente correto;
6. retestar sem depender de “o modelo pareceu obedecer”.

## 3. Fundamentos

### 1. Tool capability
A ferramenta define o que o agente consegue realmente fazer no mundo externo.

### 2. Least privilege
Cada tool deve ter escopo, identidade e permissões mínimos.

### 3. Human approval
Ações irreversíveis, financeiras, destrutivas ou de alto impacto exigem barreira de aprovação independente do modelo.

## 4. Arquitetura mental

```text
usuário / conteúdo externo
          ↓
normalização + classificação de confiança
          ↓
modelo / RAG / planner
          ↓
POLICY ENFORCEMENT POINT
          ↓
identidade + autorização + aprovação
          ↓
tool / banco / API
          ↓
audit log + resultado
```

O modelo pode **propor**. A política decide se a proposta pode virar ação.

## 5. Exemplo técnico

```ts
const TOOLS = {
  readReport: { risk: 'low', approval: false },
  updateRecord: { risk: 'high', approval: true }
};

function mayRun(tool: keyof typeof TOOLS, approved: boolean) {
  return !TOOLS[tool].approval || approved;
}
```

O exemplo não tenta “resolver AI Security com regex ou if”. Ele mostra onde colocar uma **barreira determinística** que continue válida mesmo quando a saída do modelo muda.

## 6. Laboratório guiado

**Objetivo:** Criar um mock agent local com tools de leitura e uma tool de alteração protegida por política determinística e aprovação explícita.

### Passo 1 — baseline
Crie dados totalmente fictícios e execute o fluxo legítimo. Registre input, contexto entregue ao modelo, decisão de política, tool call e output.

### Passo 2 — variação adversarial segura
Introduza apenas texto sintético que tente contradizer a finalidade esperada, acessar documento de outro usuário ou pedir uma tool acima do privilégio permitido.

### Passo 3 — evidência
A evidência relevante é a decisão do controle: `allow`, `deny`, `approval-required`, ACL aplicada, redaction efetuada ou tool call bloqueada. **A resposta textual do modelo, sozinha, não comprova segurança.**

### Passo 4 — correção
Mova a proteção para a camada correta: ACL antes de RAG, least privilege na identidade, schema na tool, aprovação fora do modelo, secrets fora do contexto ou validação de output.

### Passo 5 — reteste
Repita exatamente os casos positivos e negativos. O fluxo legítimo deve continuar funcionando e a condição proibida deve permanecer bloqueada.

## 7. Checkpoints

- Consigo dizer qual componente tem autoridade real?
- Consigo mostrar qual dado externo é não confiável?
- A proteção funciona se o modelo gerar uma frase diferente?
- Tenho um teste negativo reproduzível?
- O log permite reconstruir quem pediu, qual tool foi proposta e quem autorizou?

## 8. Detecção e observabilidade

Registre pelo menos:

```text
request_id
user_id / agent_id
model_version
retrieval_document_ids
tool_name
validated_arguments
policy_decision
approval_actor
result_class
```

Não grave segredos inteiros nem dados pessoais desnecessários apenas para “ter mais log”.

## 9. Defesa em camadas

1. **Minimize o contexto** entregue ao modelo.
2. **Separe instruções de dados** externos.
3. **Autorize antes da recuperação** de conteúdo privado.
4. **Valide argumentos de tools** por schema e regra de negócio.
5. **Use identidades separadas e least privilege**.
6. **Exija aprovação para ações de alto impacto**.
7. **Trate output como não confiável** antes de renderizar/executar.
8. **Versione prompts, policies, modelo e testes**.

## 10. Erros comuns

- acreditar que “system prompt forte” substitui autorização;
- colocar secrets no prompt e esperar que o modelo não os revele;
- aplicar ACL depois que documentos privados já entraram no contexto;
- entregar tool administrativa ao agente e tentar controlar tudo por linguagem natural;
- não testar mudanças de modelo;
- não saber qual identidade executou uma ação.

## 11. Troubleshooting

Se o teste for instável, não aumente a quantidade de prompts aleatoriamente. Separe:

1. entrada;
2. retrieval;
3. modelo;
4. policy;
5. tool;
6. output.

Teste cada fronteira de maneira determinística sempre que possível.

## 12. Mini desafio

Desenhe um assistente que lê documentos e pode criar um rascunho, mas **não pode enviar**, excluir ou alterar permissões. Marque onde você colocaria ACL, validação de tool, identidade e aprovação.

## Flashcards
- **Tool capability** → A ferramenta define o que o agente consegue realmente fazer no mundo externo.
- **Least privilege** → Cada tool deve ter escopo, identidade e permissões mínimos.
- **Human approval** → Ações irreversíveis, financeiras, destrutivas ou de alto impacto exigem barreira de aprovação independente do modelo.
- **Baseline** → comportamento conhecido antes da variação de teste.
- **Evidência** → dado observável que sustenta ou enfraquece uma hipótese.
- **Reteste** → repetição do mesmo caso após a mudança defensiva para provar o efeito.
