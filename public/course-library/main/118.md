# Aula 118 — Xrefs, Strings e Imports

**Trilha:** Assembly & RE · **Profundidade:** N · **Tempo:** 55 minutos.  
**Pré-requisitos recomendados:** grafo de chamadas e noção de referência estática; não bloqueiam o acesso.  
**Ambiente:** Node.js 22+, fixtures sintéticas de autoria do curso; sem licenças, binários de terceiros, API paga ou depurador obrigatório.

> Use apenas executáveis próprios ou expressamente autorizados. Não faça bypass de proteção, licença ou análise ativa de amostras suspeitas fora de sandbox autorizado.

## 1. Caso concreto e competência

Um executável didático tem a string `ERROR_PAYMENT`, mas ela pertence a uma função `unused` que não é chamada por `entry`. A análise sem grafo diria que o erro necessariamente ocorre em toda execução. Isso confunde presença da string com evidência de reachability ou execução.

**Ao concluir, o estudante demonstra:** Localizar referências cruzadas, recuperar um caminho de chamadas e diferenciar texto/import presente de código efetivamente alcançável. É preciso prever, reproduzir, comparar contraexemplo e expressar a limitação, não apenas citar uma ferramenta.

## 2. Vocabulário antes do experimento

1. **String** é sequência de bytes interpretada como texto e pode residir em dados ou código; presença não garante uso.

2. **Xref** é referência de um endereço a outro identificada estaticamente ou dinamicamente; pode ser incerta em código indireto.

3. **Import** identifica dependência/símbolo referenciado no binário; existência de import não garante chamada em todos os caminhos.

## 3. Mecanismo causal e exemplo resolvido

`findReferences(graph,target,entry)` percorre um grafo sintético de chamadas pela largura. Para `entry→parse→logError`, retorna caminho de referência; para `unused`, `reachable=false`. Mesmo 'reachable' no grafo estático significa que existe caminho potencial no modelo, **não que ocorreu na execução**; branches, valores de input, function pointers e otimizações limitam inferências. O resultado deve ser comparado a trace de binário próprio antes de afirmar evento.

**Não confundir direção de arestas:** Xrefs-to responde quem referencia o símbolo; Xrefs-from aponta referências feitas por um local. O teste de grafo adota direção caller→callee.

### Recorte executável do modelo

```js
// O módulo está em public/course-labs/a111-120/models.mjs
findReferences({entry:['parse'],parse:['logError'],unused:[]},'logError','entry'); // path ['entry','parse','logError']
```

**O que conta como evidência:** string alvo, referência de origem/destino, caminho potencial, condições de execução e teste dinâmico separado.

**Armadilha que deve ser evitada:** Tratar presença de string, import ou Xref como prova de que operação ocorreu.

**Materiais:** [modelos de operações](/course-labs/a111-120/models.mjs) e [10 testes Node isolados](/course-labs/a111-120/lab.test.mjs). O projeto não requer Ghidra, x64dbg, Windows, IDE ou execução de binários nativos para passar nesta prática.


**Caso positivo:** Uma função referenciada por cadeia de chamadas potencial é descrita como alcançável no grafo simplificado.

**Caso negativo:** Uma string presente somente em função `unused` não é classificada como alcançável a partir de entry.

### Passo a passo com checkpoints

1. Diferencie xref de string e call graph desenhando nós entry, parse, logError, unused.
2. Rode a busca para logError e unused; explique diferença de resultado.
3. Crie cenário com branch sempre falso e mostre por que call graph estático ainda não comprova execução.

**Troubleshooting:** Se o teste falhar, confirme versão de Node, entrada e significado do estado capturado. Uma divergência deve produzir novo caso de teste/revisão do modelo, não a remoção da asserção. Resultados sintéticos não são evidência de execução em CPU real.

## 5. Investigação, correção e regressão

Defina entrada e saída observável antes de modificar algoritmo, source ou interpretação de listing. Documente endereço/estado quando houver debug de programa próprio; repita o mesmo teste que demonstrou a falha e inclua um caminho legítimo semelhante para evitar correção excessiva.

**Critério de correção:** a hipótese incompatível é identificada ou rejeitada e a operação legítima continua produzindo o efeito previsto. Esta fixture comprova somente a regra simulada. Em ambiente nativo, símbolos, otimizações, binário, arquitetura, ABI e estado do processo exigem revisão própria.

## 6. Prova final independente — caso de transferência

Um binário educacional inclui import `WriteFile` e uma string `backup_done`, mas o fluxo normal chama somente `parseFile` e `reportStatus`. A função `saveBackup` possui a única referência a WriteFile e não há caminho de call de entry até ela no modelo.

**Responda sem consultar o gabarito:**

1. O que a import WriteFile comprova?
2. Por que a string backup_done é apenas uma pista?
3. Como buscar xrefs para localizar a função que as utiliza?
4. Que conclusão permite um grafo sem caminho de entry até saveBackup?
5. Qual limitação existe quando há chamadas indiretas ou carregamento dinâmico?
6. Qual teste no programa próprio confirmaria gravação de arquivo sem assumir apenas pela string?
