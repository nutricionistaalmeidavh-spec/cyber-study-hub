## 2. Visão geral

Same-Origin Policy restringe interações entre origens; CORS é o mecanismo controlado para relaxar parte dessas restrições.

## 3. Aprofundamento: o que realmente está acontecendo

Same-Origin Policy é uma regra do navegador. CORS é uma forma controlada de relaxar leitura cross-origin. Nenhum dos dois substitui autenticação/autorização server-side.

## 5. Conceitos fundamentais

### 1. Origin
Combinação de esquema, host e porta.
### 2. Preflight
Requisição OPTIONS usada para verificar permissões CORS.
### 3. Access-Control-Allow-Origin
Header que declara origens permitidas.
### 4. Credentials
Cookies/autenticação que exigem política CORS mais cuidadosa.

## 6. Fluxo técnico

1. **Página possui uma origin**
2. **JavaScript tenta acessar outra origin**
3. **Navegador aplica SOP**
4. **Servidor pode responder com política CORS**
5. **Browser decide se expõe a resposta ao script**

### Checkpoint 1

Descreva o fluxo acima sem usar o nome da técnica. Onde está a primeira decisão de segurança?

## 7. Exemplo técnico — Allowlist CORS explícita

```ts
const origins = new Set(["https://app.exemplo.com"]);

function corsOrigin(origin?: string) {
  if (!origin) return false;
  if (!origins.has(origin)) throw new Error("Origin não permitida");
  return origin;
}
```

### Como ler o exemplo

Evite refletir qualquer Origin automaticamente, especialmente com credenciais.

## 8. Por que a vulnerabilidade/mecanismo acontece

Same-Origin Policy é a regra do navegador; CORS é um mecanismo controlado pelo servidor para relaxar parte dessa regra. CORS não substitui autenticação nem autorização.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 9. Laboratório guiado — Comparar same-origin e cross-origin

**Modo:** PC

1. Suba duas aplicações locais em portas diferentes.
2. Faça uma requisição fetch entre elas.
3. Observe o erro do navegador sem CORS.
4. Adicione allowlist para uma origem específica.
5. Confira headers de preflight e resposta.

## 10. Como detectar

Audite respostas CORS, origens refletidas e combinações de ACAO/credentials inseguras.

Transforme a frase acima em telemetria:

```text

```

## 11. Como corrigir / reduzir risco

Use allowlist explícita, não reflita Origin indiscriminadamente e evite credenciais com políticas amplas.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 13. Erros comuns de raciocínio

- Confundir indicador com confirmação.
- Concluir vulnerabilidade pelo nome da ferramenta.
- Aplicar hardening sem testar impacto operacional.
- Não diferenciar prevenção de detecção.
- Fazer correção e esquecer o reteste.
