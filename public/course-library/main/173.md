## 2. Objetivo e mecanismo causal

Sanitizers acrescentam verificações ao código compilado e precisam também do runtime na linkedição. ASan detecta acessos a regiões marcadas como inválidas, incluindo redzones e objetos liberados. UBSan verifica categorias de comportamento indefinido, como overflow de int com sinal. Uma execução sem alerta só cobre os caminhos que ela percorreu; memória dentro de uma mesma alocação pode continuar fora do contrato lógico sem cruzar uma redzone.

## 4. Exemplo resolvido — estado, decisão e efeito

lab.c/signed calcula INT_MAX+1: UBSan relata signed integer overflow. O mesmo mecanismo não explica uaf: em lab.c, malloc(4) cria objeto, free encerra seu lifetime, alias[0] lê após a liberação e ASan mostra heap-use-after-free. Para overflow8.bin, o ASan mostra WRITE de 1 byte no fim de name; a alocação é stack, não heap. Separar classe e tamanho do acesso evita chamar todos os três de “buffer overflow”.

## 7. Código comentado e artefatos

```c
// flags devem participar da compilação E da linkedição
// cc -g -O0 -fsanitize=address -fno-omit-frame-pointer lab.c -o lab

p[0] = 42;
unsigned char *alias = p;
```

## 8. Laboratório executável

Ambiente-base: Linux x86-64, Python 3.11+, compilador C11 GCC e binutils. Use cópia local; os programas são próprios e não acessam rede. Na raiz do pacote cumulativo:

```bash
cd public/course-labs/phase16-memory
python3 run.py build
python3 run.py types
python3 run.py heap
python3 run.py parser
```

O build fornece `make_fixtures.py`, arquivos em `fixtures/`, hashes em `fixtures/manifest.json` e executáveis em `build/`. Uma falha de geração ou compilação interrompe o runner. Ele verifica saídas reais, tem timeout e desativa core dumps. Os crashes deliberados ficam restritos aos processos de laboratório.

**Resultado esperado e checkpoints:** Três diagnósticos distintos em build/logs/signed.txt, uaf.txt e v1-overflow8.txt. Cada um exige retorno diferente de zero e texto específico. heap-fixed salva 42 antes de free e encerra com saída 0; parser-v2 rejeita a fronteira inválida com saída 2.

Compare previsão e observação antes de avançar. Quando a atividade usa `run.py`, abra os logs em `build/logs/` e o JSON `build/results-<grupo>.json`: retorno do programa vulnerável e retorno do runner são coisas diferentes. A análise Python imprime JSON calculado sobre as fixtures disponíveis.

## 10. Defesa e reteste

O modo `signed-fixed` recebe o mesmo `a=INT_MAX` e rejeita adicionar1 antes de executar a soma: `if (a > INT_MAX - 1)` retorna2. O modo `signed-valid` usa `a=INT_MAX-1`, passa pela mesma guarda e calcula INT_MAX com saída0. Ambos usam UBSan. `run.py types` exige a rejeição específica e `accepted at_limit=1`; isso retesta o mesmo contrato aritmético, além do exemplo separado de conversão250+10. A guarda é específica para adicionar1 a um int, não uma API geral de soma.

Corrija a operação e o ownership: use resultado largo, consuma objeto vivo, valide comprimento antes da escrita. Recompile e linke com as mesmas opções de instrumentação. Use versões ASan e UBSan no processo de teste; preserve builds sem instrumentação para medir desempenho, sem confundir esses resultados.

## 11. Troubleshooting específico

“undefined reference to __asan_*” indica falta de sanitizer no link. Frames sem nomes podem resultar de ausência do simbolizador; o log ainda contém arquivo/linha no GCC deste ensaio. ASan detect_leaks=0 aqui limita o exercício a acessos; não houve validação de leaks.

## 14. Quiz

### 1. Quem detecta INT_MAX+1 neste lab?
A. Stack canary
B. RELRO
C. UBSan
D. NX

**Resposta:** C. UBSan instrumenta a operação aritmética com sinal.

### 2. Um teste ASan sem alerta prova memória segura?
A. Não; depende de caminhos executados e limites observáveis
B. Sim, se -g estiver ativo
C. Sim, para heap
D. Somente com saída 0

**Resposta:** A. Instrumentação não substitui cobertura e contratos funcionais.

### 3. Erro __asan_* no link pede o quê?
A. Remover includes
B. Usar -O3
C. Alterar o input
D. Linkar com a opção/runtime do sanitizer

**Resposta:** D. Os acessos instrumentados dependem das funções do runtime.

### 1. Caso de aprendizagem

Um log relata AddressSanitizer: heap-use-after-free; outro, runtime error: signed integer overflow.

### 2. Mecanismo específico

ASan identifica erros de memória selecionados (temporal e espacial); UBSan reporta categorias de comportamento indefinido. Alertas classificam sintomas, não explorabilidade. Traço limpo não prova ausência de falhas em caminhos não exercitados. O laboratório C nativo de memória continua disponível como opção em Linux/GCC.

- **Controle legítimo:** heap-use-after-free → TEMPORAL_MEMORY.
- **Contraprova:** signed integer overflow → UNDEFINED_BEHAVIOR; exit code 0 → NO_REPORT_IN_TRACE.
- **Defesa:** corrigir a condição causal, rejeitar entrada inválida e preservar o caso legítimo.
