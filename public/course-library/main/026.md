# Aula 026 — Memória: Stack, Heap e Buffer Overflow

**Trilha:** Redes, Sistemas e Engenharia Reversa · **Profundidade:** Intermediário · **Duração sugerida:** 45–65 minutos.  
**Objetivo observável:** Distinguir durações/locais de armazenamento e verificar limites de buffer com casos seguros e controlados.

> Práticas defensivas somente em `localhost`, fixtures locais e executáveis próprios; não usar terceiros, malware real nem redes industriais. Os laboratórios não modificam configurações do host.

## Problema real e por que aprender

Um programa copia uma string para buffer de 8 bytes. Um desenvolvedor usa `<= sizeof(buf)` no laço e acredita que está seguro. Você precisa identificar o acesso fora do limite sem criar payload ofensivo.

**Antes de começar:** Noções de ponteiro, array, função, sizeof e compilação C; não requer exploração de vulnerabilidades.

**O que você entregará:** previsão escrita antes do experimento; evidência observada; hipótese alternativa; decisão defensiva testável e resposta ao cenário inédito. Não é preciso instalação paga.

## Fundamentos: o vocabulário necessário

- **stack:** Região gerenciada pelo runtime/ABI para chamadas e objetos automáticos, sem prometer um layout universal.
- **heap:** Região administrada por alocador dinâmico com malloc/free; tempo de vida controlado.
- **limite válido:** Array de 8 elementos oferece índices de 0 a 7, não 0 a 8.
- **overflow:** Acesso além de limites de objeto; pode causar comportamento indefinido e corrupção.
- **AddressSanitizer:** Instrumentação para detectar classes de acesso inválido no programa de teste; cobertura e disponibilidade variam.

## Mecanismo técnico passo a passo

Uma cópia segura precisa conhecer a capacidade de destino, a quantidade de bytes recebidos e se será incluído byte NUL. Validar apenas comprimento de caracteres é inadequado quando protocolo envia bytes. `sizeof` de array em escopo de declaração mede capacidade; após decair para ponteiro, sizeof mede o ponteiro. Acessos fora de objeto são comportamento indefinido mesmo quando parecem funcionar.

A pergunta para testar entendimento é **qual componente decide o resultado, com qual dado e qual limite de confiança?** Registre pelo menos uma suposição que pode estar errada.

## Exemplo resolvido: do dado à conclusão

Para char buf[8], entrada de 7 letras ASCII ocupa 7 bytes + terminador NUL (8 total) e cabe; entrada de 8 letras precisaria 9 bytes com NUL e deve ser recusada para esta API de string. O laboratório recebe comprimentos 0, 7 e 8 e marca OK, OK, REJECT antes de copiar.

**Como raciocinar:** (1) defina estado inicial e entradas; (2) antecipe o resultado observável; (3) execute/inspecione somente o objeto autorizado; (4) compare saída com previsão; (5) se divergir, investigue antes de trocar a regra. A conclusão deve ser tão restrita quanto os dados que a sustentam.

## Contraexemplo: a conclusão fácil está errada

Stack versus heap não determina automaticamente se overflow é explorável. ASan é ferramenta de diagnóstico, não defesa de produção; proteções do sistema não substituem validação de fronteira. Para dados binários, `strlen` pode falhar por zero embutido.

**Exercício parcialmente guiado.** Primeiro marque qual afirmação no contraexemplo excede a evidência. Depois formule uma hipótese alternativa e indique **que medição a diferenciaria**. A primeira etapa é trabalhada na explicação acima; escreva você mesmo a evidência discriminante.

## Laboratório reproduzível e seguro

Compile `cc -std=c11 -Wall -Wextra -fsanitize=address,undefined -o /tmp/csh_bounds public/course-labs/a-021-030/bounds.c` e execute. Sem suporte a sanitizers, compile sem as flags e justifique perda de cobertura. O exemplo não contém cópia fora de limite nem demonstra exploração.

### Resultado esperado e hipótese de falha

- **Caso positivo:** Entradas com até 7 bytes terminam com NUL, comprimento 8 é recusado antes da gravação.
- **Caso negativo/limite:** Nenhum teste exige corromper memória; `strlen` sobre bytes arbitrários não é usado como prova de comprimento.
- **Evidência mínima:** comando ou arquivo, data, versão/ambiente, entrada, saída, interpretação e limitação. Registre o resultado **real**; não marque sucesso se não conseguiu executar.
- **Recuperação:** se a ferramenta opcional faltar, use o fixture descrito, documente o bloqueio e não confunda leitura do exemplo com execução real.

## Defesa, detecção e reteste

**Controle defensivo:** Verificar limites no limite da confiança, preferir APIs com capacidade explícita e testes de fronteira; habilitar instrumentação e fuzzing em software próprio durante QA.

**Detecção/investigação:** Registrar input-length, capacidade, resultado da verificação e backtrace quando seguro; não tratar crash isolado como prova suficiente de exploração.

**Reteste:** repita o caso legítimo, o caso inválido/limite e um caso novo que não aparecia no exemplo. Informe qual comportamento deve continuar funcionando para não "corrigir" o problema bloqueando usuários legítimos.
