## 6. Exemplo técnico — Exemplo original, agora lido como evidência

```javascript
function escaparHTML(s) {
      return s.replace(/[&<>"']/g, c => MAP[c]);
    }
    res.send(`<p>${escaparHTML(nome)}</p>`);
```

O código não é um fim: identifique entrada, decisão, estado e efeito observável.

### Equivalente didático em Portugol

```text
nomeSeguro <- escaparHTML(nome)
    escreva("<p>" + nomeSeguro + "</p>")
```

Use o Portugol para enxergar a lógica; APIs reais de rede, banco, criptografia e SO continuam sendo estudadas na tecnologia correspondente.

## 9. Como defender / corrigir

Use output encoding por contexto, APIs seguras do DOM e sanitização quando HTML controlado for realmente necessário.

A correção deve agir sobre a causa. Evite controles cosméticos como esconder IDs, renomear rotas, desativar mensagens sem corrigir a decisão ou confiar somente no frontend.

## 14. Aprofundamento específico — XSS: da entrada não confiável ao sink do DOM

### Problema concreto e objetivo demonstrável

Um portal de suporte recebe o nome de exibição `<b>Equipe</b>`. Na tela de comentários, um desenvolvedor atribui esse texto ao `innerHTML`; o navegador passa a interpretar a entrada como marcação. Se outra entrada produzir instruções executáveis, a fronteira de confiança é atravessada. A pergunta certa não é “o texto tinha uma palavra suspeita?”, e sim “em qual contexto o dado foi interpretado?”.

**Ao concluir, você deve ser capaz de:** localizar a decisão no sistema; prever comportamento permitido e negado; reproduzir o exemplo em ambiente isolado; explicar o motivo do resultado; propor correção e retestar sem bloquear o caso legítimo.

### Mecanismo, conceitos e limites

XSS pode envolver dado refletido na resposta, armazenado e exibido depois, ou recebido/transformado pelo próprio JavaScript do navegador. A cadeia é **source** (URL, comentário, API) → transformações → **sink** (`innerHTML`, interpretação de HTML etc.). Em contexto de **texto HTML**, a defesa preferida é usar `textContent`/APIs seguras: o navegador trata a entrada como texto literal. Ao gerar HTML por string, faça encoding para aquele contexto, como converter `&`, `<`, `>`, aspas quando pertinente. Para atributos, URL, CSS e JavaScript, as regras são outras; **escapar HTML indiscriminadamente não é solução universal**. `HttpOnly`, CSP e sanitização apropriada são camadas distintas e não substituem escolha de sink seguro.

### Exemplo resolvido (com raciocínio e evidência)

O comentário fictício `<b class="x">O'Hara & equipe</b>` deve aparecer como **texto**, com sinais angulares visíveis, e não como título em negrito. Para interpolação em corpo HTML, a versão codificada é `&lt;b class=&quot;x&quot;&gt;O&#39;Hara &amp; equipe&lt;/b&gt;`.

```js
// Browser, elemento <p id="comentario"></p> criado no HTML estático
const recebido = new URLSearchParams(location.search).get('nome') ?? '';
document.getElementById('comentario').textContent = recebido;
// Evitar: element.innerHTML = recebido
```

O script de laboratório Node verifica a codificação, mas **não abre um navegador**. Para comprovar visualmente, crie uma página HTML em arquivo local com o trecho acima, abra em seu navegador e compare texto literal com marcação **benigna** somente. Não use dados de terceiros e não execute payloads maliciosos.

### Casos positivos, negativos e critérios de resultado

A entrada `<b>olá</b>` não deve criar `<b>` quando texto é esperado. O texto `O'Hara & equipe` deve permanecer intacto semanticamente após exibição. Encoding HTML de texto não garante segurança dentro de `href=`, código JS inline ou CSS; exige contexto próprio. Frameworks escapam por padrão em templates comuns, mas APIs explícitas de HTML bruto precisam de regras especiais.

## 16. Defesa, evidências e reteste

Prefira texto literal e APIs DOM apropriadas, faça encoding contextual ao gerar HTML e evite sinks perigosos com conteúdo não confiável. Se a aplicação realmente permite HTML do usuário, empregue sanitizador mantido e restrições de tags/atributos/URLs, com testes negativos. Use CSP como proteção em profundidade e revisite caminhos de URL, API e armazenamento. Reteste funcionalidade legítima: comentários que contêm `<` não devem desaparecer ou quebrar layout.

Produza um relatório curto com quatro partes: (a) hipótese e escopo; (b) entrada e estado inicial; (c) saída observada, comparada à esperada; (d) melhoria e repetição dos casos positivo e negativo. Não inclua tokens, senhas, dados pessoais ou URLs de sistemas alheios.
