# Aula 038 — SAST, DAST, SCA e Secret Scanning

**Trilha principal:** Pentest & Secure Development · **Duração sugerida:** 50–65 min · **Estado:** aprofundamento editorial A (IA) sujeito a registro SHA-256.  
**Ambiente:** Node.js 22+, sem Docker obrigatório, sem assinatura ou API paga. Testes só com dados fictícios, em memória ou serviço `127.0.0.1` criado pela suíte.

> Só execute técnicas ativas em ativos próprios ou autorizados explicitamente. O resultado de uma fixture local não se transfere automaticamente para sistemas externos. As atividades não requerem credenciais reais.

## Problema e objetivo mensurável

Um projeto local contém um arquivo de dependências, código de servidor e uma resposta HTTP fictícia. A análise estática encontra um caminho de entrada para SQL não parametrizado; a SCA identifica dependência em lockfile; um DAST vê HTTP; a revisão de segredos examina somente um marcador `dummy-secret`, nunca credencial verdadeira.

**Competência observável:** Escolher a ferramenta correta para cada classe de evidência e aplicar política de segredos sem expô-los. Para demonstrá-la, o estudante deve prever a decisão, executar os casos positivos e negativos e explicar evidências, hipóteses alternativas e limites da simulação. Não basta nomear ferramentas.

## Fundamentos e pré-requisitos recomendados

Os pré-requisitos são recomendações, nunca bloqueio da aula: HTTP básico, diferença entre autenticação/autorização, lógica booleana e leitura de logs. Onde necessário, use o vocabulário abaixo antes de abrir o terminal.

1. **Conceito 1.** SAST: análise de código ou fluxo de dados sem precisar rodar a aplicação.

2. **Conceito 2.** DAST: teste da aplicação em execução dentro do escopo permitido.

3. **Conceito 3.** SCA: inventário de bibliotecas/dependências confrontado com informações de vulnerabilidade; advisory depende de versão e contexto.

4. **Conceito 4.** Secret scanning: detecção de padrões ou entropia de credenciais, com falsos positivos possíveis.

## Mecanismo técnico: entrada, fronteira, controle e resultado

O tipo de fonte importa: lockfile/dependency → SCA; code/tainted-sink → SAST; http/response → DAST; code/dummy-secret → SECRET. Não confunda 'encontrou versão' com 'é explorável'. `npm audit` pode requerer consulta a um registro externo; o núcleo desta aula usa só fixtures locais sem essa dependência. Se um segredo verdadeiro for descoberto em outro contexto, a remediação inclui revogação/rotação, histórico, logs e alcance, não somente apagar a linha.

**Modelo de decisão:** estado inicial → entrada controlada → componente que decide → efeito observável → comparação com a política. Sempre diga onde mora a autoridade: aplicativo, navegador, banco, armazenamento ou processo de entrega. O nome de uma ferramenta não responde essa pergunta.

### Exemplo resolvido e comentado

```js
import { categorizeScanner } from './models.mjs';
for (const item of [{source:'lockfile',kind:'dependency'},{source:'code',kind:'tainted-sink'},{source:'http',kind:'response'}]) {
 console.log(categorizeScanner(item));
} // SCA, SAST, DAST
```

> Este trecho é um recorte da fixture da aula; execute o teste completo pelo comando abaixo, a partir da raiz do projeto. A sintaxe de import acima representa o módulo do diretório de laboratório, e não uma dependência publicada.

**Evidência esperada:** Saídas SCA, SAST, DAST e SECRET para fontes distintas; nenhuma conexão com banco de advisories de terceiros.

**Requisitos:** Node.js 22 ou superior, terminal local e repositório. O código e os testes estão em `/course-labs/a031-040/models.mjs` e `/course-labs/a031-040/lab.test.mjs`. **O que deve aparecer:** Saídas SCA, SAST, DAST e SECRET para fontes distintas; nenhuma conexão com banco de advisories de terceiros. A suíte pode reportar também testes das outras nove aulas, mas cada assert está identificado pelo ID desta aula.

### Quando algo não funciona

Sem lista de advisories atualizada, SCA local classifica natureza da verificação mas não atesta vulnerabilidades correntes. Um DAST que devolve 403 pode significar proteção correta.

Para recuperar: confira a versão `node --version`, inicie no diretório raiz, execute novamente uma única vez após corrigir a causa e compare os resultados; não modifique expectativas só para tornar os testes verdes.

## Detecção, prevenção e reteste

**Evidência a observar:** Centralize achado com fingerprint, versão, alcance, ambiente, resultado de triagem e owner; evite logar segredos.

**Medida corretiva:** Aplique tipos complementares de scanner e revisão humana. Achado crítico comprovado deve bloquear release; exceção exige governança explícita.

**Critério de reteste:** o caminho originalmente indevido deve ser negado sob as mesmas pré-condições, enquanto o caminho legítimo continua funcionando. Documente casos não cobertos. Um caso rejeitado não é automaticamente prova de que todas as variações estão seguras.

## Prova final independente — competência aplicada

**Novo cenário, distinto da fixture:** CI apresenta um valor parecido com chave em fixture de testes, uma dependência com alerta de versão e uma rota de login que retorna 401. O gerente quer classificar os três como incidentes.

Responda *sem abrir o gabarito*, incluindo resultado previsto e ao menos uma limitação:

1. Qual método gerou cada sinal e que evidência adicional ele fornece?
2. Qual deles exige revogação imediata somente se confirmado como credencial real?
3. Por que 401 não prova falha de autenticação?
4. Como investigar a dependência sem declarar exploitabilidade somente por versão?
5. Que controles evitam expor tokens no PR e logs?
6. Que lacuna resta após scanners verdes e que teste manual seria justificável no escopo?

Após concluir, compare seu relatório com o [gabarito independente e rubrica](/course-labs/a031-040/answer-keys/AULA-038.md). A publicação do gabarito não substitui a tentativa independente.
