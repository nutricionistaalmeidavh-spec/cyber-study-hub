## 2. Visão geral

Falhas DOM surgem quando código cliente move dados não confiáveis de fontes para sinks perigosos sem validação ou encoding adequado.

## 3. Aprofundamento: o que realmente está acontecendo

Vulnerabilidades DOM-based podem existir inteiramente no navegador: a resposta do servidor pode ser estática, mas JavaScript lê uma source controlável e entrega o valor a um sink que interpreta HTML, script ou URL.

Vulnerabilidades DOM-based acontecem no navegador quando uma fonte controlável chega a um sink perigoso. A resposta do servidor pode estar correta e, ainda assim, o JavaScript do cliente criar o problema.

Ao estudar, tente sempre localizar cinco elementos:

```text
entrada/estado
→ componente que interpreta
→ decisão
→ efeito observável
→ controle que quebra a cadeia
```

## 5. Conceitos fundamentais

### 1. Source
Origem de dados, como location, postMessage ou storage.
### 2. Sink
API que interpreta dados de forma perigosa, como innerHTML.
### 3. Taint flow
Caminho do dado não confiável até um sink.
### 4. postMessage
Canal entre janelas que exige validação de origin e payload.

## 6. Fluxo técnico

1. **Fonte: URL, hash, postMessage ou storage**
2. **JavaScript lê o valor**
3. **O valor percorre transformações**
4. **Sink altera DOM, URL ou código**
5. **API segura ou sanitização interrompe o fluxo**

### Checkpoint 1

Descreva o fluxo acima sem usar o nome da técnica. Onde está a primeira decisão de segurança?

## 7. Exemplo técnico — textContent em vez de innerHTML

```js
const params = new URLSearchParams(location.search);
const name = params.get("name") ?? "";

const output = document.querySelector("#welcome");
if (output) {
  output.textContent = `Olá, ${name}`;
}
```

### Como ler o exemplo

Quando a intenção é exibir texto, textContent evita interpretar marcação HTML.

Ao revisar cada linha/bloco, marque:

- o dado de entrada;
- o estado confiável usado na decisão;
- a condição de rejeição;
- o efeito/log que você esperaria observar.

## 8. Por que a vulnerabilidade/mecanismo acontece

Vulnerabilidades DOM-based acontecem no navegador quando uma fonte controlável chega a um sink perigoso. A resposta do servidor pode estar correta e, ainda assim, o JavaScript do cliente criar o problema.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 9. Laboratório guiado — Rastrear fonte → transformação → sink

**Modo:** Celular + PC

1. No celular, identifique exemplos de source e sink.
2. No PC, crie uma página local que leia um parâmetro da URL.
3. Renderize primeiro com textContent.
4. Use DevTools para acompanhar o valor no código.
5. Liste quais sinks do projeto merecem revisão: innerHTML, insertAdjacentHTML, eval e URLs dinâmicas.

### Resultado esperado

Você deve conseguir desenhar o caminho de um dado controlável até o DOM e escolher uma API mais segura.

### Checkpoint 2 — antes da correção

Qual evidência mínima demonstra a condição estudada sem ampliar impacto desnecessariamente?

### Checkpoint 3 — depois da correção

Repita o mesmo teste e registre a diferença. Se o cenário mudou, o reteste não é comparável.

## 10. Como detectar

Use análise estática/dinâmica do fluxo source→sink e monitore erros/DOM mutations inesperadas.

Transforme a frase acima em telemetria:

```text
quem?
onde?
qual ação?
qual recurso/destino?
qual resultado?
qual sequência temporal?
```

## 11. Como corrigir / reduzir risco

Prefira APIs seguras como textContent, valide origin em postMessage e aplique sanitização contextual.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 12. Troubleshooting

- Confirme versões, portas, identidade e estado inicial do laboratório.
- Colete baseline antes de mudar configuração.
- Se uma ferramenta “não encontrar”, verifique cobertura e fonte de dados antes de concluir ausência de risco.
- Se um finding aparecer, leia a evidência e a pré-condição antes de classificá-lo.
- Mantenha laboratório isolado e restaure snapshot quando a aula pedir mudança de configuração.

## 13. Erros comuns de raciocínio

- Confundir indicador com confirmação.
- Concluir vulnerabilidade pelo nome da ferramenta.
- Aplicar hardening sem testar impacto operacional.
- Não diferenciar prevenção de detecção.
- Fazer correção e esquecer o reteste.

## 15. Quiz
