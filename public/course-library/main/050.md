## 2. Visão geral

Falhas DOM surgem quando código cliente move dados não confiáveis de fontes para sinks perigosos sem validação ou encoding adequado.

## 3. Aprofundamento: o que realmente está acontecendo

Vulnerabilidades DOM-based podem existir inteiramente no navegador: a resposta do servidor pode ser estática, mas JavaScript lê uma source controlável e entrega o valor a um sink que interpreta HTML, script ou URL.

Vulnerabilidades DOM-based acontecem no navegador quando uma fonte controlável chega a um sink perigoso. A resposta do servidor pode estar correta e, ainda assim, o JavaScript do cliente criar o problema.

Ao estudar, tente sempre localizar cinco elementos:

```text
entrada/estado
→ componente que interpreta
→ decisão
→ efeito observável
→ controle que quebra a cadeia
```

## 5. Conceitos fundamentais

### 1. Source
Origem de dados, como location, postMessage ou storage.
### 2. Sink
API que interpreta dados de forma perigosa, como innerHTML.
### 3. Taint flow
Caminho do dado não confiável até um sink.
### 4. postMessage
Canal entre janelas que exige validação de origin e payload.

## 6. Fluxo técnico

1. **Fonte: URL, hash, postMessage ou storage**
2. **JavaScript lê o valor**
3. **O valor percorre transformações**
4. **Sink altera DOM, URL ou código**
5. **API segura ou sanitização interrompe o fluxo**

## 7. Exemplo técnico — textContent em vez de innerHTML

```js
const params = new URLSearchParams(location.search);
const name = params.get("name") ?? "";

const output = document.querySelector("#welcome");
if (output) {
  output.textContent = `Olá, ${name}`;
}
```

### Como ler o exemplo

Quando a intenção é exibir texto, textContent evita interpretar marcação HTML.

Ao revisar cada linha/bloco, marque:

- o dado de entrada;
- o estado confiável usado na decisão;
- a condição de rejeição;
- o efeito/log que você esperaria observar.

## 8. Por que a vulnerabilidade/mecanismo acontece

Vulnerabilidades DOM-based acontecem no navegador quando uma fonte controlável chega a um sink perigoso. A resposta do servidor pode estar correta e, ainda assim, o JavaScript do cliente criar o problema.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 10. Como detectar

Use análise estática/dinâmica do fluxo source→sink e monitore erros/DOM mutations inesperadas.

Transforme a frase acima em telemetria:

```text
quem?
onde?
qual ação?
qual recurso/destino?
qual resultado?
qual sequência temporal?
```

## 11. Como corrigir / reduzir risco

Prefira APIs seguras como textContent, valide origin em postMessage e aplique sanitização contextual.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## Problema e competência verificável — AULA-050 (oficina A)

**Caso inédito:** Uma página recebe '<img src=x>' em fragmento de URL e uma mensagem postMessage de outra origem tentando alterar um aviso visual.

**Decisão crítica:** fluxo source→sink importa: texto deve ir a textContent e mensagens requerem validação exata de origem e formato.

**Hipótese que precisa ser refutada:** texto HTML permanece literal; postMessage de outra origem é rejeitado.

**Evidência esperada:** safeDomText('<img src=x>') retorna sink=textContent; origem externa falha.

**Competência:** explicar a causa, prever observáveis, executar teste com entrada legítima e adversarial, selecionar a defesa e declarar os limites do teste.

### Mecanismo e exemplo resolvido

1. **Estado inicial:** Uma página recebe '<img src=x>' em fragmento de URL e uma mensagem postMessage de outra origem tentando alterar um aviso visual.
2. **Entrada e fronteira:** fluxo source→sink importa: texto deve ir a textContent e mensagens requerem validação exata de origem e formato.
3. **Decisão:** Selecionar APIs DOM por contexto (textContent), validar origin/payload e sanitizar apenas quando HTML explícito for requisito.
4. **Observação:** safeDomText('<img src=x>') retorna sink=textContent; origem externa falha.
5. **Interpretação:** texto HTML permanece literal; postMessage de outra origem é rejeitado. Não confunda a evidência de um modelo isolado com exploração ou comprovação em produto de terceiros.

### Laboratório guiado (offline, código disponível)

Pré-requisito: Node.js 22 ou superior. Sem contas, API comercial ou rede. A execução é isolada e determinística.


**Checkpoint 1 (prever):** Antes de rodar, escreva o que ocorrerá com a entrada legítima e a adversarial no caso 050.

**Checkpoint 2 (observar):** Na saída JSON procure `normal` (controle positivo) e `hostile` (controle negativo); compare os campos e diga qual condição bloqueou ou isolou o risco.

**Checkpoint 3 (corrigir e retestar):** Selecionar APIs DOM por contexto (textContent), validar origin/payload e sanitizar apenas quando HTML explícito for requisito. Reexecute e registre também o caso legítimo para evitar uma "correção" que só desliga a função.

**Troubleshooting:** Se o Node não reconhecer módulos ESM, confirme `node --version` (22+), execute o comando na raiz do repositório e preserve a extensão `.mjs`. Se `hostile` não for um erro, explique o isolamento de dados ou a invariância positiva esperada neste caso.

### Detecção, defesa, limites e fontes

- **O que procurar:** texto HTML permanece literal; postMessage de outra origem é rejeitado.
- **Controle primário:** Selecionar APIs DOM por contexto (textContent), validar origin/payload e sanitizar apenas quando HTML explícito for requisito.
- **Controle de compatibilidade:** safeDomText('<img src=x>') retorna sink=textContent; origem externa falha.
- **Limitação honesta da evidência:** Modelo Node não executa DOM real, CSP ou event handlers; precisa de teste de navegador para afirmações de UI.
- **Referência técnica para leitura crítica:** https://portswigger.net/web-security/cross-site-scripting/dom-based
