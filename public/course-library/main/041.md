## 2. O problema em uma frase

SSTI acontece quando entrada não confiável influencia o template que o servidor interpreta. O risco não é “usar template engine”, mas permitir que dados controláveis atravessem a fronteira entre dado e expressão de template.

## 3. O que você precisa dominar

- **2.** Passe entrada do usuário como dados, não como código/template.
- **3.** Erros de renderização e avaliação inesperada são sinais importantes.

## 5. Por que isso importa

SSTI acontece quando entrada não confiável influencia o template que o servidor interpreta. O risco não é “usar template engine”, mas permitir que dados controláveis atravessem a fronteira entre dado e expressão de template.

Na prática, segurança não depende de decorar o nome da técnica. Ela depende de localizar a fronteira de confiança, identificar o dado ou estado que muda a decisão e provar, com evidência mínima, se o controle impede o comportamento indesejado.

Os pontos-chave desta aula devem ser usados como perguntas de revisão:

- Mantenha templates sob controle da aplicação.
- Passe entrada do usuário como dados, não como código/template.
- Erros de renderização e avaliação inesperada são sinais importantes.

## 6. Exemplo técnico — Exemplo original, agora lido como evidência

```javascript/pseudocódigo
const html = template.render({ name: userInput });
// template fixo; userInput entra como dado
```

O código não é um fim: identifique entrada, decisão, estado e efeito observável.

### Equivalente didático em Portugol

```text
template <- carregarTemplateFixo()
html <- renderizar(template, nomeUsuario)
responder(html)
```

Use o Portugol para enxergar a lógica; APIs reais de rede, banco, criptografia e SO continuam sendo estudadas na tecnologia correspondente.

## 9. Como defender / corrigir

Nunca trate entrada do usuário como template executável; mantenha templates sob controle da aplicação e dados como dados.

A correção deve agir sobre a causa. Evite controles cosméticos como esconder IDs, renomear rotas, desativar mensagens sem corrigir a decisão ou confiar somente no frontend.

## 10. Como detectar / investigar

Procure erros da engine, expressões avaliadas inesperadamente e rotas onde entrada controla o template em vez de apenas valores.

Uma detecção útil combina:

```text
identidade/host
+ ação
+ recurso/destino
+ horário
+ resultado
+ contexto
```

## Problema e competência verificável — AULA-041 (oficina A)

**Caso inédito:** Um portal usa a mesma saudação para Ana e para uma entrada '{{7*7}}'. A equipe recebeu a hipótese de que a expressão passou a ser interpretada como template.

**Decisão crítica:** template de saudação constante; dado de usuário inserido como texto.

**Hipótese que precisa ser refutada:** {{7*7}} permanece literal, sem execução nem acesso ao runtime.

**Evidência esperada:** renderGreeting('Ana') produz 'Olá, Ana!'; renderGreeting('{{7*7}}') preserva a expressão.

**Competência:** explicar a causa, prever observáveis, executar teste com entrada legítima e adversarial, selecionar a defesa e declarar os limites do teste.

### Mecanismo e exemplo resolvido

1. **Estado inicial:** Um portal usa a mesma saudação para Ana e para uma entrada '{{7*7}}'. A equipe recebeu a hipótese de que a expressão passou a ser interpretada como template.
2. **Entrada e fronteira:** template de saudação constante; dado de usuário inserido como texto.
3. **Decisão:** Construa o template apenas em código confiável, trate nome como dado e aplique escaping de saída HTML; não confunda escaping HTML com sandbox do template engine.
4. **Observação:** renderGreeting('Ana') produz 'Olá, Ana!'; renderGreeting('{{7*7}}') preserva a expressão.
5. **Interpretação:** {{7*7}} permanece literal, sem execução nem acesso ao runtime. Não confunda a evidência de um modelo isolado com exploração ou comprovação em produto de terceiros.

### Laboratório guiado (offline, código disponível)

Pré-requisito: Node.js 22 ou superior. Sem contas, API comercial ou rede. A execução é isolada e determinística.

```bash
node public/course-labs/a41-50/run.mjs 41
node --test public/course-labs/a41-50/lab.test.mjs
```

**Checkpoint 1 (prever):** Antes de rodar, escreva o que ocorrerá com a entrada legítima e a adversarial no caso 041.

**Checkpoint 2 (observar):** Na saída JSON procure `normal` (controle positivo) e `hostile` (controle negativo); compare os campos e diga qual condição bloqueou ou isolou o risco.

**Checkpoint 3 (corrigir e retestar):** Construa o template apenas em código confiável, trate nome como dado e aplique escaping de saída HTML; não confunda escaping HTML com sandbox do template engine. Reexecute e registre também o caso legítimo para evitar uma "correção" que só desliga a função.

**Troubleshooting:** Se o Node não reconhecer módulos ESM, confirme `node --version` (22+), execute o comando na raiz do repositório e preserve a extensão `.mjs`. Se `hostile` não for um erro, explique o isolamento de dados ou a invariância positiva esperada neste caso.

### Detecção, defesa, limites e fontes

- **O que procurar:** {{7*7}} permanece literal, sem execução nem acesso ao runtime.
- **Controle primário:** Construa o template apenas em código confiável, trate nome como dado e aplique escaping de saída HTML; não confunda escaping HTML com sandbox do template engine.
- **Controle de compatibilidade:** renderGreeting('Ana') produz 'Olá, Ana!'; renderGreeting('{{7*7}}') preserva a expressão.
- **Limitação honesta da evidência:** Este modelo não executa Jinja, Twig nem qualquer engine real; mede apenas a fronteira template fixo/dado.
- **Referência técnica para leitura crítica:** https://portswigger.net/web-security/server-side-template-injection
