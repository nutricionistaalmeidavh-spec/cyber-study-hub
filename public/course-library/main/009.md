# Aula 009 — CSRF: credenciais automáticas e intenção da requisição

**Trilha:** Web/AppSec Fundamentals · **Profundidade:** normal · **Tempo:** 45–60 min.  
Pré-requisitos explicados aqui: cookie mantém uma sessão; POST envia dados; o servidor decide se aceita a alteração. Execute somente os serviços locais fornecidos, com identidades fictícias.

## Alice autenticada não significa Alice solicitando a ação

Alice entrou no portal e recebeu um cookie de sessão. Depois, um site diferente induz seu navegador a enviar uma requisição ao portal para alterar seu e-mail. Se o navegador anexar o cookie e o servidor validar apenas a sessão, a alteração pode ocorrer sem a intenção de Alice. Esse é o problema de CSRF: usar credenciais que o navegador apresenta automaticamente para provocar uma ação.

Ler a resposta não é condição necessária. A política de mesma origem pode impedir que o site externo leia o retorno, mas a alteração já ter ocorrido. Para roubo de dados por leitura entre origens, outras regras e vulnerabilidades entram no cenário.

O risco depende do modo de autenticação e do contexto da requisição. Um cliente que adiciona manualmente `Authorization: Bearer ...` possui um modelo diferente de cookies automáticos; isso não elimina outros riscos, como XSS, armazenamento de tokens ou configurações CORS incorretas.

## Sessão, origem, site e token

Uma **sessão** associa um identificador opaco a um estado no servidor: usuário Alice, expiração e token anti-CSRF. O cookie não precisa carregar esses dados; ele pode conter apenas a chave aleatória do registro.

Uma **origem** combina esquema, host e porta. **Site**, para SameSite, segue regras de domínio registrável e esquema; dois subdomínios podem ser same-site e ainda cross-origin. Portanto, SameSite não é sinônimo de “somente minha página exata”.

Um **synchronizer token** é um segredo aleatório associado à sessão e apresentado no formulário ou cabeçalho de uma ação. A sessão prova quem está autenticado; o token adiciona uma evidência de que o cliente obteve o valor esperado naquele contexto. Isso não prova consciência humana nem supera um XSS capaz de operar na origem confiável.

Fluxo legítimo:

1. O servidor cria a sessão e um token aleatório, entregando-o por uma resposta acessível à aplicação legítima.
2. O navegador mantém o cookie; o formulário envia o token ao executar POST.
3. O servidor exige sessão válida **e token presente no formato correto**.
4. Compara o token recebido ao da sessão, valida a operação e somente então muda o e-mail.

Tokens não devem ir na URL, porque histórico, logs e referers podem expô-los. Esta aula usa token de sessão; token por requisição também é possível, com consequências para múltiplas abas e botão voltar. A implementação deve escolher e documentar o contrato. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## O defeito do exemplo anterior

O teste `recebido !== salvo` rejeita divergência, mas dois valores ausentes são iguais em JavaScript:

```js
undefined === undefined // true: nenhum token foi apresentado nem emitido
```

Logo, igualdade sem presença permite que um erro de inicialização vire aprovação. Usar comparação em tempo constante sem validar tamanhos também é incorreto: `timingSafeEqual` exige buffers de mesmo comprimento.

O trecho abaixo pertence ao programa completo `csrf.mjs`:

```js
export function validCsrf(received, stored) {
  if (typeof received !== 'string' || typeof stored !== 'string') return false;
  if (!/^[a-f0-9]{64}$/.test(received) || !/^[a-f0-9]{64}$/.test(stored)) return false;
  return timingSafeEqual(Buffer.from(received, 'hex'), Buffer.from(stored, 'hex'));
}
```

Cada token vem de `randomBytes(32).toString('hex')`: 32 bytes se tornam 64 caracteres hexadecimais. A expressão regular verifica representação, não aleatoriedade; quem fornece aleatoriedade é o gerador. Um valor `'a'.repeat(64)` passa pelo formato, mas só será válido se corresponder ao token emitido.

Na alteração, a ordem é sessão → token → validação do novo e-mail → mutação. O campo de e-mail do exercício aceita apenas letras minúsculas e `@example.invalid`; essa restrição é uma fixture, não um validador de e-mail de produção.

## Exemplo resolvido: mesma sessão, três entradas

| Sessão enviada | Token no corpo | Status | E-mail após a tentativa |
|---|---|---|---|
| Alice | Ausente | 403 | `alice@example.invalid` |
| Alice | Token de Bob | 403 | `alice@example.invalid` |
| Alice | Token de Alice | 200 | `novo@example.invalid` |
| Ausente | Qualquer um | 401 | Nenhuma conta alterada |

A segunda linha impede confundir “qualquer token emitido pelo serviço” com “token dessa sessão”. A resposta 403 deve vir antes da escrita; responder 403 depois de atualizar o banco não corrige CSRF.

Autoexplicação: por que repetir o token de Bob com o cookie de Alice deve falhar? Porque as duas evidências precisam pertencer ao mesmo contexto. Por que `HttpOnly` não resolve este cenário sozinho? Ele restringe leitura do cookie por JavaScript, mas o navegador continua podendo enviá-lo nas requisições elegíveis.

## Laboratório real de decisão e HTTP

Com Node.js 24, na raiz do pacote:

```sh
cd public/course-labs/phase16-web-p0
npm ci
node csrf.mjs
node csrf-http.mjs
node --test --test-name-pattern='CSRF' web.test.mjs
```

O primeiro programa compara explicitamente o teste antigo e o corrigido. Espere `antigo_sem_tokens: true`, `corrigido_sem_tokens: false`, duas rejeições 403 e um aceite 200.

O segundo sobe um servidor HTTP em porta aleatória de loopback, cria uma sessão fictícia, faz as requisições e encerra o servidor. A saída inclui:

```text
session: 201
absent: 403
unchanged: 'alice@example.invalid'
accepted: 200
changed: 'novo@example.invalid'
```

O cookie mantém a identidade entre requisições reais. `/lab-session` seleciona Alice/Bob para o exercício; **não é autenticação de produção**. O cookie é HttpOnly/SameSite=Lax; o lab usa HTTP local e omite Secure por esse motivo. Em serviço HTTPS, adote Secure e reveja domínio, path, duração e renovação da sessão.

Este driver usa `fetch` do Node e envia Cookie explicitamente. Ele demonstra a regra do backend e o estado antes/depois; **não testa a política SameSite de um navegador nem reproduz uma navegação cross-site**. Para observar essa camada, use um navegador em duas origens do seu laboratório, preservando logs de rede e registrando se o cookie foi efetivamente enviado. Não conclua que SameSite foi testado só porque o cabeçalho existe.

Checkpoint: confirme tanto o 403 quanto o e-mail inalterado. Depois confirme o 200 com alteração. Esses dois resultados evitam uma “correção” que simplesmente bloqueie todas as operações.

## Defesa em camadas e reteste

Mantenha GET sem efeitos sensíveis e exija o token nas rotas autenticadas que alteram estado. SameSite reduz envio de cookies em certos contextos; validação estrita de Origin/Referer e Fetch Metadata pode reforçar a política quando integrada à arquitetura. Cabeçalho personalizado e CORS restrito ajudam quando esse é o contrato do cliente, mas não tornam todo POST automaticamente protegido.

Não aceite vários formatos de corpo inadvertidamente em uma rota que depende do comportamento de preflight. E não use CORS apenas como um nome genérico para “proteção CSRF”: ele trata acesso entre origens e precisa ser avaliado junto de cookies, métodos e cabeçalhos.

Registre eventos como `csrf_rejected`, rota, request ID e categoria do motivo, sem token/cookie. Uma elevação após deploy pode revelar front-end antigo ou expiração mal tratada, não necessariamente ataque. Para investigar, compare idade da sessão, origem permitida e presença do token, sem coletar segredos.

| Sintoma | Hipótese específica | Como resolver |
|---|---|---|
| Tudo retorna 401 | Cookie ausente ou sessão expirada | Verifique manutenção da sessão antes do token |
| Requisição legítima retorna 403 | Token de sessão anterior, aba antiga ou campo errado | Busque token no contexto atual; não remova a validação |
| `timingSafeEqual` lança exceção | Comprimentos incompatíveis | Exija formato/tamanho antes da comparação |
| 403, mas e-mail mudou | Mutação ocorreu antes da autorização | Reordene a operação e teste estado persistido |
| CORS bloqueou leitura e a alteração ocorreu | Confusão entre leitura da resposta e envio/efeito | Examine requisição e estado do servidor separadamente |

Reteste: sem sessão, token ausente, vazio, malformado, de outra sessão e correto; GET não altera nada; expiração invalida a sessão. Para a camada navegador, acrescente testes separados de SameSite/origem e documente os resultados reais.

## Desafio, quiz e flashcards

Desafio: projete duas abas com token por sessão e expiração de 15 minutos. Mostre o comportamento após logout/login e diga como recuperar a tela sem reenviar automaticamente uma alteração antiga. A solução deve obter contexto novo e pedir uma nova ação, não aceitar o token obsoleto.

1. `undefined === undefined` aceita uma operação. Qual controle faltou? A) Comparar os valores depois de alterar o e-mail. B) Converter ambos os ausentes para string vazia e compará-los. C) Exigir presença e formato antes da comparação. D) Aceitar qualquer token que tenha sido emitido pelo servidor. **C:** igualdade de ausências não prova um token emitido.
2. Qual resultado prova melhor que a rejeição ocorreu antes da mutação? A) 403 com e-mail original preservado. B) Console sem erro. C) 200 com mensagem “bloqueado”. D) Página externa sem conseguir ler a resposta. **A:** combina decisão e efeito observado.
3. O cookie de Alice e o token de Bob são válidos isoladamente. O servidor deve: A) Aceitar, pois ambos vieram dele. B) Rejeitar a combinação de contextos. C) Trocar a sessão para Bob. D) Renovar o cookie e aceitar. **B:** o token precisa corresponder à sessão autenticada.
4. O teste HTTP do Node passou. O que continua sem ser provado? A) Que houve status HTTP. B) Que o e-mail mudou no caso permitido. C) Que os tokens ausentes foram recusados. D) Que o navegador respeitou a política SameSite. **D:** Node não exerce a navegação e as regras de cookies do navegador.

**Flashcards:** Cookie válido prova intenção? → Não; identifica uma sessão que pode ser enviada automaticamente. Qual é a falha de dois tokens ausentes? → Comparação de `undefined` com `undefined` pode aprovar. O que muda antes de escrever? → Sessão e token são verificados, depois o dado e a mutação. Por que 403 não basta? → O estado pode ter sido alterado antes da resposta. Same-site equivale a same-origin? → Não; esquema/host/porta definem origem, enquanto site usa outra fronteira.

## Segundo cenário: distinguir navegador, cliente HTTP e aplicação

Um teste de Node com `fetch` e cabeçalho `Cookie` escrito manualmente verifica a **decisão do servidor**, mas não comprova o que navegadores fariam com SameSite. Uma requisição iniciada por formulário em outra origem pode ser enviada sem que a página atacante consiga ler a resposta. Portanto, são duas perguntas distintas:

1. **O navegador anexa credenciais neste contexto?** Depende do tipo de credencial, atributos do cookie, navegação e política do navegador.
2. **Se a requisição chegar autenticada, o backend permite a mutação?** Exige sessão, autorização de negócio e defesa anti-CSRF conforme o contrato da rota.

**Diferença entre origin e site:** `https://app.example.test` e `https://files.example.test` são origens distintas, ainda que possam ser mesmo site dependendo do domínio registrável e esquema usado no experimento. `https://app.example.test:8443` é origem diferente de `https://app.example.test:443`. Não substitua uma análise da fronteira de confiança por uma comparação ingênua de strings contendo `example`.

### Três previsões antes do teste

- **POST com cookie Alice, sem token, rota protegida:** 403 e e-mail sem alteração.
- **POST com cookie Alice e token Bob:** 403 e e-mail sem alteração.
- **POST com cookie Alice e token Alice:** 200 e e-mail alterado se os demais requisitos forem válidos.

O 403 sozinho não demonstra sucesso: **leia o estado depois do pedido**. Uma implementação que atualiza o e-mail e só então devolve 403 é insegura. Um bloqueio que recusa até o token correto é uma regressão de disponibilidade funcional.

## Exercício de transferência: escolha controles, não slogans

Você está revisando um endpoint fictício `POST /account/email` que usa sessão por cookie. Considere as versões abaixo, sempre em localhost:

- **V1:** exige login, porém ignora token; não valida origem.
- **V2:** exige login e compara o token recebido com um valor da sessão **sem** rejeitar ausência dos dois.
- **V3:** exige login, verifica token aleatório existente e associado à sessão e valida entrada **antes** da mutação.

**Perguntas:** (1) Por que autenticação de V1 não basta? (2) Qual igualdade enganosa ameaça V2? (3) Que duas observações demonstram V3 sem bloquear o fluxo legítimo? (4) Por que configurar CORS sozinho não substitui validação anti-CSRF? (5) O que muda se a aplicação autentica com token Bearer anexado explicitamente pelo cliente, em vez de cookie automático?

**Critérios comentados:** V1 confia no cookie automaticamente apresentado; V2 pode aceitar `undefined === undefined`; V3 deve negar entrada ausente/incorreta sem mutar estado e aceitar entrada válida com mutação; CORS regula principalmente acesso de script à resposta e certos pedidos, não autoriza operações nem cobre todos os fluxos simples; Bearer explicitamente anexado não é enviado automaticamente por formulários cross-site, embora outras vulnerabilidades permaneçam.

### Caso negativo de navegador (opcional, ambiente controlado)

Se você conseguir usar um navegador real em **duas origens do seu laboratório**, documente a origem inicial, a origem destino, o método, o tipo de envio, atributos de cookie e cabeçalhos `Origin`/`Sec-Fetch-Site`. Registre se o cookie de sessão foi anexado **antes** de analisar a decisão do backend. Não force o envio de credenciais em domínios externos nem use contas reais. Para um teste automatizado sem navegador, escreva claramente **“política de navegador não testada”**.

### Falhas e recuperação durante a prática

- `401` antes do teste de token → confira se existe uma sessão de laboratório válida; não interprete como bloqueio anti-CSRF.
- `403` com token correto → verifique emissão, associação, parsing de corpo e expiração sem relaxar a validação global.
- `200` com token errado e estado alterado → reprove a versão e preserve a entrada que reproduz a falha para regressão.
- `200` sem alteração → pode haver outro erro de negócio; status não substitui verificação do estado.

**Entrega de domínio:** uma tabela de pelo menos quatro tentativas contendo identidade, presença/associação do token, status esperado, status observado, estado antes/depois e conclusão. Guarde tokens apenas como rótulos “Alice”, “Bob”, “ausente”, nunca seus bytes em relatórios compartilhados.

**Fontes:** [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) e [MDN — SameSite cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Set-Cookie#samesitesamesite-value). Ambas reforçam que SameSite compõe a defesa e que origem e site são fronteiras diferentes.
