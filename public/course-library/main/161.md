## 2. Objetivo e mecanismo causal

Segurança de memória exige três invariantes: objeto vivo, acesso dentro de sua extensão e tipo/alinhamento compatíveis. Uma entrada pode violar o comprimento sem mudar o ponteiro; free pode invalidar um ponteiro sem mudar seu valor numérico. O primeiro caso é espacial, o segundo temporal. O parser próprio fornece uma escrita fora do array e uma leitura fora da alocação; lab.c fornece uso após free. O diagnóstico classifica a violação, mas não estabelece automaticamente explorabilidade.

## 4. Exemplo resolvido — estado, decisão e efeito

Em N 08 ABCDEFGH, size=10, n=8 e name ocupa oito bytes. O teste n>8 passa, a cópia ocupa [0,7] e NUL tenta índice 8. Em R 08 X, size=3 e o corpo tem um byte; 2+n=10 aponta além da alocação de três bytes. No UAF, objeto de quatro bytes está vivo antes de free e morto depois: alias[0] seria inválido mesmo com índice zero. Logo, corrigir só o índice não resolve lifetime.

## 7. Código comentado e artefatos

```c
if (size < 2) return -1; // garante que size-2 não sofre underflow
size_t n = data[1];
if (n >= sizeof name || n > size - 2) return -1;
memcpy(name, data + 2, n); // corpo suficiente e destino com espaço
name[n] = '\0';         // terminador ainda pertence ao objeto
```

## 10. Defesa e reteste

Para violação espacial, valide extensão antes do acesso; para violação temporal, altere ownership e ordem de uso/liberação. Reteste com o mesmo arquivo e inclua caso válido. ASLR/NX podem limitar efeitos de uma falha, mas não restauram o contrato de objetos.

## 11. Troubleshooting específico

Se o programa simplesmente termina por sinal, abra o log completo antes de classificar. Diagnóstico de shadow memory indisponível é falha de ambiente, não confirmação da hipótese. Use builds non-PIE de análise definidos pelo runner.

## 14. Quiz

### 1. alias[0] após free viola qual invariante?

B. Tamanho do cabeçalho

**Resposta:** C. O objeto já morreu; índice zero não torna o acesso válido.

A. Alocação de entrada criada pelo driver
B. Array name da stack

## Complemento A editorial — aplicação e transferência de competência (AULA-161)

Este complemento amplia o laboratório real existente, **sem substituir** os programas C, fixtures, comandos, avisos de segurança ou evidências anteriores. O objetivo é provar decisão e reteste em cenário novo, com interpretação independente.

### 1. Caso de trabalho e competência exigida

Um parser próprio lê campo de 4 bytes de uma alocação de 8 bytes. O índice inicial é 6, mas a equipe verifica apenas que 6 < 8. Separadamente, uma referência válida aponta para uma alocação já liberada. O relatório precisa reconhecer duas classes de defeito distintas, sem afirmar execução de código arbitrário.

**Competência:** distinguir a invariante violada, explicar o mecanismo que causa a condição, selecionar a correção causal e demonstrar o caminho legítimo em reteste. Duração complementar: 65–85 min. Custo obrigatório: R$0.

1. **Segurança espacial** exige que intervalo [offset, offset+width) esteja contido no objeto; verificar só offset é insuficiente.

2. **Segurança temporal** exige que o objeto ainda esteja vivo durante o uso; endereço numérico igual não restabelece lifetime.

3. **Sanitizer** evidencia o acesso inválido no trajeto executado, não o potencial de exploração universal.

### 2. Raciocínio mecanístico e contraexemplo

No caso espacial, offset=6 e width=4 exige bytes 6,7,8,9; a capacidade 8 só cobre 0…7. Condição robusta é offset>=0, width>0, offset<=capacity e width<=capacity-offset, evitando overflow na soma. Se `alive=false`, mesmo offset 0 e width 1 falham por lifetime; não há correção espacial que torne o ponteiro seguro. O parser C real em `/course-labs/phase16-memory` já ilustra stack-buffer-overflow, heap-buffer-overflow e heap-use-after-free com ASan. O novo modelo complementa, não substitui o laboratório de C.

**Teste positivo independente:** capacidade 8, offset 4 e width 4, com objeto vivo: acesso válido na fixture.

**Teste negativo independente:** offset 6, width 4 ou `alive=false`: respectivamente fora de faixa e uso temporal inválido.

**Limite da experiência:** O modelo JS não aloca endereços nativos, não mede alinhamento/tipos, lifetime real, ASan, risco de ataque nem impacto.
