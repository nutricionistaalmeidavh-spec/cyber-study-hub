## 2. Visão geral

OAuth delega autorização; OIDC adiciona identidade. A segurança está em redirect URIs, state/nonce, PKCE e validação correta dos tokens.

## 3. Aprofundamento: o que realmente está acontecendo

OAuth 2.0 delega autorização. OIDC adiciona identidade. Confundir access token, ID token, authorization code e refresh token cria decisões erradas mesmo quando a criptografia está correta.

## 5. Conceitos fundamentais

### 1. Authorization Code
Código temporário trocado por tokens.
### 2. PKCE
Prova que vincula o cliente que iniciou o fluxo ao resgate do code.
### 3. State
Valor usado para relacionar resposta ao fluxo iniciado e mitigar CSRF.
### 4. Nonce
Valor usado no OIDC para vincular o ID token ao fluxo.

## 6. Fluxo técnico

1. **Cliente inicia autorização**
2. **Authorization Server autentica usuário**
3. **State/nonce vinculam a resposta à sessão**
4. **PKCE protege troca do código**
5. **Cliente recebe tokens com finalidade definida**
6. **API valida access token; cliente valida ID token quando aplicável**

## 7. Exemplo técnico — Gerar challenge PKCE

```js
const verifier = base64url(crypto.getRandomValues(new Uint8Array(32)));
const digest = await crypto.subtle.digest(
  "SHA-256",
  new TextEncoder().encode(verifier)
);
const challenge = base64url(new Uint8Array(digest));

// Salve verifier apenas para a troca do authorization code.

```

### Como ler o exemplo

PKCE reduz o valor de um authorization code interceptado sem o verifier correspondente.

## 8. Por que a vulnerabilidade/mecanismo acontece

OAuth delega autorização; OIDC adiciona identidade. Os erros mais comuns surgem em redirect URI, state, PKCE, armazenamento de tokens e confusão entre access token e ID token.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 10. Como detectar

Procure redirects fora da allowlist, reutilização de code, tokens para audiência errada e falhas de state/nonce.

## 11. Como corrigir / reduzir risco

Use redirect URIs exatas, PKCE, state/nonce fortes e valide issuer, audience e assinatura.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 18. Oficina A — OAuth e OIDC Security

**Objetivo mensurável:** Separar delegação OAuth de autenticação OIDC e identificar vínculos de redirect URI, state/PKCE, emissor, nonce e tokens.

### Situação profissional e pré-requisitos

Uma aplicação começa Authorization Code + PKCE para uma conta fictícia. O cliente guarda em sessão a transação com `state`, provedor esperado e `code_verifier`; o callback não pode aceitar códigos sem vínculo à solicitação iniciada.

Para começar, identifique o ator, o dado controlável, o componente que decide, o recurso afetado e o resultado que realmente pode ser observado. Não atribua ao laboratório funções de produção. Refaça a distinção entre hipótese, evidência e interpretação antes de qualquer mudança no controle.

### Mecanismo: acompanhe o dado até a decisão

PKCE S256 envia `code_challenge` derivado de um `code_verifier` aleatório e revela o verifier somente no token endpoint. State vincula o callback à transação quando empregado; OIDC nonce vincula ID Token e autenticação, e iss protege contra mix-up. Access token não deve ser aceito como ID Token. Redirect URI registrada deve ser comparada exatamente com exceções previstas para loopback nativo.

**Exemplo resolvido.** `pkcePair(Buffer.alloc(32,7))` ilustra a derivação SHA-256 sem rede real. `verifyAuthorizationResponse` compara state e emissor esperados, marca transação como usada e rejeita replays. O teste não emite nem troca tokens reais.

**Questão de compreensão:** em qual momento a entrada deixa de ser mero dado e passa a interferir em uma decisão? Formule uma frase citando o objeto exato, a condição de falha e a observação esperada. Não confunda a explicação de mecanismo com uma prova de exploração.

**Limites do experimento:** O simulador não implementa cliente OAuth completo, endpoint `/token`, validação de JWT do ID Token, token binding nem armazenamento de sessão durável.
