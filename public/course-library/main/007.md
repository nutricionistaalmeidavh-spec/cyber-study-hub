## 9. Como defender / corrigir

Use queries parametrizadas, validação de entrada e menor privilégio no banco; evite montar SQL com concatenação.

A correção deve agir sobre a causa. Evite controles cosméticos como esconder IDs, renomear rotas, desativar mensagens sem corrigir a decisão ou confiar somente no frontend.

## 10. Como detectar / investigar

Monitore erros SQL, padrões de input anormais, consultas fora do baseline e aumento súbito de erros 5xx ligados ao banco.

Uma detecção útil combina:

```text
+ ação
+ recurso/destino
+ horário
+ resultado
+ contexto
```

## 14. Aprofundamento específico — SQL Injection: dado não pode virar instrução

### Problema concreto e objetivo demonstrável

Um formulário busca pedido pelo identificador informado. Quando o backend concatena o valor numa string SQL, aspas recebidas do cliente podem mudar o significado da consulta. Um usuário legítimo chamado O'Hara também demonstra por que “proibir apóstrofo” é uma solução ruim: prejudica dados normais sem separar código e valores.

**Ao concluir, você deve ser capaz de:** localizar a decisão no sistema; prever comportamento permitido e negado; reproduzir o exemplo em ambiente isolado; explicar o motivo do resultado; propor correção e retestar sem bloquear o caso legítimo.

### Mecanismo, conceitos e limites

Uma consulta SQL contém **estrutura** (`SELECT`, `FROM`, `WHERE`) e **valores** que devem ser vinculados como parâmetros. Na construção insegura, texto externo é incorporado à instrução antes de o banco interpretá-la; um delimitador pode encerrar o literal. Na consulta parametrizada, o motor SQL recebe a instrução e os valores separadamente, mantendo o valor como dado. Isso não autoriza automaticamente o acesso: uma query parametrizada ainda pode devolver objetos de outro usuário se faltar filtro de proprietário. Evite privilégios amplos de banco, mensagens com SQL bruto e concatenação de nomes de coluna/tabela (identificadores exigem allowlist específica, não placeholder comum).

### Exemplo resolvido (com raciocínio e evidência)

Banco de teste contém `(R10,ana,livro)` e `(R11,bia,caderno)`. A entrada fictícia `' OR 1=1 --` aplicada à consulta *deliberadamente vulnerável* `"SELECT id FROM pedidos WHERE id = '" + dado + "'"` muda a condição e retorna ambos. Essa string aparece **somente** contra SQLite em memória no seu dispositivo. Já `"SELECT id FROM pedidos WHERE id = ?"` com `dado` como parâmetro retorna lista vazia, pois não existe pedido com esse texto literal. A busca normal por `R10` retorna só R10.

Além disso, `SELECT id FROM pedidos WHERE id=? AND owner=?` assegura escopo quando combinado com identidade confiável. Placeholder sozinho previne alteração de sintaxe, mas não entrega autorização.

## 16. Defesa, evidências e reteste

Não concatene valores externos em SQL. Use consultas parametrizadas em todas as rotas, reduza privilégios de banco e valide tamanho/tipo por regra de negócio. Uma ORM só ajuda quando utilizada corretamente; consultas raw ainda podem ser vulneráveis. Faça retestes que assegurem tanto a resistência à injeção quanto buscas normais e escopo por usuário.

Produza um relatório curto com quatro partes: (a) hipótese e escopo; (b) entrada e estado inicial; (c) saída observada, comparada à esperada; (d) melhoria e repetição dos casos positivo e negativo. Não inclua tokens, senhas, dados pessoais ou URLs de sistemas alheios.
