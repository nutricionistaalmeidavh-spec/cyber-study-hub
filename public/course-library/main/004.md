# Aula 004 — Senhas, Hash, Salt e Bcrypt

**Trilha:** Web/AppSec Fundamentals · **Profundidade:** normal · **Tempo:** 45–60 min.  
Conhecimento de função, string e `await` ajuda; os exemplos abaixo explicam o necessário. Prática exclusivamente com senhas fictícias no próprio computador.

## O problema: o banco foi copiado

O banco guarda o cadastro de Alice. Se a coluna `password` contiver sua senha, uma cópia do banco expõe imediatamente esse segredo. Criptografar com uma chave mantida junto do banco apenas desloca o problema. O serviço normalmente precisa verificar uma tentativa de login, não recuperar a senha original.

O contrato desejado é: cadastrar uma senha gera um verificador; apresentar a mesma senha é aceito; apresentar outra é rejeitado. Uma cópia dos verificadores não deve transformar cada tentativa offline em uma operação barata. Isso não torna uma senha fraca impossível de descobrir: o adversário ainda pode testar hipóteses contra o verificador. Nesta aula usamos apenas duas tentativas fictícias, sem listas de senhas reais.

## Hash, salt e custo são decisões diferentes

Um hash comum, como SHA-256, produz um resumo determinístico de bytes. Essa propriedade ajuda a conferir integridade de arquivos, mas a velocidade é inconveniente para guardar senhas. Um hash de senha introduz trabalho deliberadamente caro e parâmetros ajustáveis.

**Salt** é um valor aleatório diferente para cada cadastro. Ele participa do cálculo e é guardado junto do resultado; não precisa ser secreto. Assim, duas pessoas com a mesma senha têm verificadores diferentes, e trabalho pré-computado para um salt não serve diretamente para outro. O salt não aumenta a força da senha escolhida nem impede uma tentativa dirigida a um único verificador.

**Custo bcrypt** é um expoente do trabalho de expansão de chave: aumentar de 10 para 11 tende a aproximadamente duplicar o trabalho, não a acrescentar 10%. O tempo observado também depende de CPU, implementação e carga. Um custo excessivo pode saturar o serviço de login; limite concorrência e tentativas, além de medir latência sob carga realista.

**Pepper** é um segredo separado do banco usado em uma construção projetada para isso. Exige gestão de segredo, disponibilidade e estratégia de troca. Não é um salt fixo e não deve ser concatenado por improvisação ao exemplo.

Para novos sistemas, a orientação consultada prioriza Argon2id, que também exige memória: um ponto mínimo documentado é 19 MiB, duas iterações e paralelismo 1. Bcrypt continua relevante para manter e migrar sistemas existentes; o lab o usa por ser o tema desta aula. Cost 10 é o piso didático, não uma decisão universal de produção. Consulte e dimensione os parâmetros no ambiente real. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Como a verificação funciona

O valor bcrypt codificado registra versão, custo, salt e resultado. Ao verificar, a biblioteca recupera os parâmetros desse valor, executa a operação sobre a senha recebida e compara o resultado. Ela não descriptografa o verificador. Por isso, chamar `hash(tentativa)` novamente e comparar as strings é incorreto: o novo cadastro gera outro salt.

Neste laboratório, `bcryptjs` fornece a implementação e `await` espera a Promise terminar. A API assíncrona evita bloquear toda a operação como uma única chamada síncrona longa; ela não cria automaticamente um serviço ilimitado de processamento paralelo.

```js
// Trecho de passwords.mjs; imports e programa completo acompanham o laboratório.
export async function register(password, cost = 10) {
  validatePassword(password);
  if (!Number.isInteger(cost) || cost < 10 || cost > 14) {
    throw new Error('CUSTO_FORA_DO_LAB');
  }
  return bcrypt.hash(password, cost); // salt aleatório gerado pela biblioteca
}

export async function authenticate(password, encodedHash) {
  validatePassword(password);
  return bcrypt.compare(password, encodedHash); // reutiliza os parâmetros salvos
}
```

Os limites 10–14 são uma restrição deste exercício; não equivalem à faixa completa do algoritmo. Nunca use este registro isolado como uma API de autenticação pronta: persistência, recuperação de conta, rate limiting e sessões não estão implementados aqui.

### O limite é de bytes, não de letras

Bcrypt considera até 72 bytes de entrada. Truncar silenciosamente permite que duas entradas diferentes depois desse limite sejam equivalentes para o algoritmo. O código rejeita o excesso antes de cadastrar **e** verificar:

```js
if (Buffer.byteLength(password, 'utf8') > 72) {
  throw new Error('LIMITE_BCRYPT_72_BYTES');
}
```

`'é'.repeat(36)` ocupa 72 bytes em UTF-8, mas tem 36 caracteres. Repetir 37 vezes ocupa 74 bytes. `password.length` mede unidades UTF-16 em JavaScript, não o comprimento UTF-8 usado na fronteira. Não retire caracteres, espaços ou acentos silenciosamente; uma política de transformação precisa ser explícita e consistente.

## Exemplo resolvido: cadastrar duas vezes

| Operação | Resultado esperado | Explicação |
|---|---|---|
| `register('senha fictícia')` duas vezes | Strings diferentes | Cada chamada gera seu salt |
| `authenticate('senha fictícia', primeiroHash)` | `true` | A tentativa usa o salt/custo do primeiro verificador |
| `authenticate('outra', primeiroHash)` | `false` | O resultado da tentativa não corresponde |
| Cadastrar 37 letras `é` | Exceção de 72 bytes | A fronteira evita truncamento |

Autoexplicação: se o salt é público, por que ele ainda é útil? Resposta: sua função é individualizar o trabalho, não ser uma segunda senha. Se a comparação direta de dois hashes dá `false`, isso prova que as senhas eram diferentes? Não: salts diferentes bastam para mudar os valores.

### Exercício parcialmente resolvido

Você recebeu `const hash = await register('laboratório');`. Complete uma única expressão que aceite a tentativa correta sem gerar novo cadastro. Gabarito: `await authenticate('laboratório', hash)`. Teste também `laboratorio`, sem acento: deve retornar `false`, pois os bytes são diferentes.

### Prática independente

Em um arquivo local que importe `register`, meça três cadastros de cada custo 10 e 11 com `performance.now()`. Use uma senha fictícia fixa, mas deixe a biblioteca variar o salt. Compare medianas e anote versão do Node e CPU. Não exija uma razão exata de 2: escalonamento e aquecimento introduzem ruído. Não faça benchmark concorrente contra um serviço publicado.

## Detecção, correção e reteste

Revise o formato/algoritmo e os parâmetros dos verificadores, sem exportar senhas ou hashes para logs. Métricas úteis incluem duração de verificação, taxa de falhas por conta/origem e saturação da fila. Muitas falhas online podem sugerir abuso; uma cópia offline do banco não necessariamente produz eventos no login.

Para migrar, guarde a identificação do algoritmo por registro. Após um login validado com o algoritmo antigo, derive um verificador novo usando a senha que acabou de ser apresentada e substitua o registro de maneira consistente. Não é possível recalcular Argon2id a partir do hash bcrypt e obter o mesmo contrato de uma senha original. Contas que não retornarem precisam de uma estratégia de recuperação adequada.

Reteste cadastro, login correto, login errado, caracteres multibyte, atualização de custo e falhas de persistência. A alteração do custo não deve invalidar verificadores antigos enquanto o fluxo de migração os suporta.

| Sintoma | Causa provável | Investigação e ação |
|---|---|---|
| Dois hashes da mesma senha são diferentes | Salt aleatório funcionando | Verifique com `compare`; não compare hashes entre si |
| Todas as tentativas parecem aceitas | Promise usada como booleano, sem `await` | Inspecione o resultado resolvido; `Promise` é truthy |
| Senha longa falha só no login | Políticas diferentes no cadastro e verificação | Aplique a mesma validação de bytes nas duas fronteiras |
| Login ficou lento após elevar custo | Trabalho por tentativa aumentou | Meça fila/latência; ajuste capacidade e limites, não remova o hash |

## Desafio e revisão

Desenhe a migração de 100 contas fictícias de cost 10 para uma política nova. Defina quando rehash acontece, o que registrar sem segredo e como lidar com usuários inativos. Critérios: verificar antes de migrar, salt novo, operação persistida consistente e reteste de credenciais antigas durante a transição.

1. Alice e Bob escolheram a mesma senha, mas seus verificadores diferem. Qual explicação é compatível com um cadastro correto? A) O mesmo hash sempre muda quando é lido do banco. B) Cada cadastro usa salt distinto. C) O salt é um segredo exclusivo fornecido pelo usuário. D) A diferença prova que uma das senhas foi digitada incorretamente. **B:** variação do salt altera o verificador sem alterar a senha.
2. Qual entrada ultrapassa o limite de 72 bytes do exercício? A) 36 letras `é`. B) 72 letras ASCII `a`. C) 37 letras `é`. D) 35 letras `é`. **C:** 37 × 2 = 74 bytes em UTF-8.
3. Qual operação verifica uma tentativa contra um registro? A) `compare(tentativa, hashSalvo)`. B) `hash(tentativa) === hashSalvo`. C) Decodificar o salt e obter a senha. D) Comparar apenas os prefixos de custo. **A:** a comparação reutiliza os parâmetros do registro; os demais caminhos não verificam a senha.
4. Aumentar cost 10 para 11 sem testar carga pode causar o quê? A) Duplicar o tamanho do verificador salvo. B) Exigir trocar os salts de todos os registros antes do próximo login. C) Invalidar todos os hashes antigos por usarem outro custo. D) Aumentar latência e consumo de CPU por tentativa. **D:** o trabalho cresce; registros anteriores ainda carregam seus próprios parâmetros.

**Flashcards:** Por que salt não é secreto? → Ele separa cálculos por cadastro, não autoriza login. Qual tamanho deve ser medido antes de bcrypt? → Bytes UTF-8, com limite de 72 neste contrato. Por que `await` importa? → O booleano só existe após resolver a Promise. Pode rehash de migração usar somente o hash antigo? → Não para obter um verificador direto da senha original. O que medir ao trocar custo? → Latência e saturação sob carga representativa, além de correção do login.
