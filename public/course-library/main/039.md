# Aula 039 — DevSecOps

**Trilha principal:** Pentest & Secure Development · **Duração sugerida:** 50–65 min · **Estado:** aprofundamento editorial A (IA) sujeito a registro SHA-256.  
**Ambiente:** Node.js 22+, sem Docker obrigatório, sem assinatura ou API paga. Testes só com dados fictícios, em memória ou serviço `127.0.0.1` criado pela suíte.

> Só execute técnicas ativas em ativos próprios ou autorizados explicitamente. O resultado de uma fixture local não se transfere automaticamente para sistemas externos. As atividades não requerem credenciais reais.

## Problema e objetivo mensurável

Um serviço de notas passa no build, mas falha teste de autorização. O pipeline anterior usava `continue-on-error`, exibindo etapa verde. A entrega não deve ocorrer quando uma verificação bloqueante falha, ainda que o código compile e a hospedagem funcione.

**Competência observável:** Montar um gate de CI de segurança determinístico que impede entrega com testes falhos ou risco alto confirmado. Para demonstrá-la, o estudante deve prever a decisão, executar os casos positivos e negativos e explicar evidências, hipóteses alternativas e limites da simulação. Não basta nomear ferramentas.

## Fundamentos e pré-requisitos recomendados

Os pré-requisitos são recomendações, nunca bloqueio da aula: HTTP básico, diferença entre autenticação/autorização, lógica booleana e leitura de logs. Onde necessário, use o vocabulário abaixo antes de abrir o terminal.

1. **Conceito 1.** Gate: condição verificável que impede avanço enquanto não atendida.

2. **Conceito 2.** Fail-closed: na ausência de aprovação, não liberar deploy automaticamente.

3. **Conceito 3.** Artefato reproduzível: compilação e verificações com versões/entradas registradas.

## Mecanismo técnico: entrada, fronteira, controle e resultado

O contrato mínimo exige testsPassing=true, artifactBuilt=true e verifiedHighRisks=0. Build não implica integridade de autorização; zerar alarmes sem tratar causa também não. Exceções em produção exigem processo registrado e decisor autorizado, mas este laboratório não oferece bypass. CI roda sem acesso a secrets nem serviço pago; deploy é propositalmente excluído do exercício.

**Modelo de decisão:** estado inicial → entrada controlada → componente que decide → efeito observável → comparação com a política. Sempre diga onde mora a autoridade: aplicativo, navegador, banco, armazenamento ou processo de entrega. O nome de uma ferramenta não responde essa pergunta.

### Exemplo resolvido e comentado

```js
import { releaseGate } from './models.mjs';
releaseGate({testsPassing:true,verifiedHighRisks:0,artifactBuilt:true}); // true
releaseGate({testsPassing:false,verifiedHighRisks:0,artifactBuilt:true}); // false
```

> Este trecho é um recorte da fixture da aula; execute o teste completo pelo comando abaixo, a partir da raiz do projeto. A sintaxe de import acima representa o módulo do diretório de laboratório, e não uma dependência publicada.

**Evidência esperada:** Publicação permitida somente com testes, build e ausência de risco alto confirmado; caso negativo bloqueado.

## Laboratório reproduzível — um positivo e um negativo

**Requisitos:** Node.js 22 ou superior, terminal local e repositório. O código e os testes estão em `/course-labs/a031-040/models.mjs` e `/course-labs/a031-040/lab.test.mjs`. O serviço HTTP criado na aula 032 e no capstone escuta exclusivamente `127.0.0.1` em porta aleatória, fecha ao terminar e não faz requisições a serviços externos.

```sh
# A partir da raiz do repositório
node --test public/course-labs/a031-040/lab.test.mjs
```

**Roteiro guiado com previsão e feedback:**

1. Escreva primeiro o teste de gate vermelho: build passa mas autorização falha.
2. Corrija o estado do teste, preservando o bloqueio de risco confirmado alto.
3. Explique como branch protections e revisão independente complementam a função simples.

**Checkpoint A — antes:** anote qual resultado positivo preserva o uso legítimo.  
**Checkpoint B — depois:** anote o caso negativo, dado de entrada, controle que decidiu e resultado real.  
**Checkpoint C — interpretação:** declare uma hipótese alternativa e qual dado adicional seria necessário para descartá-la.

**O que deve aparecer:** Publicação permitida somente com testes, build e ausência de risco alto confirmado; caso negativo bloqueado. Arquive somente o nome do teste e os valores de estado/decisão sintéticos; não adicione tokens ou dados pessoais. A suíte pode reportar também testes das outras nove aulas, mas cada assert está identificado pelo ID desta aula.

### Quando algo não funciona

Um pipeline pode exibir job bem-sucedido porque erros foram ignorados; verifique códigos de saída e proteção de branch, não apenas rótulos.

Para recuperar: confira a versão `node --version`, inicie no diretório raiz, execute novamente uma única vez após corrigir a causa e compare os resultados; não modifique expectativas só para tornar os testes verdes.

## Detecção, prevenção e reteste

**Evidência a observar:** Guarde commit SHA, logs minimizados, versões, evidência dos testes e responsável pela revisão; nunca faça echo de tokens.

**Medida corretiva:** Integre gates proporcionais ao risco, revisão e retestes contínuos. Observabilidade pós-release continua necessária.

**Critério de reteste:** o caminho originalmente indevido deve ser negado sob as mesmas pré-condições, enquanto o caminho legítimo continua funcionando. Documente casos não cobertos. Um caso rejeitado não é automaticamente prova de que todas as variações estão seguras.

## Prova final independente — competência aplicada

**Novo cenário, distinto da fixture:** O pipeline de um app financeiro aprova `npm run build`, mas falha teste que impede duas cobranças com mesmo idempotency key. Um desenvolvedor propõe ignorar o teste por 48 horas e deixar CI verde.

Responda *sem abrir o gabarito*, incluindo resultado previsto e ao menos uma limitação:

1. Qual fato impede a publicação mesmo com build concluído?
2. Em que etapa do pipeline a verificação de idempotência deve executar?
3. Qual critério faria o teste deixar de bloquear de maneira técnica?
4. O que registrar para aprovação excepcional, sem mascarar falha?
5. Como preservar rastreabilidade entre artefato testado e commit publicado?
6. Qual monitoramento continua útil mesmo após o gate passar?

Após concluir, compare seu relatório com o [gabarito independente e rubrica](/course-labs/a031-040/answer-keys/AULA-039.md). A publicação do gabarito não substitui a tentativa independente.
