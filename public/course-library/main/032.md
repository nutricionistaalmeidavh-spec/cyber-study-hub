# Aula 032 — Reconhecimento e Superfície de Ataque

**Trilha principal:** Pentest & Secure Development · **Duração sugerida:** 40–55 min · **Estado:** aprofundamento editorial A (IA) sujeito a registro SHA-256.  
**Ambiente:** Node.js 22+, sem Docker obrigatório, sem assinatura ou API paga. Testes só com dados fictícios, em memória ou serviço `127.0.0.1` criado pela suíte.

> Só execute técnicas ativas em ativos próprios ou autorizados explicitamente. O resultado de uma fixture local não se transfere automaticamente para sistemas externos. As atividades não requerem credenciais reais.

## Problema e objetivo mensurável

Um protótipo didático expõe `/`, `/health` e `/api/notes`. O serviço devolve 200 nas duas primeiras rotas e 401 na API de notas. O trabalho não é 'achar vulnerabilidades': é mapear os recursos conhecidos, documentar os limites da amostra e distinguir autenticação esperada de erro.

**Competência observável:** Construir inventário verificável de endpoints de uma aplicação própria sem transformar descoberta em ataque. Para demonstrá-la, o estudante deve prever a decisão, executar os casos positivos e negativos e explicar evidências, hipóteses alternativas e limites da simulação. Não basta nomear ferramentas.

## Fundamentos e pré-requisitos recomendados

Os pré-requisitos são recomendações, nunca bloqueio da aula: HTTP básico, diferença entre autenticação/autorização, lógica booleana e leitura de logs. Onde necessário, use o vocabulário abaixo antes de abrir o terminal.

1. **Conceito 1.** Superfície de ataque: pontos pelos quais dados ou identidades entram e saem de componentes.

2. **Conceito 2.** Inventário: registro de ativo, rota, método, autenticação, dono e observação.

3. **Conceito 3.** Baseline: condição de referência necessária para reconhecer mudanças reais.

## Mecanismo técnico: entrada, fronteira, controle e resultado

Descobertas começam pelos recursos fornecidos ou explicitamente autorizados. A função `inventoryOwnApp()` cria um servidor efêmero em 127.0.0.1, escolhe porta aleatória, percorre três rotas aprovadas e encerra o listener. `401` significa que há uma política de autenticação para aquela requisição, não uma falha; status HTTP não é teste de bypass. Métodos e estados de autenticação não cobertos ficam como lacuna do inventário, jamais como 'seguros'.

**Modelo de decisão:** estado inicial → entrada controlada → componente que decide → efeito observável → comparação com a política. Sempre diga onde mora a autoridade: aplicativo, navegador, banco, armazenamento ou processo de entrega. O nome de uma ferramenta não responde essa pergunta.

### Exemplo resolvido e comentado

```js
import { inventoryOwnApp } from './models.mjs';
const rows=await inventoryOwnApp();
console.table(rows); // /:200, /health:200, /api/notes:401
```

> Este trecho é um recorte da fixture da aula; execute o teste completo pelo comando abaixo, a partir da raiz do projeto. A sintaxe de import acima representa o módulo do diretório de laboratório, e não uma dependência publicada.

**Evidência esperada:** Três rotas e status `[200,200,401]` somente em loopback. Nenhum scanner toca IPs públicos.

## Laboratório reproduzível — um positivo e um negativo

**Requisitos:** Node.js 22 ou superior, terminal local e repositório. O código e os testes estão em `/course-labs/a031-040/models.mjs` e `/course-labs/a031-040/lab.test.mjs`. O serviço HTTP criado na aula 032 e no capstone escuta exclusivamente `127.0.0.1` em porta aleatória, fecha ao terminar e não faz requisições a serviços externos.

```sh
# A partir da raiz do repositório
node --test public/course-labs/a031-040/lab.test.mjs
```

**Roteiro guiado com previsão e feedback:**

1. Antes do comando, desenhe browser → API e destaque quais rotas constam no escopo.
2. Execute o servidor próprio e registre três linhas: rota, status e necessidade presumida de autenticação.
3. Proponha uma segunda linha para cada rota com método POST: não a teste sem incluí-la no escopo atualizado.

**Checkpoint A — antes:** anote qual resultado positivo preserva o uso legítimo.  
**Checkpoint B — depois:** anote o caso negativo, dado de entrada, controle que decidiu e resultado real.  
**Checkpoint C — interpretação:** declare uma hipótese alternativa e qual dado adicional seria necessário para descartá-la.

**O que deve aparecer:** Três rotas e status `[200,200,401]` somente em loopback. Nenhum scanner toca IPs públicos. Arquive somente o nome do teste e os valores de estado/decisão sintéticos; não adicione tokens ou dados pessoais. A suíte pode reportar também testes das outras nove aulas, mas cada assert está identificado pelo ID desta aula.

### Quando algo não funciona

Se surgir 404, confirme que está rodando a fixture, não outra aplicação local. 401 não autoriza tentativa de adivinhar credenciais.

Para recuperar: confira a versão `node --version`, inicie no diretório raiz, execute novamente uma única vez após corrigir a causa e compare os resultados; não modifique expectativas só para tornar os testes verdes.

## Detecção, prevenção e reteste

**Evidência a observar:** Compare inventário por versão e data; route owner, método e tipo de informação são mais úteis que um número isolado de endpoints.

**Medida corretiva:** Reduza exposição desnecessária, documente owners e aplique proteção de autenticação/autorização independentemente de o recurso aparecer no inventário.

**Critério de reteste:** o caminho originalmente indevido deve ser negado sob as mesmas pré-condições, enquanto o caminho legítimo continua funcionando. Documente casos não cobertos. Um caso rejeitado não é automaticamente prova de que todas as variações estão seguras.

## Prova final independente — competência aplicada

**Novo cenário, distinto da fixture:** Um inventário aprovado de um painel acadêmico lista `GET /notas` (401), `GET /assets/logo.svg` (200) e `POST /exportar` (403 para usuário comum). O scanner marca os dois erros 4xx como críticos.

Responda *sem abrir o gabarito*, incluindo resultado previsto e ao menos uma limitação:

1. Quais dados adicionais faltam para transformar essas observações em inventário utilizável?
2. O que os códigos 401 e 403 demonstram e o que não demonstram?
3. Qual componente decide se o aluno vê notas?
4. Qual teste positivo de baixa intrusão diferenciaria bloqueio correto de quebra funcional?
5. Quando uma rota nova deve voltar à revisão de escopo?
6. Que evidência sustentaria atualização de inventário sem qualificar severidade prematuramente?

Após concluir, compare seu relatório com o [gabarito independente e rubrica](/course-labs/a031-040/answer-keys/AULA-032.md). A publicação do gabarito não substitui a tentativa independente.
