# Aula 015 — SSRF: quem escolhe a conexão do servidor?

**Trilha:** Web/AppSec Fundamentals · **Profundidade:** profunda · **Tempo:** 70–90 min.  
Prática: Node.js 24, terminal e dois servidores fictícios iniciados automaticamente em loopback. Nenhuma conta cloud, destino externo ou credencial real é necessária.

## O recurso legítimo e a fronteira de confiança

Um portal mostra uma prévia de um catálogo. No funcionamento esperado, a aplicação recebe o identificador `catalogo`, consulta uma origem aprovada e devolve o texto público. Se a API aceitar uma URL arbitrária e executar `fetch(url)`, quem controla a entrada passa a influenciar conexões feitas com a posição de rede do servidor.

O navegador do usuário pode não alcançar um serviço interno, mas o backend pode. A vulnerabilidade SSRF ocorre quando essa capacidade de conexão é usada fora do contrato autorizado. O efeito depende do destino: leitura de dados, acionamento de ações, uso de credenciais automáticas ou interação com serviços que confiam na rede de origem. Uma resposta com status 500 não prova nenhum desses impactos.

O laboratório histórico validava somente `hostname` antes do `fetch`. Isso é uma parte possível da política, mas não resolve mudança de destino por redirect, resolução DNS, portas e protocolos. Agora isolamos uma falha específica: **a URL inicial é permitida, mas sua resposta manda o cliente HTTP visitar outra origem**.

## O que acontece entre a string e a conexão

O processamento contém decisões diferentes:

1. **Interpretar:** o parser separa esquema, host, porta, caminho, query e credenciais. Comparar strings soltas pode produzir uma política diferente do parser que fará a conexão.
2. **Autorizar o destino lógico:** o recurso é realmente necessário? O usuário deveria controlar uma URL ou apenas um ID?
3. **Resolver e conectar:** nomes podem gerar endereços IPv4/IPv6. A decisão de rede precisa corresponder ao endereço efetivamente usado na conexão.
4. **Processar a resposta:** um 302/307/308 pode mudar o destino. Um cliente que segue redirecionamentos automaticamente inicia outra requisição.
5. **Limitar recursos:** tempo de conexão/leitura, tamanho do corpo, concorrência e número de saltos são limites distintos.
6. **Entregar o resultado:** erro detalhado, corpo e headers upstream podem expor informações que a funcionalidade não precisa revelar.

Uma allowlist feita com o parser correto é preferível a procurar palavras proibidas. Porém, uma lista de nomes não substitui a política de resolução e conexão. Separar um `dns.lookup` da chamada que resolve novamente pode criar uma janela entre checagem e uso. Em sistemas que realmente precisam aceitar URLs externas, use uma camada de saída projetada e testada para essa fronteira; não copie uma regex como solução universal.

O exercício evita esse problema escolhendo origens numéricas fixas criadas pelo próprio processo. Isso permite observar redirecionamento sem fingir que o lab implementou defesa DNS completa. [OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html).

## Exemplo resolvido: uma origem autorizada muda o destino

Dois serviços HTTP locais usam portas aleatórias:

- **Source**, uma origem pública simulada: `/public` devolve `CATALOGO_PUBLICO`; `/jump` devolve 302 para o outro serviço.
- **Internal**, uma origem interna simulada: devolve `DADO_INTERNO_FICTICIO` e incrementa um contador por requisição.

“Pública” e “interna” descrevem papéis lógicos do exercício. Ambos são loopback; não há internet ou rede empresarial envolvida.

O caminho vulnerável valida a origem inicial e deixa `fetch` seguir o redirect:

```js
async function legacyPreview(url) {
  if (new URL(url).origin !== source.origin) {
    throw new Error('ORIGEM_INICIAL_REJEITADA');
  }
  return (await fetch(url, { signal: AbortSignal.timeout(2000) })).text();
}
```

Ao passar `source.origin + '/jump'`, a comparação é verdadeira: a primeira origem está permitida. A resposta 302 é então processada pelo cliente, que visita `internal.origin + '/private'`. O corpo final já veio de outra origem. A autorização original não foi reaplicada automaticamente ao segundo salto.

A evidência é composta: o retorno contém o marcador interno **e** o contador do serviço interno aumentou. Um simples erro ou uma diferença de tempo seria evidência mais fraca e exigiria investigação adicional.

## Correção do contrato: IDs e redirecionamento fechado

Para esta funcionalidade, não há necessidade de aceitar URLs. O usuário escolhe um recurso de catálogo administrado pelo serviço:

```js
const catalog = new Map([
  ['catalogo', source.origin + '/public'],
  ['redirecionamento-teste', source.origin + '/jump']
]);

async function fixedPreview(resourceId) {
  const destination = catalog.get(resourceId);
  if (!destination) throw new Error('RECURSO_REJEITADO');
  const response = await fetch(destination, {
    redirect: 'manual',
    signal: AbortSignal.timeout(2000)
  });
  if (response.status >= 300 && response.status < 400) {
    throw new Error('REDIRECT_REJEITADO');
  }
  if (!response.ok) throw new Error(`UPSTREAM_${response.status}`);
  return response.text();
}
```

O usuário não fornece esquema, host, porta ou credenciais. O catálogo contém um redirect proposital para o teste negativo, e a função o rejeita antes de seguir. `redirect: 'manual'` não rejeita por si só: o código precisa verificar o status. Na produção, o catálogo também precisa ser administrado por uma fronteira confiável; transferir sua edição ao mesmo usuário recolocaria o problema.

O corpo do lab é pequeno e controlado. Em produção, consumir `response.text()` sem limite de bytes é uma lacuna de disponibilidade. Um timeout total não substitui o limite de tamanho. Proxies de saída e políticas de rede devem restringir o que esse componente realmente precisa alcançar.

## Laboratório executável e resultado observável

```sh
cd public/course-labs/phase16-web-p0
npm ci
node ssrf.mjs
node --test --test-name-pattern='SSRF' web.test.mjs
```

O programa cria os serviços, executa os casos e encerra os listeners. Saída esperada:

```text
happy: 'CATALOGO_PUBLICO'
legacy: 'DADO_INTERNO_FICTICIO'
redirectDenied: true
arbitraryDenied: true
internalHits: 1
internalHitsAfterFix: 0
```

Leia o resultado em ordem: o caso legítimo funciona; o caminho antigo acessa o serviço interno uma vez; o caminho corrigido recusa tanto o redirect quanto uma URL oferecida no lugar do ID; nenhuma nova conexão interna acontece nessa etapa. `internalHits` permanecer em 1 não significa que a correção falhou: esse acesso pertence à reprodução antiga. O delta após a correção é a medição relevante.

O teste exige os marcadores e o delta, não apenas ausência de exceção. Execute em seu computador e preserve comando, versão do Node e saída. Portas aleatórias e tempos não precisam ser idênticos entre execuções.

### Checkpoints de raciocínio

Antes de rodar, preveja: por que o antigo não bloqueia `/jump`, se checa uma allowlist? Depois, responda sem olhar o código: quem iniciou a segunda conexão? O cliente HTTP do servidor, após interpretar Location. Por que bloquear apenas respostas que contenham “interno” seria tarde demais? A conexão e seu eventual efeito já ocorreram.

### Exercício parcialmente resolvido

Um colega escreveu `const response = await fetch(destination, { redirect: 'manual' }); return response.text();`. Complete o bloco entre fetch e retorno para recusar mudança de destino. Gabarito: detectar status 300–399 e lançar `REDIRECT_REJEITADO`. Explique o que continua ausente: timeout, validação de status de sucesso e limites de corpo, além da política que selecionou `destination`.

### Prática independente

Na sua cópia de `ssrf.mjs`, acrescente ao serviço Source `/gone`, que devolve 404, e um ID confiável `ausente` no catálogo. Execute o caminho corrigido com esse ID. Espere `UPSTREAM_404`, sem aumento do contador interno. Depois altere somente `/jump` para 307 e repita: a rejeição deve continuar. Esses testes exercitam falhas distintas sem trocar o destino por sistemas externos.

## Detecção: correlação de entrada, saída e destino

Um serviço de prévias deve registrar ID solicitado, decisão de política, destino aprovado, status upstream, duração e bytes recebidos; use um identificador de correlação. Não registre credenciais embutidas em URLs, tokens de query ou corpos sensíveis.

No ambiente real, observe tentativas de usar a funcionalidade fora do catálogo, redirecionamentos recusados, conexões a destinos fora do perfil e divergências entre destino esperado e efetivo. A ausência de corpo interno na resposta não prova ausência de SSRF: uma interação pode ser **blind**, observável apenas em logs do destino/rede. Não converta uma hipótese em “confirmado” só por reconhecer a tecnologia ou um banner.

O contador do lab é instrumentação de teste. Em produção, a correlação pode usar logs do cliente HTTP, proxy de saída, DNS e fluxo de rede, sempre respeitando o acesso autorizado. Nenhuma dessas fontes isolada garante cobertura completa.

## Hardening e reteste

Defina o mínimo de destinos e protocolos necessários. Prefira recursos predefinidos; restrinja redirecionamentos; faça a política de resolução acompanhar o cliente que conecta; imponha limites de tempo, bytes e concorrência; não encaminhe cookies ou Authorization recebidos pelo portal para o upstream sem um contrato explícito. Segmente o componente para não alcançar serviços administrativos que não usa.

Após corrigir, execute a mesma matriz: catálogo permitido funciona; ID desconhecido falha antes da conexão; redirect falha sem salto; 404 é tratado; destino interno não recebe novas chamadas. Para um produto com URLs gerais, acrescente casos controlados IPv4/IPv6, resolução e mudança de endereço, sem afirmar que esta implementação de catálogo já os cobre.

| Sintoma | Explicação provável | Ação específica |
|---|---|---|
| `fetch is not defined` | Node antigo | Use a versão 24 do lab |
| Retorno antigo já é `REDIRECT_REJEITADO` | Você chamou o caminho corrigido | Confira o caso executado antes de concluir que não reproduz |
| Contador interno sobe no corrigido | Redirect ainda seguido ou catálogo alterado | Revise `redirect: 'manual'` e compare delta entre etapas |
| `internalHits` vale 1 ao final | Reprodução antiga já o incrementou | Leia `internalHitsAfterFix`, esperado zero |
| Timeout em tudo | Listener não iniciou ou recurso local indisponível | Confirme erro de bind/execução; não troque por IP público |

## Desafio final

Você precisa adicionar imagens de três provedores parceiros. Proponha um contrato que continue usando IDs e versões de recurso, com catálogo administrativo, limite de 1 MiB, timeout, validação de tipo e observabilidade. Liste quais condições geram rejeição antes e depois da conexão. Critério: a função de prévia não se torna um cliente HTTP arbitrário, e um teste negativo deve conferir que o destino proibido recebeu zero chamadas.

## Quiz e flashcards

1. A URL permitida devolve 302 para outra origem. Por que a checagem inicial pode ser insuficiente? A) A allowlist avalia somente a extensão do corpo final. B) Um 302 garante automaticamente que a nova origem é equivalente à inicial. C) O cliente pode iniciar outra conexão sem repetir a política. D) Verificar apenas o status 200 final também comprova autorização de todos os saltos. **C:** a política foi aplicada à primeira conexão, não ao salto.
2. Qual par de evidências demonstra o caso deste lab? A) Marcador interno e contador do serviço interno incrementado. B) Só um 500 após a requisição. C) Só latência maior que a do catálogo. D) A URL inicial ter passado na allowlist. **A:** conecta resultado e acesso ao destino controlado.
3. `internalHits` é 1 e o delta corrigido é 0. O que conclui? A) A defesa falhou necessariamente. B) A reprodução antiga acessou o destino; o reteste não criou novo acesso. C) Os dois caminhos acessaram uma vez. D) O contador prova segurança de todo o DNS. **B:** o delta distingue as etapas.
4. O que `redirect: 'manual'` garante sozinho? A) Só hosts públicos serão usados. B) O corpo tem tamanho limitado. C) Toda resposta será 200. D) O cliente não seguirá automaticamente o redirecionamento; o código ainda deve tratar o status. **D:** as demais garantias pertencem a outros controles.

**Flashcards:** Onde nasce a requisição SSRF? → No componente servidor que processa a entrada influenciada pelo cliente. URL inicial permitida basta? → Não se novos destinos podem surgir sem a mesma política. O que prova ausência de novo salto no lab? → Delta zero no contador interno durante o caminho corrigido. Por que IDs ajudam? → O serviço mantém autoridade sobre a URL completa. Timeout limita bytes? → Não; tamanho e tempo exigem limites próprios. Um erro 500 confirma SSRF? → Não; é preciso evidência da conexão e de seu efeito no escopo.
