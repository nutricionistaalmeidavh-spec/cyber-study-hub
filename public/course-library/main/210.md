# Aula 210 — Threat Modeling do laboratório

**Trilha:** Projeto final / Capstone  
**Revisão:** A técnico-editorial assistida por IA (não nota de aluno)  
**Tempo sugerido:** 60–100 minutos  
**Ambiente obrigatório:** Node.js 22+, laboratório sintético local R$ 0, sem conta externa.

## 1. Situação realista e ligação com o roadmap

No laboratório final, Alice acessa app web, retriever RAG fake e tool de notas. Antes de testar, identifique ativos, fluxos de dados e fronteiras de confiança, com proprietário de controle e hipótese negativa por fluxo.

Aula 209 é recomendada, nunca bloqueante.

**Ao concluir**, você será capaz de identificar o controle que tem autoridade, prever um caso permitido, negar uma variação adversarial segura, manter o caso permitido após a defesa e apresentar evidências sem alegar que a fixture é um sistema real.

## 2. Fundamentos que explicam a causa — não apenas nomes

**Fronteira de confiança:** Ameaça não é uma lista de buzzwords: é hipótese sobre ativo e fluxo. Para cada fronteira, descreva ator, dado, precondição, controle no destino, impacto e evidência esperada. STRIDE pode auxiliar como checklist.

**Falha que queremos reconhecer:** Fluxo user→retriever sem rótulo de autenticação, tool sem hipótese de ameaça ou mitigação sem teste negativo.

**Correção causal (onde o controle realmente atua):** THREAT_MODEL.md com DFD, matriz de risco/controle, dono e teste por destino; revisão estrutural é apenas gate preliminar.

```text
ator e contexto confiável ──► orquestrador / dados não confiáveis
                                       │
                                       ▼
                          política / validação determinística
                           │                        │
                           ▼                        ▼
                        RECUSAR                ação mock permitida
                           └──────── log mínimo ────┘
                                        │
                                        ▼
                           evidência / reteste do positivo
```

Regra operacional: o LLM pode propor, mas não fornecer a sua própria identidade, conceder permissão de conta, transformar conteúdo RAG em tool call, validar hash de um arquivo não recebido ou provar que aprovou uma operação humana.

## 3. Exemplo técnico completo, local e previsível

**Passo 1.** Instale apenas Node.js 22+ (ou use o que já tem). Não é necessário instalar npm packages, login ou API key.

**Passo 2.** Na raiz do projeto, inicie `node` para abrir o REPL e cole o JavaScript abaixo. Se preferir, salve como `exemplo-210.mjs` na raiz e use `node exemplo-210.mjs`.

```js
import {reviewThreatModel} from './public/course-labs/a201-210/models.mjs';
const assets=['retriever','tool'];
const flows=[{from:'user',to:'retriever',trustBoundary:'auth'},{from:'retriever',to:'tool',trustBoundary:'policy'}];
const threats=[{asset:'retriever',control:'ACL',negativeTest:'cross-tenant',owner:'backend'},
{asset:'tool',control:'approval',negativeTest:'write-denied',owner:'runtime'}];
console.log(reviewThreatModel({assets,flows,threats}));
```

**Passo 3.** Antes de rodar, preveja as decisões do contrato: 

| Variação de entrada | Saída esperada | Justificativa causal |
| --- | --- | --- |
| Caso 1 | `MODEL_READY_FOR_REVIEW` | Ativos, fluxos e provas mapeados. |
| Caso 2 | `FLOW_UNMODELED` | Fluxo sem fronteira declarada. |
| Caso 3 | `UNCOVERED_ASSET` | Componente sem ameaça/controle. |
| Caso 4 | `CONTROL_WITHOUT_EVIDENCE` | Mitigação declarada sem teste negativo. |

O exemplo é mínimo para mostrar entrada e oráculo; o teste completo abaixo cobre esses cenários com assertions, incluindo bloqueios que não aparecem no snippet simplificado.

## 4. Laboratório guiado (não exige IA real)

**Arquivos:** [guia local](/course-labs/a201-210/README.md), [modelo de decisão](/course-labs/a201-210/models.mjs), [testes automatizados](/course-labs/a201-210/lab.test.mjs).

```bash
node --test public/course-labs/a201-210/lab.test.mjs
```

O teste **210** é obrigatório. Ele é um contrato de decisão em memória, não uma aplicação operacional.

1. **Baseline:** Desenhe DFD com ator, frontend, backend, retriever e tool; identifique trust boundaries.
2. **Variação negativa:** Produza THREAT_MODEL.md com matriz ativo, origem/destino, ameaça, impacto, controle, dono, negativo e evidência.
3. **Observação:** Rode 210 removendo fronteira e ameaça da tool; observe recusas.
4. **Correção e reteste:** Priorize duas hipóteses e forneça ao passo seguinte do capstone, mantendo o escopo aprovado em 209.

Atenção a reteste duplo: **negação da ação indevida + manutenção da ação autorizada**. Não é suficiente negar tudo, nem confiar que a geração de texto pareça correta.

## 5. Como documentar evidência e implementar defesa

Crie `EVIDENCIAS-210.md` com entrada sintética, ator, ativo, contexto, versão do modelo de decisão, esperado, observado, hipótese, componente que decidiu, controle proposto, reteste e limites. Exemplo da estrutura:

```text
run_id: aula-210-local-01
asset: recurso fictício
actor: identidade de fixture
expected: decisão prevista
observed: resultado do teste Node
evidence: comando e saída (sem segredos)
root_cause: fronteira de confiança cruzada
fix: regra no componente com autoridade real
retest: bloqueio adversarial + caso permitido
limitation: fixture in-memory, não produto auditado
```

**Visão defensiva:** THREAT_MODEL.md com DFD, matriz de risco/controle, dono e teste por destino; revisão estrutural é apenas gate preliminar.

**Detecção:** registre request ID, identidade fictícia, recurso e decisão, sem prompt completo, segredo, dados reais ou texto privado. Na implementação real, inclua logger com retenção/segurança apropriadas e revisão de autorização antes de persistir eventos.

**Stop condition:** teste apenas ambientes próprios, intencionalmente vulneráveis ou autorizados. Pare quando a hipótese estiver comprovada. Não aumente o impacto para «demonstrar melhor».

## 6. Avaliação de transferência — faça antes de abrir as respostas

Responda num segundo cenário que use **outros IDs fictícios** e uma permissão diferente; não copie apenas a saída do snippet.

1. Ativo e fronteira são a mesma coisa?
2. O que o DFD registra?
3. Qual teste negativo protege a tool?
4. Quando a matriz está incompleta?
5. Qual a conexão com 209?

**Desafio:** formule um sexto teste negativo que altere só uma variável, declare saída esperada e explique qual componente deve impedir o abuso. Depois formule um teste positivo para não regredir.

**Rubrica (100 pontos):** conceito/fronteira 30; causa/controle 20; teste negativo 20; reteste funcional 20; limites/ética 10. Meta 80/100, sem ação fora do escopo. O gabarito fica separado para que seja possível avaliar sem spoiler: [Gabarito AULA-210](/course-labs/a201-210/answer-keys/AULA-210.md).

## 7. Acesso e limites de validade

**Núcleo obrigatório R$ 0:** Node.js 22, textos markdown, fixtures de decisão, testes Node; toda a atividade roda offline depois de obter os arquivos.

**Extensão optativa:** Acrescente matriz de riscos STRIDE com severidade justificada, sem pontuação inventada; não execute ataques em alvos de terceiros.

Este contrato não comprova segurança operacional de LLMs reais, pipelines RAG com embeddings, banco/vetores de produção, assinaturas, credenciais/JWT, aprovação humana de verdade ou aprendizado validado com estudantes. A classificação A é uma **revisão editorial assistida por IA**, condicionada à QA da branch e sem ensaio humano.

**Leitura de referência:** https://owasp.org/www-community/Threat_Modeling_Process. Projeto OWASP GenAI 2026: https://genai.owasp.org/resource/owasp-genai-llm-top-10-2026/. Não confunda a taxonomia da edição 2025 com a edição 2026.


## 8. Artefato obrigatório do capstone — modelo preenchível
### THREAT_MODEL.md
```md
# Diagrama de fluxo
Alice/Bob → [auth] → retriever → [tool policy] → mock nota
# Matriz de hipóteses
| ativo | origem | fronteira | hipótese | controle | dono | negativo |
| retriever | user | auth | cross-tenant | ACL pre-RAG | backend | leitura t2 negada |
| tool | retriever | policy | write indevida | aprovação vinculada | runtime | write sem approval negada |
```
**Gate para avançar:** cada ativo com fluxo, hipótese de abuso, controle e reteste explícitos. Testes não substituem autorização definida na aula 209.
