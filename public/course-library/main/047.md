## 1. Conexão com a Aula 46

Na Aula 46 estudamos **Web Cache Poisoning**: uma entrada influencia uma resposta que é armazenada e depois entregue a outros usuários.

Agora estudamos um problema parecido, mas diferente:

> Em **Web Cache Deception**, o conteúdo sensível já existe e é legítimo. O erro é o cache interpretar aquela resposta privada como se fosse um recurso público/cacheável.

**Poisoning:** “consigo influenciar o conteúdo que será armazenado para outras pessoas.”  
**Deception:** “consigo fazer o cache armazenar uma resposta privada que nunca deveria ser compartilhada.”

## 4. O problema concreto

Imagine uma aplicação:

```text
https://app.exemplo.local/account
```

Quando Alice está autenticada, ela recebe:

```html
<h1>Olá, Alice</h1>
<p>Plano: Premium</p>
<p>E-mail: alice@exemplo.local</p>
```

Essa resposta é **personalizada e privada**.

Agora imagine que a infraestrutura use uma regra simplista:

```text
Se a URL terminar com .css, .js, .png ou .jpg:
    considerar recurso estático
    permitir cache compartilhado
```

Isso parece razoável para `/assets/app.css`, mas pode falhar se a aplicação tratar `/account/profile.css` como uma rota dinâmica de conta enquanto o cache enxergar apenas o sufixo `.css`.

```text
Cache:      “parece arquivo estático”
Aplicação:  “é uma página autenticada”
```

A vulnerabilidade nasce dessa divergência de interpretação.

---

## 5. Duas decisões que não podem ser confundidas

Um cache precisa responder a duas perguntas diferentes.

### A. Qual é a chave desta entrada?

Exemplo simplificado:

```text
GET | app.exemplo.local | /assets/app.css
```

A chave pode considerar método, host, path, query string e headers selecionados.

Isso é a **cache key**.

### B. Essa resposta pode ser armazenada e compartilhada?

A política pode considerar status, método, caminho, `Cache-Control`, `Set-Cookie`, autenticação e regras do CDN.

Isso é **cacheability**.

> Uma cache key perfeita não torna uma página privada adequada para cache compartilhado.

## 6. Fluxo normal de um asset público

```text
Navegador
   |
   | GET /assets/app.css
   v
CDN / Reverse Proxy
   |
   | MISS
   v
Origin / aplicação
   |
   | Cache-Control: public, max-age=3600
   v
CDN armazena
   |
   | próxima requisição = HIT
   v
Navegador
```

Esse fluxo é desejável porque o CSS é igual para todos.

---

## 7. Fluxo perigoso de Cache Deception

Alice solicita:

```http
GET /account/profile.css HTTP/1.1
Cookie: session=alice
```

A aplicação pode interpretar `/account/profile.css` como uma rota dinâmica de `/account/*` e retornar conteúdo privado de Alice.

O cache, porém, pode interpretar `profile.css` como asset estático.

```text
Alice
  |
  | GET /account/profile.css
  v
Cache MISS
  |
  v
Origin retorna “Olá Alice”
  |
  v
Cache armazena a resposta
  |
  | mesma chave
  v
Bob
  |
  | GET /account/profile.css
  v
Cache HIT
  |
  v
“Olá Alice”
```

O backend não necessariamente autorizou Bob como Alice. O segundo request pode nem chegar ao backend.

---

## 8. Poisoning × Deception

| Pergunta | Cache Poisoning | Cache Deception |
|---|---|---|
| O que é armazenado? | conteúdo influenciado/alterado | conteúdo privado legítimo |
| Erro central | entrada relevante fora da cache key ou tratamento incorreto | resposta privada considerada cacheável |
| Foco | integridade do cache | confidencialidade |
| Mentalidade | “faço o cache guardar minha variação” | “faço o cache guardar minha página privada” |
| Correção típica | cache key + normalização + controle de entradas | política explícita de cacheabilidade + roteamento coerente |

---

## 9. Headers importantes

### `Cache-Control: private`

A resposta não deve ser reutilizada por um cache compartilhado.

### `Cache-Control: no-store`

A resposta não deve ser armazenada.

### `Cache-Control: public`

A resposta pode ser considerada para cache compartilhado quando as demais regras permitirem.

### `Vary`

Altera quais dimensões participam da seleção de uma representação. É útil, mas não substitui uma decisão correta sobre **se** aquela resposta deveria ser compartilhada.

---

## 10. Path confusion

**Path confusion** é a divergência entre o significado dado ao mesmo caminho por componentes diferentes.

```text
Aplicação:
/account/qualquer-coisa
→ rota de conta

Cache:
termina em .css
→ asset
```

A URL é a mesma; a semântica não.

---

## 11. Resposta privada correta

```http
HTTP/1.1 200 OK
Content-Type: text/html
Cache-Control: private, no-store
```

O ponto principal é: essa representação não deve virar objeto público compartilhado.

## 12. Asset público correto

```http
HTTP/1.1 200 OK
Content-Type: text/css
Cache-Control: public, max-age=31536000, immutable
```

Isso faz sentido para algo como `/assets/app.3f7a.css`.

---

## 13. Anti-padrão

```js
if (pathname.endsWith('.css') ||
    pathname.endsWith('.js') ||
    pathname.endsWith('.png')) {
  cache(response);
}
```

A extensão da URL está sendo tratada como **prova de que o conteúdo é público**. Mas a URL é apenas entrada de roteamento.

---

## 14. Política defensiva: decidir antes de ler e antes de guardar

O contrato deste cache é restrito: apenas GET anônimo em `/assets/`, resposta 200 com `public` e `max-age` explícitos, sem `Set-Cookie`, `Vary` ou diretivas privadas. Requisições com Cookie, Authorization ou X-Lab-User fazem BYPASS **antes de consultar uma entrada existente**. Guardar corretamente e selecionar incorretamente ainda pode misturar contextos.

Não basta testar o armazenamento com cache vazio. Primeiro aqueça `/assets/app.css` como anônimo; depois envie a mesma URL com identidade. A resposta deve fazer BYPASS, apesar de já existir um objeto cacheado. A regra de namespace sozinha não demonstra esse comportamento.

## 15. Código anotado e tempo de vida

O arquivo executado é `cache-policy.mjs`:

```js
// Política propositalmente restrita: GET público, sem Vary nem identidade.
export function isAnonymousAsset(req) {
  const h = req.headers;
  return req.method === 'GET' && req.path.startsWith('/assets/') &&
    !h['x-lab-user'] && !h.cookie && !h.authorization;
}
export function storageTtl(req, response) {
  if (!isAnonymousAsset(req) || response.status !== 200) return 0;
  if (response.headers.has('set-cookie') || response.headers.has('vary')) return 0;
  const directives = (response.headers.get('cache-control') || '').toLowerCase().split(',').map(x => x.trim());
  if (!directives.includes('public') || directives.some(x => ['private','no-store','no-cache'].includes(x.split('=')[0]))) return 0;
  const maxAge = directives.find(x => /^max-age=\d+$/.test(x));
  return maxAge ? Math.min(Number(maxAge.split('=')[1]), 3600) * 1000 : 0;
}
export class TimedCache {
  constructor(now = Date.now) { this.now = now; this.entries = new Map(); }
  get(key) {
    const entry = this.entries.get(key);
    if (!entry) return null;
    if (entry.expires <= this.now()) { this.entries.delete(key); return null; }
    return { ...entry, age: Math.floor((this.now() - entry.storedAt) / 1000) };
  }
  put(key, value, ttl) {
    if (ttl <= 0) return;
    if (this.entries.size >= 100) this.entries.delete(this.entries.keys().next().value);
    this.entries.set(key, { ...value, storedAt: this.now(), expires: this.now() + ttl });
  }
}
```

`isAnonymousAsset` aplica o contrato da requisição. `storageTtl` examina a resposta e retorna milissegundos de armazenamento, ou zero para recusa. A classe recebe um relógio para que o teste avance no tempo sem esperar uma hora; entradas expiradas são removidas no acesso. `Age` relata segundos desde o armazenamento nesta simulação; o lab limita a 100 entradas e a TTL de uma hora.

Esta é uma política deliberadamente menor que um cache HTTP completo. Não implementa revalidação, `s-maxage`, armazenamento persistente, variantes Vary ou todo o cálculo de idade da RFC. `no-cache` é recusado por falta de revalidação, embora não signifique universalmente “proibido armazenar”. Campos/diretivas desconhecidos não autorizam armazenamento por si. Não publique estes proxies didáticos como CDN.

### Exercício parcialmente resolvido

Uma implementação consulta `cache.get(key)` e só depois examina Cookie. Mova a decisão para antes da leitura: `const saved = isAnonymousAsset(req) ? cache.get(key) : null;`. Explique por que isso muda o resultado quando o cache já está aquecido. Gabarito: uma requisição autenticada deixa de poder reutilizar um objeto antes que sua elegibilidade seja conhecida.

### Prática independente

Classifique `/account`, `/api/me`, `/assets/app.css`, `/public/avatar/42` e `/reports/export.csv`. Neste lab, apenas `/assets/app.css` sem identidade pode entrar, condicionado à resposta. As demais rotas não estão no namespace autorizado. Em um produto real, avatar/export exigem descobrir se o recurso é público ou personalizado antes de ampliar a política; o nome não basta.

## Teste de contexto com cache aquecido e TTL

Depois do MISS/HIT público, execute:

```sh
curl -i -H 'Cookie: session=ficticia' http://127.0.0.1:4001/assets/app.css
curl -i -H 'Authorization: Bearer ficticio' http://127.0.0.1:4001/assets/app.css
npm test
```

As duas requisições fazem BYPASS. Cookie e Authorization participam da recusa de cache; somente X-Lab-User simula a identidade no origin. O teste automático inicia três servidores em portas livres, exige Alice/MISS → Bob/HIT com corpo de Alice no antigo, isolamento no corrigido, público MISS/HIT, três headers de contexto com BYPASS e 404 sem armazenamento. Outro teste avança o relógio: Age=1 após um segundo e ausência da entrada na expiração; verifica `private`, `Set-Cookie` e `Vary`.

Limites: não testa CDN comercial, cache do navegador ou todas as regras HTTP. Ao terminar, Ctrl+C nos servidores manuais limpa seus Maps em memória; não existe diretório de cache a apagar.

# 27. Como detectar em sistemas próprios

Pergunte:

1. quais rotas retornam conteúdo personalizado?
2. elas enviam `Cache-Control` coerente?
3. existe CDN/reverse proxy?
4. a política é baseada apenas em extensão?
5. backend e proxy interpretam paths da mesma maneira?
6. há rotas curingas como `/account/*`?
7. respostas com `Set-Cookie` podem ser armazenadas?
8. requests autenticados podem produzir HIT compartilhado?
9. há logs de HIT/MISS/BYPASS?
10. existe teste automatizado com usuários diferentes?

### Sinais úteis

- rota de conta/perfil aparecendo como `HIT` compartilhado;
- `Age` aumentando em resposta personalizada;
- `private`/`no-store` sendo ignorado;
- cache HIT sem request correspondente no log do origin;
- usuários diferentes recebendo a mesma representação privada;
- path dinâmico com sufixo típico de asset.

Exemplo de raciocínio:

```text
CDN log:  /account/profile.css → HIT
Origin:   nenhum request correspondente
Resposta: conteúdo personalizado
Hipótese: objeto privado armazenado em cache compartilhado
```

---

# 28. Como corrigir

## Controle 1 — privado por padrão

Use políticas explícitas para conteúdo sensível, por exemplo `private` e/ou `no-store` conforme a necessidade.

## Controle 2 — assets em namespaces públicos

Prefira `/assets/`, `/static/` e `/public/` em vez de inferir publicidade apenas por extensão.

## Controle 3 — CDN respeita o origin

Evite regras que sobrescrevam indiscriminadamente a política da aplicação.

## Controle 4 — autenticação participa da política

Resposta produzida sob contexto autenticado merece tratamento conservador.

## Controle 5 — normalize roteamento

Proxy e aplicação devem interpretar o path de forma consistente.

## Controle 6 — teste com dois usuários

```text
Alice → resposta de Alice
Bob   → resposta de Bob
```

Nunca:

```text
Alice → resposta de Alice
Bob   → HIT com resposta de Alice
```

# 29. Erros comuns

### “Basta colocar Vary: Cookie”
Não necessariamente. `Vary` altera a seleção da representação, mas conteúdo altamente sensível pode simplesmente não dever entrar em cache compartilhado.

### “HTTPS resolve”
Não. HTTPS protege o transporte, não a política de cache.

### “UUID evita isso”
Não. O problema não depende de IDs previsíveis.

### “É igual a IDOR”
Não. Em IDOR/BOLA, o backend toma uma decisão incorreta de autorização. Em cache deception, um cache intermediário pode responder sem que o backend processe a segunda solicitação.

### “Basta bloquear .css”
Não. `.css` é só um exemplo. A correção é alinhar roteamento, sensibilidade e política de cache.

# 30. Troubleshooting do laboratório

### `EADDRINUSE`
Há outro processo usando a porta. Encerre-o ou altere a porta.

### `curl` indisponível
No PowerShell você pode usar `Invoke-WebRequest`.

### Bob recebe Bob no proxy vulnerável

### Origin não responde
Teste primeiro `http://127.0.0.1:3000` antes de usar o proxy.

# 33. Quiz

### 1. Qual definição descreve melhor Web Cache Deception?
A. Alterar um header fora da cache key para modificar respostas futuras.  
B. Fazer conteúdo privado ser armazenado e reutilizado como se fosse público/cacheável.  
C. Executar código por meio de template.  
D. Acessar objeto alheio diretamente por ID.  

**Resposta: B.** O foco é exposição de uma resposta privada legítima devido a uma decisão incorreta de cacheabilidade/roteamento.

### 2. Qual é a principal diferença para Cache Poisoning?
A. Deception só existe em HTTP/2.  
B. Poisoning exige autenticação.  
C. Poisoning foca em influenciar conteúdo armazenado; deception em armazenar indevidamente conteúdo privado.  
D. Não existe diferença.  

**Resposta: C.**

### 3. Por que `*.css => cache` pode ser perigoso?
A. CSS sempre contém senha.  
B. A aplicação pode tratar um path terminado em `.css` como rota dinâmica/autenticada.  
C. Navegadores não suportam CSS cacheado.  
D. Todo CSS deveria usar POST.  

**Resposta: B.**

### 4. Qual política é mais coerente para uma página de conta altamente sensível?
A. `public, max-age=86400`.  
B. Ignorar Cache-Control.  
C. Política privada/no-store conforme a necessidade.  
D. Remover HTTPS.  

**Resposta: C.**

### 5. Qual reteste demonstra melhor a correção?
A. Mesmo request duas vezes pelo mesmo usuário.  
B. Só conferir status 200.  
C. Usuários diferentes e prova de que conteúdo privado não vira HIT compartilhado.  
D. Trocar User-Agent.  

**Resposta: C.**

### 6. Um `HIT` em rota autenticada é sempre vulnerabilidade?
A. Sim.  
B. Não necessariamente; é preciso considerar arquitetura, tipo de cache, chave e conteúdo.  
C. Apenas no Chrome.  
D. Somente com JWT.  

**Resposta: B.**

# 34. Flashcards

1. **Web Cache Deception** → armazenamento indevido de conteúdo privado como objeto reutilizável por cache compartilhado.
2. **Cacheability** → decisão sobre se uma resposta pode ser armazenada/reutilizada.
3. **Cache key** → atributos usados para identificar uma entrada do cache.
4. **private** → resposta não deve ser reutilizada por cache compartilhado.
5. **no-store** → resposta não deve ser armazenada.
6. **Poisoning × Deception** → poisoning influencia conteúdo; deception expõe conteúdo privado armazenado indevidamente.
7. **Checkpoint de correção** → usuários distintos recebem apenas seus próprios conteúdos; conteúdo privado não aparece como HIT compartilhado indevido.
