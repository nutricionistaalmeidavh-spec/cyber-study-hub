## 2. Visão geral

Command injection ocorre quando input influencia comandos do sistema operacional executados pela aplicação.

## 3. Aprofundamento: o que realmente está acontecendo

Command injection é, antes de tudo, um erro de fronteira entre dado e linguagem de comando. Quando o objetivo pode ser realizado por API ou por `execFile/spawn` com argumentos separados, passar por um shell é complexidade e risco desnecessários.

Command injection aparece quando texto do usuário é concatenado em uma string interpretada por um shell. A defesa mais forte é não passar pelo shell quando a tarefa pode ser feita por uma API específica.

Ao estudar, tente sempre localizar cinco elementos:

```text
entrada/estado
→ componente que interpreta
→ decisão
→ efeito observável
→ controle que quebra a cadeia
```

## 5. Conceitos fundamentais

### 1. Shell
Interpretador de comandos que amplia risco quando recebe strings concatenadas.
### 2. Argument injection
Abuso de parâmetros mesmo sem metacaracteres de shell.
### 3. Allowlist
Validação por conjunto fechado de valores permitidos.
### 4. Process API
API que executa binário e argumentos separadamente, reduzindo interpretação pelo shell.

## 6. Fluxo técnico

1. **Aplicação recebe uma entrada**
2. **Código monta um comando de sistema**
3. **Shell interpreta metacaracteres e argumentos**
4. **Processo filho executa com os privilégios da aplicação**
5. **APIs sem shell e allowlists reduzem o risco**

## 7. Exemplo técnico — execFile com argumentos separados

```js
import { execFile } from "node:child_process";

const allowed = new Set(["example.com", "localhost"]);

function pingHost(host) {
  if (!allowed.has(host)) throw new Error("Host não permitido");

  execFile("ping", ["-c", "1", host], { timeout: 3000 }, (err, stdout) => {
    if (err) return;
    console.log(stdout);
  });
}
```

### Como ler o exemplo

Não concatene a entrada em uma string de shell. Mesmo assim, valide o conjunto de valores aceitos.

## 8. Por que a vulnerabilidade/mecanismo acontece

Command injection aparece quando texto do usuário é concatenado em uma string interpretada por um shell. A defesa mais forte é não passar pelo shell quando a tarefa pode ser feita por uma API específica.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 10. Como detectar

Procure processos filhos inesperados, argumentos anômalos, erros de shell e execuções originadas por serviços web.

Transforme a frase acima em telemetria:

```text
quem?
onde?
qual ação?
qual recurso/destino?
qual resultado?
qual sequência temporal?
```

## 11. Como corrigir / reduzir risco

Evite shell, use APIs com argumentos separados, allowlists estritas e princípio do menor privilégio.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 18. Oficina A — Command Injection

**Objetivo mensurável:** Separar entrada do usuário, seleção de operação, executável autorizado e argumentos efetivos; defender contra injeção de shell e injeção de argumentos.

### Situação profissional e pré-requisitos

Um painel de diagnóstico aceita `action=health`. Um programador monta `sh -c "node --version " + action` embora só precise obter a versão do Node. A entrada controla sintaxe de shell e pode modificar a operação. O contrato real exige uma operação de saúde fixa, sem comando fornecido pela requisição.

Para começar, identifique o ator, o dado controlável, o componente que decide, o recurso afetado e o resultado que realmente pode ser observado. Não atribua ao laboratório funções de produção. Refaça a distinção entre hipótese, evidência e interpretação antes de qualquer mudança no controle.

### Mecanismo: acompanhe o dado até a decisão

Na versão vulnerável, uma string atravessa a fronteira de dados para a gramática do interpretador. Mesmo que `execFile` dispense shell, opções inesperadas podem mudar a semântica do binário chamado: por isso a decisão é **permitir operações**, não apenas escapar caracteres.

**Exemplo resolvido.** `plannedProcess("health")` devolve `{executable:"node", args:["--version"], shell:false}`. `plannedProcess("--inspect")` e `plannedProcess("health; echo injected")` lançam `AÇÃO_NÃO_PERMITIDA`. O laboratório *não executa* texto fornecido por usuário.

**Questão de compreensão:** em qual momento a entrada deixa de ser mero dado e passa a interferir em uma decisão? Formule uma frase citando o objeto exato, a condição de falha e a observação esperada. Não confunda a explicação de mecanismo com uma prova de exploração.

### Laboratório seguro, passo a passo

1. Use um diretório próprio e dados sintéticos. Abra o terminal na raiz do repositório; não execute em sistemas de terceiros.
2. Leia o código do módulo `/course-labs/a051-060/models.mjs` e localize **`plannedProcess`**. Para a aula 052, utilize também o laboratório original de path traversal indicado abaixo.

```sh

```

4. Escreva três observações concretas: valor/estado de entrada, resposta obtida e por que isso sustenta a hipótese. Reexecute um caso permitido para demonstrar ausência de regressão.
5. Não modifique proteções do host nem use credenciais reais. Um resultado de teste automático não substitui teste end-to-end no navegador ou revisão de integração real.

**Resultado verificável:** Uma entrada com caracteres de metacomando deve ser rejeitada **antes** de iniciar qualquer processo; uma operação legítima deve continuar disponível. `shell:false` sozinho não substitui validação das opções aceitas.

**Limites do experimento:** A demonstração só planeja chamada de processo, não prova permissões de SO, isolamento de processo, timeout ou comportamento de um executável desconhecido.

### Defesa, observabilidade e reteste

| Etapa | Evidência mínima | Interpretação permitida |
|---|---|---|
| Antes | Entrada sintética e decisão observada | O caso local exemplifica um risco; não descreve todos os ambientes |
| Controle | Regra explícita, elemento protegido e erro de rejeição | O controle bloqueia o cenário ensaiado |
| Reteste negativo | Mesmo caso de risco agora rejeitado | Não houve aceitação do caso negativo |
| Reteste positivo | Caso legítimo preservado | O controle não quebrou esse caminho funcional |

**Falha frequente:** concluir que um teste passou apenas porque não houve exceção; compare também o estado final esperado. Colete somente eventos necessários e remova identificadores sensíveis de logs. Em caso de divergência, anote plataforma, versão do Node e qual asserção falhou, em vez de ajustar a resposta para "passar".
