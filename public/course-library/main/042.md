## 2. O problema em uma frase

Insecure Deserialization surge quando dados serializados não confiáveis são reconstruídos como objetos ou tipos com poder maior do que deveriam. A defesa moderna é tratar payloads como dados validados, com schema e tipos explícitos.

## 3. O que você precisa dominar

- **1.** Não aceite tipo/classe arbitrária vinda do payload.
- **2.** Valide campos e esquema antes de criar objetos de domínio.
- **3.** Nunca confie em atributos privilegiados só porque vieram serializados.

## 5. Por que isso importa

Insecure Deserialization surge quando dados serializados não confiáveis são reconstruídos como objetos ou tipos com poder maior do que deveriam. A defesa moderna é tratar payloads como dados validados, com schema e tipos explícitos.

Na prática, segurança não depende de decorar o nome da técnica. Ela depende de localizar a fronteira de confiança, identificar o dado ou estado que muda a decisão e provar, com evidência mínima, se o controle impede o comportamento indesejado.

Os pontos-chave desta aula devem ser usados como perguntas de revisão:

- Não aceite tipo/classe arbitrária vinda do payload.
- Valide campos e esquema antes de criar objetos de domínio.
- Nunca confie em atributos privilegiados só porque vieram serializados.

## 6. Exemplo técnico — Exemplo original, agora lido como evidência

```javascript/pseudocódigo
const data = Schema.parse(JSON.parse(body));
const user = { name: data.name, email: data.email };
```

O código não é um fim: identifique entrada, decisão, estado e efeito observável.

### Equivalente didático em Portugol

```text
dados <- validarJSON(corpo)
usuario.nome <- dados.nome
usuario.email <- dados.email
```

Use o Portugol para enxergar a lógica; APIs reais de rede, banco, criptografia e SO continuam sendo estudadas na tecnologia correspondente.

## 9. Como defender / corrigir

Prefira formatos de dados simples com schema, tipos explícitos e sem construção arbitrária de objetos/classes a partir de input não confiável.

A correção deve agir sobre a causa. Evite controles cosméticos como esconder IDs, renomear rotas, desativar mensagens sem corrigir a decisão ou confiar somente no frontend.

## 10. Como detectar / investigar

Monitore erros de parsing, tipos inesperados, campos privilegiados e desserialização de objetos fora do schema.

Uma detecção útil combina:

```text
identidade/host
+ ação
+ recurso/destino
+ horário
+ resultado
+ contexto
```

## Problema e competência verificável — AULA-042 (oficina A)

**Caso inédito:** Um serviço recebe preferências JSON de um usuário e tenta aplicar um campo inesperado role=admin como se fosse configuração autorizada.

**Decisão crítica:** JSON.parse somente reconstrói dados; o risco aparece no uso posterior sem validação de esquema e no reuso de desserializadores capazes de instanciar objetos.

**Hipótese que precisa ser refutada:** campo role e chave __proto__ são rejeitados, mas theme/locale legítimos passam.

**Evidência esperada:** parsePreferences('{"theme":"dark","locale":"pt-BR"}') aceita; acrescentar role reprova.

**Competência:** explicar a causa, prever observáveis, executar teste com entrada legítima e adversarial, selecionar a defesa e declarar os limites do teste.

### Mecanismo e exemplo resolvido

1. **Estado inicial:** Um serviço recebe preferências JSON de um usuário e tenta aplicar um campo inesperado role=admin como se fosse configuração autorizada.
2. **Entrada e fronteira:** JSON.parse somente reconstrói dados; o risco aparece no uso posterior sem validação de esquema e no reuso de desserializadores capazes de instanciar objetos.
3. **Decisão:** Validar tipos, campos aceitos e privilégios após desserializar; não usar formato de objetos executáveis para dados não confiáveis.
4. **Observação:** parsePreferences('{"theme":"dark","locale":"pt-BR"}') aceita; acrescentar role reprova.
5. **Interpretação:** campo role e chave __proto__ são rejeitados, mas theme/locale legítimos passam. Não confunda a evidência de um modelo isolado com exploração ou comprovação em produto de terceiros.

### Laboratório guiado (offline, código disponível)

Pré-requisito: Node.js 22 ou superior. Sem contas, API comercial ou rede. A execução é isolada e determinística.


**Checkpoint 1 (prever):** Antes de rodar, escreva o que ocorrerá com a entrada legítima e a adversarial no caso 042.

**Checkpoint 2 (observar):** Na saída JSON procure `normal` (controle positivo) e `hostile` (controle negativo); compare os campos e diga qual condição bloqueou ou isolou o risco.

**Checkpoint 3 (corrigir e retestar):** Validar tipos, campos aceitos e privilégios após desserializar; não usar formato de objetos executáveis para dados não confiáveis. Reexecute e registre também o caso legítimo para evitar uma "correção" que só desliga a função.

**Troubleshooting:** Se o Node não reconhecer módulos ESM, confirme `node --version` (22+), execute o comando na raiz do repositório e preserve a extensão `.mjs`. Se `hostile` não for um erro, explique o isolamento de dados ou a invariância positiva esperada neste caso.

### Detecção, defesa, limites e fontes

- **O que procurar:** campo role e chave __proto__ são rejeitados, mas theme/locale legítimos passam.
- **Controle primário:** Validar tipos, campos aceitos e privilégios após desserializar; não usar formato de objetos executáveis para dados não confiáveis.
- **Controle de compatibilidade:** parsePreferences('{"theme":"dark","locale":"pt-BR"}') aceita; acrescentar role reprova.
- **Limitação honesta da evidência:** JSON estrito não reproduz gadget chains nem RCE de serializadores nativos; não tratar este teste como auditoria de bibliotecas.
- **Referência técnica para leitura crítica:** https://cheatsheetseries.owasp.org/cheatsheets/Deserialization_Cheat_Sheet.html
