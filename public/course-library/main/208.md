# Aula 208 — Defesa de Agentes e Capstone AI Security

**Trilha:** AI / LLM Security  
**Revisão:** A técnico-editorial assistida por IA (não nota de aluno)  
**Tempo sugerido:** 90–120 minutos  
**Ambiente obrigatório:** Node.js 22+, laboratório sintético local R$ 0, sem conta externa.

## 1. Situação realista e ligação com o roadmap

Um miniagente fictício consulta RAG de Alice, propõe atualizar uma nota e produz trilha mínima. O documento do usuário pode conter injeção, mas não é fonte de intenção de tool.

Aula 207 é recomendada, nunca bloqueante.

**Ao concluir**, você será capaz de identificar o controle que tem autoridade, prever um caso permitido, negar uma variação adversarial segura, manter o caso permitido após a defesa e apresentar evidências sem alegar que a fixture é um sistema real.

## 2. Fundamentos que explicam a causa — não apenas nomes

**Fronteira de confiança:** Combine recuperação com ACL, roteamento confiável, autorização de ferramenta, aprovação específica e log mínimo. O `executeCapstoneAgent` recebe proposta já autenticada; **não converte chunks em chamadas de ferramenta**.

**Falha que queremos reconhecer:** A ferramenta tenta editar n1 sem aprovação, ler doc privado de outro tenant ou usar tool `delete-all`.

**Correção causal (onde o controle realmente atua):** Policy enforcement point fora do modelo, origem não confiável preservada, allowlist de tools, autorização de tenant, aprovação independente e log sem prompt ou segredo.

```text
ator e contexto confiável ──► orquestrador / dados não confiáveis
                                       │
                                       ▼
                          política / validação determinística
                           │                        │
                           ▼                        ▼
                        RECUSAR                ação mock permitida
                           └──────── log mínimo ────┘
                                        │
                                        ▼
                           evidência / reteste do positivo
```

Regra operacional: o LLM pode propor, mas não fornecer a sua própria identidade, conceder permissão de conta, transformar conteúdo RAG em tool call, validar hash de um arquivo não recebido ou provar que aprovou uma operação humana.

## 3. Exemplo técnico completo, local e previsível

**Passo 1.** Instale apenas Node.js 22+ (ou use o que já tem). Não é necessário instalar npm packages, login ou API key.

**Passo 2.** Na raiz do projeto, salve o JavaScript abaixo no arquivo `exemplo-208.mjs` e execute `node exemplo-208.mjs`. O arquivo `.mjs` permite imports ESM; não cole `import` estático no REPL tradicional.

```js
import {executeCapstoneAgent} from './public/course-labs/a201-210/models.mjs';
const actor={id:'alice',tenant:'t1',authenticated:true,permissions:['update-note']};
const chunks=[{id:'doc1',tenant:'t1',allowedUsers:['alice'],origin:'fixture',version:'1',text:'projeto'}];
console.log(executeCapstoneAgent({actor,chunks,proposal:{tool:'update-note',args:{noteId:'n1',tenant:'t1'}}}).decision);
```

**Passo 3.** Antes de rodar, preveja as decisões do contrato: 

| Variação de entrada | Saída esperada | Justificativa causal |
| --- | --- | --- |
| Caso 1 | `APPROVAL_REQUIRED` | Agente não aprova seu próprio efeito. |
| Caso 2 | `TOOL_ALLOWED com aprovação específica` | Aprovação amarrada ao recurso. |
| Caso 3 | `UNKNOWN_TOOL` | Ferramenta não autorizada. |
| Caso 4 | `doc2 ausente do trace` | ACL antes de construir contexto. |

O exemplo é mínimo para mostrar entrada e oráculo; o teste completo abaixo cobre esses cenários com assertions, incluindo bloqueios que não aparecem no snippet simplificado.

## 4. Laboratório guiado (não exige IA real)

**Arquivos:** [guia local](/course-labs/a201-210/README.md), [modelo de decisão](/course-labs/a201-210/models.mjs), [testes automatizados](/course-labs/a201-210/lab.test.mjs).

```bash
node --test public/course-labs/a201-210/lab.test.mjs
```

O teste **208** é obrigatório. Ele é um contrato de decisão em memória, não uma aplicação operacional.

1. **Baseline:** Desenhe fluxo usuário → RAG ACL → planejador → política → mock tool → log.
2. **Variação negativa:** Execute o caso de escrita recusada e adicione aprovação sintética vinculada a n1.
3. **Observação:** Troque a tool e injete texto fake em chunk autorizado: texto permanece dado.
4. **Correção e reteste:** Entregue CAPSTONE_AI_SECURITY.md com entradas, saídas, autorizações, trace, limites e dois retestes.

Atenção a reteste duplo: **negação da ação indevida + manutenção da ação autorizada**. Não é suficiente negar tudo, nem confiar que a geração de texto pareça correta.

## 5. Como documentar evidência e implementar defesa

Crie `EVIDENCIAS-208.md` com entrada sintética, ator, ativo, contexto, versão do modelo de decisão, esperado, observado, hipótese, componente que decidiu, controle proposto, reteste e limites. Exemplo da estrutura:

```text
run_id: aula-208-local-01
asset: recurso fictício
actor: identidade de fixture
expected: decisão prevista
observed: resultado do teste Node
evidence: comando e saída (sem segredos)
root_cause: fronteira de confiança cruzada
fix: regra no componente com autoridade real
retest: bloqueio adversarial + caso permitido
limitation: fixture in-memory, não produto auditado
```

**Visão defensiva:** Policy enforcement point fora do modelo, origem não confiável preservada, allowlist de tools, autorização de tenant, aprovação independente e log sem prompt ou segredo.

**Detecção:** registre request ID, identidade fictícia, recurso e decisão, sem prompt completo, segredo, dados reais ou texto privado. Na implementação real, inclua logger com retenção/segurança apropriadas e revisão de autorização antes de persistir eventos.

**Stop condition:** teste apenas ambientes próprios, intencionalmente vulneráveis ou autorizados. Pare quando a hipótese estiver comprovada. Não aumente o impacto para «demonstrar melhor».

## 6. Avaliação de transferência — faça antes de abrir as respostas

Responda num segundo cenário que use **outros IDs fictícios** e uma permissão diferente; não copie apenas a saída do snippet.

1. Qual componente define a autoridade?
2. Por que o doc recuperado não executa tool?
3. O que é preservado na trace?
4. Qual controle evita delete-all?
5. Quais limites de uma fixture sem LLM real?

**Desafio:** formule um sexto teste negativo que altere só uma variável, declare saída esperada e explique qual componente deve impedir o abuso. Depois formule um teste positivo para não regredir.

**Rubrica (100 pontos):** conceito/fronteira 30; causa/controle 20; teste negativo 20; reteste funcional 20; limites/ética 10. Meta 80/100, sem ação fora do escopo. O gabarito fica separado para que seja possível avaliar sem spoiler: [Gabarito AULA-208](/course-labs/a201-210/answer-keys/AULA-208.md).

## 7. Acesso e limites de validade

**Núcleo obrigatório R$ 0:** Node.js 22, textos markdown, fixtures de decisão, testes Node; toda a atividade roda offline depois de obter os arquivos.

**Extensão optativa:** O pacote 208 é capstone da trilha IA; aulas 209–210 iniciam o laboratório final geral, sem exigir concluir IA antes.

Este contrato não comprova segurança operacional de LLMs reais, pipelines RAG com embeddings, banco/vetores de produção, assinaturas, credenciais/JWT, aprovação humana de verdade ou aprendizado validado com estudantes.
