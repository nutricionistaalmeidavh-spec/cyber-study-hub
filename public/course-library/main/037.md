# Aula 037 — Secure Coding

**Trilha principal:** Pentest & Secure Development · **Duração sugerida:** 60–80 min · **Estado:** aprofundamento editorial A (IA) sujeito a registro SHA-256.  
**Ambiente:** Node.js 22+, sem Docker obrigatório, sem assinatura ou API paga. Testes só com dados fictícios, em memória ou serviço `127.0.0.1` criado pela suíte.

> Só execute técnicas ativas em ativos próprios ou autorizados explicitamente. O resultado de uma fixture local não se transfere automaticamente para sistemas externos. As atividades não requerem credenciais reais.

## Problema e objetivo mensurável

Em um app universitário, `PATCH /me` recebe `{name:'Ana Maria', role:'admin'}`. A implementação antiga mistura campos do body com o modelo do usuário. A versão segura mantém `role='reader'` porque apenas o nome é autogerenciado.

**Competência observável:** Refatorar atualização de perfil para que autorização e validação permaneçam no servidor. Para demonstrá-la, o estudante deve prever a decisão, executar os casos positivos e negativos e explicar evidências, hipóteses alternativas e limites da simulação. Não basta nomear ferramentas.

## Fundamentos e pré-requisitos recomendados

Os pré-requisitos são recomendações, nunca bloqueio da aula: HTTP básico, diferença entre autenticação/autorização, lógica booleana e leitura de logs. Onde necessário, use o vocabulário abaixo antes de abrir o terminal.

1. **Conceito 1.** Confiança de entrada: browser e requests podem ser alterados por quem os envia.

2. **Conceito 2.** Allowlist de escrita: lista explícita dos campos alteráveis pela operação.

3. **Conceito 3.** Regressão: teste que impede que um defeito corrigido volte em outra mudança.

## Mecanismo técnico: entrada, fronteira, controle e resultado

Validação de formato, autorização por recurso e regras de negócio são etapas diferentes. `role:'admin'` é string válida, mas não autorizada. A implementação `safeProfilePatch` copia o estado confiável e permite somente `name` não vazio; um endpoint administrativo separado deveria exigir política de privilégios. Persistência transacional, validação de email e controle de sessão permanecem fora do escopo dessa fixture.

**Modelo de decisão:** estado inicial → entrada controlada → componente que decide → efeito observável → comparação com a política. Sempre diga onde mora a autoridade: aplicativo, navegador, banco, armazenamento ou processo de entrega. O nome de uma ferramenta não responde essa pergunta.

### Exemplo resolvido e comentado

```js
import { safeProfilePatch } from './models.mjs';
const user={name:'Ana',role:'reader'};
const payload={name:'Ana Maria',role:'admin'};
console.log(safeProfilePatch(user,payload)); // role continua reader
```

> Este trecho é um recorte da fixture da aula; execute o teste completo pelo comando abaixo, a partir da raiz do projeto. A sintaxe de import acima representa o módulo do diretório de laboratório, e não uma dependência publicada.

**Evidência esperada:** Nome atualizado somente se válido; papel controlado pelo servidor permanece reader.

### Quando algo não funciona

O teste verde não valida automaticamente autenticação ou ORM. Se o campo for crítico, confira também persistência e logs de auditoria.

Para recuperar: confira a versão `node --version`, inicie no diretório raiz, execute novamente uma única vez após corrigir a causa e compare os resultados; não modifique expectativas só para tornar os testes verdes.

## Detecção, prevenção e reteste

**Evidência a observar:** Monitore tentativa de alterar campo protegido e decisão sem persistir JSON contendo dados privados.

**Medida corretiva:** DTO restrito, autorização no servidor, query parametrizada e segredos em configuração protegida; cada mecanismo tem teste específico.

**Critério de reteste:** o caminho originalmente indevido deve ser negado sob as mesmas pré-condições, enquanto o caminho legítimo continua funcionando. Documente casos não cobertos. Um caso rejeitado não é automaticamente prova de que todas as variações estão seguras.

## Prova final independente — competência aplicada

**Novo cenário, distinto da fixture:** Um sistema de RH recebe `{displayName:'Iara', approvedHours:400}` no PATCH do próprio perfil. `approvedHours` só pode ser alterado pelo gestor em fluxo auditado.

Responda *sem abrir o gabarito*, incluindo resultado previsto e ao menos uma limitação:

1. Qual é o campo legítimo e qual cruza uma fronteira de autorização?
2. Descreva o erro em usar `Object.assign(employee, req.body)`.
3. Construa um negativo para manter approvedHours inalterado.
4. Construa um positivo para atualização do displayName.
5. Onde deve ficar o endpoint de aprovação de horas e quem valida o gestor?
6. Qual verificação em banco e auditoria não é coberta pelo modelo in-memory?

Após concluir, compare seu relatório com o [gabarito independente e rubrica](/course-labs/a031-040/answer-keys/AULA-037.md). A publicação do gabarito não substitui a tentativa independente.
