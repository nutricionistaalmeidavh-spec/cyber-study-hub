## 2. Objetivo e mecanismo causal

Buffer overflow é escrita além da extensão de um objeto. Para um nome com capacidade cap, n bytes de texto exigem n+1 posições devido ao NUL. O contrato é n < cap e n ≤ bytes disponíveis na origem. São validações diferentes. Em um parâmetro `char dst[8]`, C ajusta a declaração para ponteiro: o 8 não garante que o chamador forneceu oito bytes. O contrato deve receber cap e ser cumprido pelo chamador.

## 4. Exemplo resolvido — estado, decisão e efeito

O arquivo overflow8.bin é N, 08, ABCDEFGH: dez bytes no total. O parser v1 testa n>8, portanto aceita 8. memcpy escreve índices 0..7 legalmente; a instrução seguinte escreve NUL no índice 8, primeiro byte fora de name. boundary7.bin contém sete caracteres, deixa índice 7 para NUL e funciona. truncated.bin declara quatro caracteres mas contém dois; isso viola a origem, independentemente do destino.

## 7. Código comentado e artefatos

```c
int copy_name(char *dst, size_t cap, const char *src, size_t n) {
    if (!dst || !src || cap == 0 || n >= cap) return -1;
    memcpy(dst, src, n); // origem também precisa oferecer n bytes
    dst[n] = '\0';      // garantido dentro do objeto por n < cap
    return 0;
}
```

## 10. Defesa e reteste

O patch usa n>=sizeof name apenas porque name é array local visível. Em API extraída, receba cap. Reteste vazio, cap−1, cap, cap+1 e origem truncada. Não trunque silenciosamente nomes se isso puder fundir identidades distintas.

## 11. Troubleshooting específico

Um alerta “stack-buffer-overflow” não significa exaustão da stack. Se a linha for memcpy em vez do terminador, confira se você usou a fixture exata: um input maior pode disparar outro acesso.

## Complemento A editorial — aplicação e transferência de competência (AULA-162)

Este complemento amplia o laboratório real existente, **sem substituir** os programas C, fixtures, comandos, avisos de segurança ou evidências anteriores. O objetivo é provar decisão e reteste em cenário novo, com interpretação independente.

### 1. Caso de trabalho e competência exigida

Um cadastro próprio armazena nome em array C de oito bytes, com terminador NUL, e lê origem descrita por comprimento fornecido no cabeçalho. Ele aceita `n<=8` e copia exatamente n bytes; com n=8 tenta escrever `dst[8]='\0'`. Outro pacote declara n=7 mas fornece apenas 6 bytes de corpo.

**Competência:** distinguir a invariante violada, explicar o mecanismo que causa a condição, selecionar a correção causal e demonstrar o caminho legítimo em reteste. Duração complementar: 70–90 min. Custo obrigatório: R$0.

1. **Capacidade** é extensão real disponível no destino, e o último índice de cap=8 é 7.

2. **String C** necessita byte NUL além de todos os bytes de conteúdo, quando a rotina promete construir string terminada.

3. **Comprimento declarado** não substitui tamanho real do buffer de origem; são dois contratos independentes.

### 2. Raciocínio mecanístico e contraexemplo

Para copiar n bytes e acrescentar `\0`, exija destino com capacidade ≥ n+1 **sem calcular n+1 de maneira sujeita a overflow**, por exemplo `n < capacity`. Em paralelo confirme `n <= actualSourceLength` depois de validar cabeçalhos sem underflow. `n=7`, capacidade 8 e origem real de 7 bytes é aceito. `n=8` falha por NO_TERMINATOR_SPACE mesmo que a cópia inicial caiba. `n=7` com origem de 6 falha como SOURCE_TRUNCATED. O laboratório C da fase 16 exercita exatamente casos de stack-buffer-overflow antes e rejeição após a correção.

**Teste positivo independente:** capacidade 8, n=7, origem 7: nome cabe com NUL sem truncamento.

**Teste negativo independente:** capacidade 8, n=8: falta NUL; n=7 com origem 6: leitura de dados insuficiente; ambos rejeitados.

**Limite da experiência:** A fixture não executa memcpy, não modela aliasing, UTF-8 multibyte, integer overflow C nem overflow real; a confirmação de memória vem do laboratório C com ASan.
