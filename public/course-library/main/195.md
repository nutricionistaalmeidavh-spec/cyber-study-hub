## 2. Problema: o pipeline publica algo que não testou

Um pipeline produz um artefato mesmo quando uma mudança permite Alice ler a nota de Bob. O problema não se resolve com um step chamado “security”: o runner precisa executar um teste que detecta a mudança, falhar com código diferente de zero e impedir que o estágio de artefato aconteça. Neste laboratório a aplicação é uma função de leitura com duas notas sintéticas; a CI é um processo local e um workflow de GitHub Actions completo, sem deploy.

Objetivos: seguir evento → checkout → teste → artefato; demonstrar bloqueio, verificar integridade e explicar a diferença entre digest e proveniência.

## 3. Fronteiras de confiança

O conteúdo de uma pull request é código não confiável que o runner executará. Permissões do `GITHUB_TOKEN`, secrets, rede, cache e arquivos do runner são capacidades independentes. `permissions: contents: read` limita o token; não neutraliza código arbitrário nem impede exfiltração de dados já disponíveis. Um runner efêmero reduz resíduos entre jobs. `pull_request_target` tem contexto privilegiado e não deve ser combinado com checkout/execução indiscriminada do código da PR.

Passar título/body de PR diretamente para um `run:` pode transformar dados em código shell. Nosso workflow não interpola texto de usuário e só roda arquivos versionados. Variáveis de ambiente com quoting são o caminho para dados quando necessários. Fixar uma action por SHA impede deslocamento de tag, mas ainda exige avaliar aquele commit. [Sintaxe de workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

## 4. Aplicação e gate executáveis

A [aplicação completa](/course-labs/phase16-platform/ci/app.cjs) recebe identidade fornecida pelo teste; não simula login HTTP. A opção `unsafe` remove exatamente a checagem de owner, permitindo demonstrar o defeito.

```javascript
'use strict';
// Fixture sem HTTP/rede: identidade é entregue pelo chamador confiável do teste.
const notes = [{id:'a',owner:'alice',text:'nota A'}, {id:'b',owner:'bob',text:'nota B'}];
exports.readNote = (user,id,unsafe=false) => {
  if (!user) return {status:401};
  const note=notes.find(n=>n.id===id);
  if (!note) return {status:404};
  if (!unsafe && note.owner!==user) return {status:403};
  return {status:200,text:note.text};
};
```

O [pipeline](/course-labs/phase16-platform/ci/pipeline.cjs) executa cinco casos: Alice/A=200, Bob/B=200, Alice/B=403, sem sessão=401 e nota inexistente=404. Só depois cria `artifact.json` e `artifact.sha256`. Cada variante limpa exclusivamente seu diretório de saída antes do teste, evitando aprovar um artefato antigo por engano.

```yaml
name: Platform teaching gate
# Copiar para .github/workflows/platform-lab.yml somente em repositório de laboratório.
on:
  push:
  pull_request:
  workflow_dispatch:
# O token só lê o checkout; não há deploy nem secrets deste exercício.
permissions:
  contents: read
jobs:
  test:
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    defaults:
      run:
        working-directory: public/course-labs/phase16-platform/ci
        shell: bash
    steps:
      # Commit imutável de actions/checkout v4.2.2.
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
        with:
          persist-credentials: false
      - name: Runtime e inventário
        run: |
          node --version
          test "$(node -p 'Number(process.versions.node.split(".")[0]) >= 22')" = true
          echo 'Dependências npm: nenhuma; apenas módulos node embutidos'
      - name: Gate bloqueia versão vulnerável
        run: |
          if node pipeline.cjs --unsafe; then
            echo 'ERRO: variante sem autorização passou'; exit 1
          fi
          test ! -d out-unsafe
      - name: Gerar após gates e verificar digest
        run: |
          node pipeline.cjs
          node verify.cjs
```

Este arquivo fica como material didático em [workflow.yml](/course-labs/phase16-platform/ci/workflow.yml). Para execução remota opcional, copie-o para `.github/workflows/platform-lab.yml` de um repositório de laboratório que conserve o caminho usado em `working-directory`. Nenhuma publicação ou configuração de repositório é feita por esta aula.

## 5. Laboratório local reproduzível

Pré-requisito: Node 22+ e shell Bash. Não há `npm install` porque o gate usa somente módulos internos. A ausência de dependências externas elimina a resolução transitiva deste app mínimo; não equivale a uma análise CVE do Node ou do runner.

```bash
cd public/course-labs/phase16-platform/ci
node --version
node pipeline.cjs
node verify.cjs
# O exit não zero é o resultado negativo ESPERADO; capture-o sem encobri-lo.
if node pipeline.cjs --unsafe; then
  echo 'ERRO: gate aceitou variante vulnerável'; exit 1
else
  echo 'PASS variante vulnerável bloqueada'
fi
test ! -d out-unsafe
node pipeline.cjs
node verify.cjs
```

Primeira execução: `PASS 5 gates; artifact SHA256 ...`; verificação: `PASS digest confere`. Na versão vulnerável, o assert `gate: alice/b` mostra `200 !== 403`, termina com exit 1 e não cria `out-unsafe`. O reteste seguro recria o mesmo JSON e digest. Tempos e versão do runner podem variar, mas os bytes do artefato não incorporam relógio ou aleatoriedade.

**Checkpoint 1:** abra o pipeline e indique a instrução que impede chegar a `writeFileSync` após falha. Resposta: a exceção de `assert.equal` encerra o processo; no workflow, o código não zero falha o step. O step que deliberadamente testa a versão insegura inverte essa expectativa usando `if`.

Agora simule alteração de artefato, sem tocar o código:

```bash
node -e "require('node:fs').appendFileSync('out-safe/artifact.json',' ')"
if node verify.cjs; then exit 1; else echo 'PASS adulteração detectada'; fi
node pipeline.cjs
node verify.cjs
```

**Checkpoint 2:** por que alguém capaz de reescrever o artefato e o digest pode passar? Porque o hash detecta inconsistência relativa a uma referência; não autentica o produtor. Uma promoção real deve vincular digest a build/commit confiáveis, atestação e política de verificação. O exercício não implementa assinaturas nem promove artefatos.

## 6. Hardening e investigação

Revise alterações de workflow como alterações de privilégio. Preserve SHA do checkout, versão do runtime, status dos gates e digest do artefato. Uma falha de teste é uma evidência de regressão, não automaticamente um ataque. Se o gate passar mas a saída não existir, confira working directory e se houve `continue-on-error`, `if: always()` indevido ou produção de artefato em outro job sem dependência.

Dependências reais pedem lockfile versionado, instalação reproduzível (`npm ci`), verificação de origem e avaliação de vulnerabilidades. Não introduzimos um scanner fictício: aqui há inventário sem pacotes e teste de autorização. O Node incluído no runner é verificado por versão mínima, mas não está fixado byte a byte; a execução em Actions permanece uma validação separada da execução local.

Troubleshooting: Node abaixo de 22 deve ser atualizado no laboratório. `ENOENT artifact.json` antes do build indica ordem incorreta. Hash diferente depois de adicionar espaço é esperado, embora o JSON continue parseável. Se a variante insegura “passar”, leia o código de saída e a presença de `out-unsafe`, não apenas o último `echo`. Cleanup local: `rm -rf out-safe out-unsafe`, somente dentro desta pasta.

## 7. Desafio

Acrescente uma operação de atualização que preserve owner. Escreva o caso de transferência indevida antes da implementação e comprove que a variante defeituosa falha antes da geração do artefato. Não basta acrescentar a palavra “SAST” ao nome de um step.

## 8. Quiz

1. O teste negativo falhou, mas um job independente criou artefato. O que faltou?
A. Um nome de workflow mais específico.
B. Dependência/gate que condicione produção ao teste aprovado.
C. `permissions: write-all`.
D. Uma tag mutável no checkout.

**Resposta:** B. A ordenação e as condições de execução devem impor o bloqueio.

2. SHA256 igual ao arquivo de referência prova o quê?
A. Que o commit passou por revisão humana.
B. Que o binário está livre de vulnerabilidades.
C. Que o produtor é o runner oficial.
D. Que os bytes correspondem à referência, sem provar autoria por si só.

**Resposta:** D. Proveniência exige uma referência autenticada e vínculo com o build.

3. Por que `contents: read` não torna seguro executar qualquer PR?
A. O código ainda pode consumir capacidades disponíveis ao processo/runner.
B. Tokens read-only permitem gravar qualquer branch.
C. A permissão se aplica apenas a arquivos JSON.
D. O Node desativa os asserts em pull requests.

**Resposta:** A. A permissão de um token é uma das fronteiras, não toda a execução.

## 9. Flashcards

- **Gate efetivo** → falha observável impede criação/promoção do artefato posterior.
- **Artefato residual** → saída antiga que pode mascarar falha; o lab limpa a pasta da variante antes do teste.
- **Action por SHA** → referência de commit imutável, ainda sujeita à revisão do código fixado.
- **Digest** → resumo dos bytes; não autentica sozinho o produtor.
- **pull_request_target** → contexto que exige cuidado especial com execução de código de PR não confiável.
