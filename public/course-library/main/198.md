## 2. Duas plataformas, duas decisões de autorização

Uma interface que esconde a nota de Bob não impede Alice de pedir o identificador diretamente. No Supabase, a política pode ser aplicada pelo PostgreSQL sobre linhas. No Firestore, Security Rules autorizam operações de documento/consulta. Autenticar fornece identidade; RLS ou rules decidem quais dados essa identidade pode ler ou modificar.

Esta aula possui dois experimentos separados: PostgreSQL real com identidade sintética e Firestore Emulator com contextos de autenticação de teste. Nenhum deles usa projeto de produção ou service key. A meta é executar SELECT/get, criação, atualização, tentativa de trocar owner e reteste com dois usuários.

## 3. Supabase: grants e RLS são camadas diferentes

Um grant permite à role executar SELECT/INSERT/UPDATE na tabela; RLS limita as linhas. Criar uma policy sem `ENABLE ROW LEVEL SECURITY` não a ativa. `USING` avalia a linha existente/visível; `WITH CHECK` valida a linha proposta em INSERT/UPDATE. Em UPDATE, ambos importam: Alice precisa ser dona antes e continuar dona depois.

`auth.uid()` representa a identidade do pedido autenticado no Supabase; sem sessão válida retorna NULL, que não passa na comparação com owner. Roles de superuser/BYPASSRLS, e normalmente o owner da tabela, têm tratamento especial. Não teste isolamento usando apenas a role administrativa. `FORCE ROW LEVEL SECURITY` sujeita o owner comum, mas não remove bypass de superuser. [RLS no PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

### Migração equivalente para um projeto Supabase de laboratório vazio

O código abaixo pressupõe o schema `auth` e as roles `anon`/`authenticated` fornecidos pelo Supabase; não deve ser executado no mesmo banco do dublê local sem adaptação. A tabela precisa estar ausente.

```sql
BEGIN;
CREATE TABLE public.notes (
  id integer PRIMARY KEY,
  user_id uuid NOT NULL REFERENCES auth.users(id),
  body text NOT NULL CHECK (length(body) <= 500)
);
ALTER TABLE public.notes ENABLE ROW LEVEL SECURITY;
REVOKE ALL ON public.notes FROM anon;
GRANT SELECT, INSERT, UPDATE ON public.notes TO authenticated;
CREATE POLICY notes_read ON public.notes FOR SELECT TO authenticated
  USING ((SELECT auth.uid()) = user_id);
CREATE POLICY notes_insert ON public.notes FOR INSERT TO authenticated
  WITH CHECK ((SELECT auth.uid()) = user_id);
CREATE POLICY notes_update ON public.notes FOR UPDATE TO authenticated
  USING ((SELECT auth.uid()) = user_id)
  WITH CHECK ((SELECT auth.uid()) = user_id);
COMMIT;
```

`SELECT auth.uid()` permite otimizações quando seu resultado é constante por statement. Não altera a regra de propriedade. Não há policy/grant de DELETE neste contrato. Chaves privilegiadas do backend nunca devem ser entregues ao navegador; bypass efetivo depende da role e do contexto/token do pedido. [Documentação Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

## 4. Exemplo resolvido: tentativa de transferir a própria nota

Alice autenticada lê a linha `id=1,user_id=Alice`. Executa UPDATE mudando `user_id` para Bob. `USING` passa porque a linha antiga é de Alice. `WITH CHECK` reprova porque a nova linha seria de Bob. O banco rejeita a escrita; sem esse segundo teste explícito o objetivo de impedir transferência poderia ser violado, conforme as demais policies existentes. Policies permissivas da mesma operação se combinam por OR: uma policy adicional ampla pode desfazer o isolamento pretendido.

Já UPDATE da linha de Bob pode produzir **zero linhas afetadas**, pois `USING` a esconde. Zero linhas não é o mesmo fenômeno de uma exceção de `WITH CHECK` e não prova que o registro inexiste para todos os usuários.

## 5. Laboratório A — PostgreSQL descartável

Pré-requisito: Docker em execução e acesso inicial à imagem `postgres:17`. [run.sh](/course-labs/phase16-platform/rls/run.sh) cria um container sem publicar porta e o remove ao terminar. [lab.sql](/course-labs/phase16-platform/rls/lab.sql) contém schema, duas roles sem login, fixtures, policies e asserts, tudo em transação encerrada com ROLLBACK.

```bash
cd public/course-labs/phase16-platform/rls
bash run.sh
```

O script usa uma função **dublê** `auth.uid()` que lê `request.jwt.claim.sub`; SET ROLE e `set_config` são instrumentos do teste. Isso exercita RLS real, mas NÃO testa assinatura JWT, PostgREST, login nem API Supabase. Um cliente SQL capaz de definir livremente essa configuração pode inventar identidade; esse mecanismo não é autenticador de produção. O comando é para banco descartável, nunca para um banco Supabase existente.

| Etapa do script | Identidade/ação | Resultado esperado |
|---|---|---|
| Antes de ENABLE RLS | Alice SELECT | 2 linhas, inclusive B: demonstração da lacuna |
| Após policies | Alice SELECT | só nota A |
| INSERT e UPDATE próprios | Alice | sucesso |
| UPDATE da nota B | Alice | 0 linhas afetadas, B intacta |
| INSERT com owner Bob | Alice | SQLSTATE 42501 |
| UPDATE A mudando owner | Alice | SQLSTATE 42501 por WITH CHECK |
| SELECT como Bob | Bob | somente B intacta |
| uid ausente na role autenticada | NULL | zero linhas |
| SELECT como lab_anon | anônimo | negado por falta de grant |
| Reteste Alice após INSERT próprio | Alice | 2 notas próprias, nenhuma B |

Saída: `BASELINE: Alice lê 2 linhas sem RLS`, mensagens `PASS ...` para os controles e `ROLLBACK`. Qualquer assert inesperado encerra com código não zero. **Checkpoint:** a segunda contagem de duas linhas não é regressão: agora Alice possui A e sua nova nota, enquanto a primeira contagem indevida incluía B. Compare IDs, não apenas contagens.

## 6. Firebase: regras não são filtros de resultado

No Firestore, `resource.data` é o documento existente; `request.resource.data` é o estado proposto depois da operação. As rules abaixo exigem owner autenticado, body textual limitado e ausência de campos extras. UPDATE compara dono anterior e novo; DELETE é negado.

```text
rules_version = '2';
service cloud.firestore {
 match /databases/{database}/documents {
  match /notes/{note} {
   function signedIn() { return request.auth != null; }
   function validNew() {
    return request.resource.data.keys().hasOnly(['owner','body'])
      && request.resource.data.body is string
      && request.resource.data.body.size() <= 500;
   }
   allow get, list: if signedIn() && resource.data.owner == request.auth.uid;
   allow create: if signedIn() && validNew() && request.resource.data.owner == request.auth.uid;
   // Documento existente e estado proposto precisam ter o mesmo dono autenticado.
   allow update: if signedIn() && resource.data.owner == request.auth.uid
      && validNew() && request.resource.data.owner == request.auth.uid;
   allow delete: if false;
  }
 }
}
```

Uma consulta sem filtro de owner não é executada para então remover resultados proibidos. O mecanismo precisa poder provar que a consulta só pode retornar documentos permitidos. Por isso a suíte inclui query com `where('owner','==','alice')` aceita e listagem irrestrita negada. [Testes oficiais de Security Rules](https://firebase.google.com/docs/rules/unit-tests).

## 8. Troubleshooting e limites de evidência

PostgreSQL: `role already exists`/`schema auth exists` indica banco não descartável; restaure a premissa em vez de apagar estruturas existentes. Se Alice vê tudo, confira `current_user`, ativação de RLS e `rolbypassrls`. Se nada pode ser escrito, confira grants além das policies. O script mostra erros completos e sempre remove seu container.

Firebase: `ECONNREFUSED` pede verificar emulador/porta; erro Java exige runtime compatível; `permission-denied` numa query sem owner é esperado, não motivo para abrir as rules. Persistência de fixtures requer conferir o mesmo project ID. Falha npm/download é limitação de instalação, não resultado das rules. O uso de versões fixas didáticas não afirma ausência de vulnerabilidades nem adequação a produção.

Nesta edição, PostgreSQL permanece **pendente de runtime** por ausência de Docker/psql. O Firestore Emulator 1.19.8 executou de fato em 127.0.0.1:8088: baseline aberto, 17 checks corrigidos e reteste passaram com exit 0. O caminho npm test via CLI foi interrompido por revisão de rede cancelada; ele não é declarado aprovado. O teste concluído iniciou diretamente o JAR já baixado, sem CLI cloud, e executou o mesmo test.mjs com FIRESTORE_EMULATOR_HOST fixo. A execução é reproduzível com [verify.py](/course-labs/phase16-platform/verify.py): `python3 ../verify.py --firebase-jar /caminho/cloud-firestore-emulator-v1.19.8.jar`, dentro da pasta firebase. Esse verificador não baixa o JAR e recusa portas já ocupadas. As negativas PERMISSION_DENIED são esperadas; sucesso do processo exige os asserts correspondentes. Consulte `docs/phase16/platform-status.json` e [evidência de execução](/course-labs/phase16-platform/validation-evidence.json) para comandos/saídas e limites; o teste de rules não valida login, JWT real ou produção.

## 9. Quiz

1. Alice pode atualizar sua nota, mas não transferi-la para Bob. Qual combinação expressa isso?
A. Apenas GRANT UPDATE na tabela.
B. USING para a linha antiga e WITH CHECK para a linha nova.
C. Desabilitar RLS depois de SELECT.
D. Verificar owner apenas na interface.

**Resposta:** B. Acesso ao estado antigo e validade do estado proposto são decisões distintas.

2. Uma query Firestore que pode incluir notas de Bob é enviada por Alice. O que esperar das rules deste lab?
A. Todas as notas, com owner ofuscado.
B. Só notas de Alice, pois rules sempre filtram dados.
C. Uma lista vazia com status de sucesso.
D. Rejeição; a query deve restringir o conjunto permitido.

**Resposta:** D. Rules autorizam a query possível, não filtram resultados arbitrários.

3. O administrador PostgreSQL leu duas notas após ENABLE RLS. Isso prova que a policy falhou?
A. Não; deve-se verificar role efetiva/bypass e repetir com a role cliente.
B. Sim; ENABLE deveria bloquear qualquer superuser.
C. Sim; FORCE remove todos os tipos de bypass.
D. Não; RLS só se aplica a INSERT.

**Resposta:** A. O teste precisa atravessar a mesma fronteira de autorização do cliente.

## 10. Flashcards

- **GRANT + RLS** → privilégio de operação na tabela mais restrição de linhas.
- **WITH CHECK** → condição que o novo estado deve satisfazer ao gravar.
- **UPDATE com zero linhas** → pode indicar linha invisível pela policy, não inexistência global.
- **Rules de Firestore** → decisão por documento/operação/consulta, não filtro posterior.
- **withSecurityRulesDisabled** → útil para seed, inválido como prova de isolamento cliente.
- **Dublê de auth.uid** → exercita autorização SQL, não valida assinatura JWT nem autenticação.

## Resultado de aprendizagem e problema concreto
Alice pode editar sua nota, mas tenta transferir owner para Bob. No PostgreSQL RLS, USING examina estado anterior e WITH CHECK estado novo; ambos importam para UPDATE.

Ao final, o estudante deve: identificar principal/recurso/limite, prever uma decisão, executar casos válido e negado, reconhecer a causa, propor correção que mantenha o uso legítimo e declarar o que o experimento não comprova.

## Mecanismo técnico e contraexemplo
Grant permite operação da role; RLS limita linhas. Sem ENABLE RLS, policy não atua. Em Firestore resource.data é o estado antigo, request.resource.data o novo; rules não fazem filtro pós-query. Admin SDK e PostgreSQL BYPASSRLS não devem validar isolamento de cliente.

**Regra de leitura:** uma configuração declarada, scanner verde ou resultado de simulador não prova a mesma propriedade na plataforma real. Não basta bloquear uma entrada: é obrigatório preservar o acesso autorizado.

## Exemplo resolvido — previsão e contraprova
O modelo didático usa `assessRowChange` com a entrada sintética:
```javascript
assessRowChange({authenticated:true,userId:'alice',oldOwner:'alice',newOwner:'alice',operation:'update'})
```
**Saída prevista:** `ALLOW`. Explique qual elemento do objeto faz a política permitir o pedido. A situação negativa é: **Alice atualiza oldOwner:'alice' para newOwner:'bob'**. A saída prevista é `DENY_OWNER`; a causa é uma diferença verificável na fronteira de confiança.

## Resposta defensiva, investigação e verificação
Exigir owner tanto em USING quanto WITH CHECK, grants mínimos, nenhum bypass em testes de usuário e query Firestore restrita. A suíte existente PostgreSQL/Firestore Emulator dá evidência real de enforcement local; a fixture JS não substitui essas integrações.

**Evidência mínima:** estado inicial, entrada e resultado esperado, saída observada, correção de causa, recusa de cenário indevido e reteste de cenário legítimo. Se a saída divergir, confira argumentos de entrada e fixture antes de concluir que existe defeito no software real.
