## 2. Visão geral

Aplicações que confiam no Host podem gerar links, redirects ou decisões de roteamento controláveis pelo cliente.

## 3. Aprofundamento: o que realmente está acontecendo

O header Host participa de roteamento e, em algumas aplicações, de geração de URLs absolutas. A aplicação deve ter uma origem canônica/configurada e uma lista de hosts aceitos; não deve transformar um valor do cliente em autoridade sobre seu próprio domínio.

Aplicações frequentemente usam Host para construir links, redirects ou decisões de roteamento. Se esse valor for confiado sem validação, infraestrutura e lógica de negócio podem discordar sobre o host legítimo.

Ao estudar, tente sempre localizar cinco elementos:

```text
entrada/estado
→ componente que interpreta
→ decisão
→ efeito observável
→ controle que quebra a cadeia
```

## 5. Conceitos fundamentais

### 1. Host
Cabeçalho HTTP que identifica o host solicitado.
### 2. X-Forwarded-Host
Cabeçalho de proxy que pode influenciar host percebido pela aplicação.
### 3. Password reset poisoning
Geração de link de redefinição usando host controlado.
### 4. Allowlist
Lista explícita de hosts aceitos.

## 6. Fluxo técnico

1. **Cliente envia Host**
2. **Proxy encaminha ou normaliza**
3. **Aplicação usa o valor em URL/redirect**
4. **Links ou decisões podem refletir host não confiável**
5. **Allowlist e configuração canônica quebram essa dependência**

### Checkpoint 1

Descreva o fluxo acima sem usar o nome da técnica. Onde está a primeira decisão de segurança?

## 7. Exemplo técnico — Host canônico por allowlist

```ts
const TRUSTED_HOSTS = new Set(["app.exemplo.local", "localhost:5173"]);

function assertTrustedHost(host = "") {
  const normalized = host.toLowerCase().trim();
  if (!TRUSTED_HOSTS.has(normalized)) {
    throw new Error("Invalid Host header");
  }
  return normalized;
}
```

### Como ler o exemplo

Para links externos importantes, uma origem configurada no servidor costuma ser mais segura que reconstruir a URL a partir do request.

Ao revisar cada linha/bloco, marque:

- o dado de entrada;
- o estado confiável usado na decisão;
- a condição de rejeição;
- o efeito/log que você esperaria observar.

## 8. Por que a vulnerabilidade/mecanismo acontece

Aplicações frequentemente usam Host para construir links, redirects ou decisões de roteamento. Se esse valor for confiado sem validação, infraestrutura e lógica de negócio podem discordar sobre o host legítimo.

Não memorize apenas “payloads” ou comandos. A mesma classe de problema reaparece em frameworks e ferramentas diferentes quando a **mesma suposição** é quebrada.

## 9. Laboratório guiado — Comparar host recebido e host configurado

**Modo:** PC

1. Crie uma aplicação local que registre Host e URL canônica configurada.
2. Faça requests locais com nomes válidos de desenvolvimento.
3. Implemente uma allowlist explícita.
4. Verifique que hosts não reconhecidos geram erro antes de redirects ou geração de links.
5. Registre o host rejeitado para detecção.

### Resultado esperado

A aplicação não deve decidir sua origem pública apenas com base em um cabeçalho fornecido pelo cliente.

### Checkpoint 2 — antes da correção

Qual evidência mínima demonstra a condição estudada sem ampliar impacto desnecessariamente?

### Checkpoint 3 — depois da correção

Repita o mesmo teste e registre a diferença. Se o cenário mudou, o reteste não é comparável.

## 10. Como detectar

Observe hosts desconhecidos, redirects externos e geração de URLs absolutas com domínios não autorizados.

Transforme a frase acima em telemetria:

```text
quem?
onde?
qual ação?
qual recurso/destino?
qual resultado?
qual sequência temporal?
```

## 11. Como corrigir / reduzir risco

Use host canônico configurado, valide hosts permitidos e trate headers de proxy apenas de infraestrutura confiável.

### Controle primário vs compensatório

O controle primário deve corrigir a decisão insegura. Logging, WAF, alerta, rate limit ou EDR podem ser importantes, mas não devem ser vendidos como substitutos da correção quando a causa está no código/configuração.

## 12. Troubleshooting

- Confirme versões, portas, identidade e estado inicial do laboratório.
- Colete baseline antes de mudar configuração.
- Se uma ferramenta “não encontrar”, verifique cobertura e fonte de dados antes de concluir ausência de risco.
- Se um finding aparecer, leia a evidência e a pré-condição antes de classificá-lo.
- Mantenha laboratório isolado e restaure snapshot quando a aula pedir mudança de configuração.

## 13. Erros comuns de raciocínio

- Confundir indicador com confirmação.
- Concluir vulnerabilidade pelo nome da ferramenta.
- Aplicar hardening sem testar impacto operacional.
- Não diferenciar prevenção de detecção.
- Fazer correção e esquecer o reteste.

## 15. Quiz

**Por quê:** Cabeçalho HTTP que identifica o host solicitado.

**Resposta:** A

**Por quê:** Use host canônico configurado, valide hosts permitidos e trate headers de proxy apenas de infraestrutura confiável.

**Por quê:** Observe hosts desconhecidos, redirects externos e geração de URLs absolutas com domínios não autorizados.

**Resposta:** A
