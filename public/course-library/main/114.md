# Aula 114 — Jumps, Calls e Control Flow

**Trilha:** Assembly & RE · **Profundidade:** P · **Tempo:** 70 minutos.  
**Pré-requisitos recomendados, não bloqueantes:** CMP/ZF, loops básicos, fluxograma de decisões.  
**Ambiente:** Node.js 22 ou superior, exemplos sintéticos de autoria do curso, sem licença, API paga, binário de terceiros ou depurador obrigatório.

> Engenharia reversa somente de binários próprios ou de uso expressamente autorizado. Não usar esta prática para contornar licenças, proteções ou operar sobre artefatos desconhecidos de fontes não verificadas.

## 1. Problema concreto e competência

O programa didático classifica pontuação: n≤0 rejeitada; 1–9 pequena; n≥10 grande. Uma leitura superficial do decompilador conclui que todos os caminhos executam bloco grande porque o bloco existe no disassembly. Presença estática não significa execução para toda entrada.

**Objetivo mensurável:** Construir e percorrer CFG de rotina própria com decisões de limite, explicitando por que cada bloco pode ou não ser alcançado.

O domínio desta aula é comprovado por previsão, experimento, comparação de saída e justificativa de uma evidência negativa; memorizar terminologia não basta.

## 2. Conceitos que o aluno precisa dominar

1. **Basic block** é sequência de instruções com único fluxo de entrada e saída na descrição simplificada de CFG.

2. **Conditional branch** depende do estado de flags; `CALL` transfere controle e produz contexto de retorno; `RET` devolve execução.

3. **CFG (Control-Flow Graph)** contém blocos e arestas possíveis; um caminho efetivamente executado é subconjunto dos caminhos estáticos.

## 3. Mecanismo técnico: de bytes a comportamento

A fixture `traceBranches()` registra o caminho `entry→reject→return` para n=-1, `entry→positive→small→return` para n=2 e `entry→positive→large→return` para n=10. O grafo dos blocos não valida por si só quais entradas realmente chegam a cada bloco; é necessário entender predicados. A fixture abstrai instruction pointer, assembler encoding e otimizações como branchless code, jump tables e loop unrolling.

**Armadilha de otimização:** compiladores podem substituir um salto explícito por instrução condicional ou operação branchless mantendo comportamento. Portanto, CFG binário e CFG do source não precisam ter a mesma forma.

### Exemplo técnico comentado

```js
// Este modelo está em public/course-labs/a111-120/models.mjs
traceBranches(10).path; // ['entry','positive','large','return']
```

**Evidência útil:** entrada, predicado, lista de blocos visitados e casos limite de fronteira. **Erro de interpretação frequente:** Confundir arestas possíveis do CFG com caminho executado por determinada entrada.

## 4. Prática executável e validação

O laboratório **realmente executado em CI** usa [modelos locais](/course-labs/a111-120/models.mjs) e [testes Node](/course-labs/a111-120/lab.test.mjs). Não é necessário instalar Ghidra, depurador, compilador C nem máquina virtual.

```sh
# Execute a partir da raiz do repositório:
node --test public/course-labs/a111-120/lab.test.mjs
```

**Caminho legítimo:** Casos de entrada legítimos alcançam seus blocos e retornam categoria coerente com as condições.

**Contraexemplo ou erro que a prática deve capturar:** Para -1, o bloco large não aparece na trilha; para 9, large também não é alcançado.

**Três checkpoints antes, durante e depois:**

1. Desenhe caixas entry, reject, positive, small, large e return antes de rodar.
2. Trace manualmente -1, 2 e 10, justificando cada aresta.
3. Altere somente o limiar 10 no seu pseudocódigo e preveja diferença em n=10 sem adulterar a fixture.

**Como registrar:** escreva entrada → operação → estado esperado → saída observada → interpretação → limite. Se um teste falhar, confronte os dados de entrada, a versão do Node e a semântica do exemplo. Não mude asserções apenas para obter verde.

## 5. Investigação, correção e limites

Para revisar binário de sua autoria, compare resultado observado, bytes/disassembly e explicação, verificando se o modo da arquitetura, tipos e convenções são os esperados. Quando um resultado contradizer o modelo, reduza o caso, guarde dados não sensíveis e só então corrija código próprio.

**Critério defensivo de aceite:** o caso legítimo permanece válido e o contraexemplo é reconhecido ou rejeitado; o teste não prova cobertura integral da ISA, compilador, debugger, máquina alvo ou ausência de bugs.

**Limitações da fixture:** ela contém apenas o mecanismo explicitado acima, não emula CPU inteira nem reproduz todos os efeitos de um executável nativo. Nem toda discrepância de disassembler é vulnerabilidade.

## 6. Avaliação independente — cenário de transferência

Um aplicativo de matrícula aceita idades 18–60. Um CFG reconstruído tem blocos `entry`, `invalidLow`, `invalidHigh`, `accept`, `return`. A implementação usa `if(age<18)... else if(age>60)... else accept`.

**Responda antes de consultar qualquer solução:**

1. Desenhe as arestas possíveis do bloco de entrada.
2. Quais blocos executam para idade 17?
3. Quais blocos executam para idade 60 e qual é a decisão?
4. Que entrada mínima diferencia `>` de `>=` na checagem superior?
5. Qual diferença entre esse CFG e a prova de que o programa inteiro não possui outros caminhos?
6. Como testar uma reconstrução de source sem exigir a mesma sequência de instruções compiladas?

Depois consulte o [gabarito separado da aula 114](/course-labs/a111-120/answer-keys/AULA-114.md), com seis respostas e critérios de aprovação.
