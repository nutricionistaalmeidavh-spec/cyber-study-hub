## 2. O problema em uma frase

WebSockets mantêm um canal persistente após o handshake HTTP. Autorização deve ser revalidada por conexão e por ação, sem assumir que a sessão inicial permanecerá válida.

## 3. O que você precisa dominar

- **Upgrade** — Mudança da conexão HTTP para WebSocket durante o handshake.
- **Origin** — Cabeçalho útil para restringir origens no handshake.
- **CSWSH** — Uso indevido de credenciais do navegador para abrir WebSocket de outra origem.
- **Revalidation** — Checagem contínua de autorização em operações sensíveis.

## 4. Modelo mental / como funciona

1. HTTP inicia o handshake
2. Servidor responde 101 Switching Protocols
3. Canal persistente é estabelecido
4. Mensagens passam sem novo request HTTP completo
5. Cada ação sensível deve revalidar autorização e sessão

## 5. Por que isso importa

WebSockets mantêm um canal persistente após o handshake HTTP. Autorização deve ser revalidada por conexão e por ação, sem assumir que a sessão inicial permanecerá válida.

Na prática, segurança não depende de decorar o nome da técnica. Ela depende de localizar a fronteira de confiança, identificar o dado ou estado que muda a decisão e provar, com evidência mínima, se o controle impede o comportamento indesejado.

Os pontos-chave desta aula devem ser usados como perguntas de revisão:

- Mudança da conexão HTTP para WebSocket durante o handshake.
- Cabeçalho útil para restringir origens no handshake.
- Uso indevido de credenciais do navegador para abrir WebSocket de outra origem.

## 6. Exemplo técnico — Autorização por mensagem em WebSocket

```ts
socket.on("message", async raw => {
  const msg = JSON.parse(raw.toString());
  const session = await sessions.get(socket.sessionId);

  if (!session?.active) {
    socket.close(4001, "Session expired");
    return;
  }

  if (!can(session.user, msg.action, msg.resourceId)) {
    socket.send(JSON.stringify({ error: "forbidden" }));
    return;
  }

  await handle(msg, session.user);
});
```

O handshake não vira um passe permanente. A operação continua sendo autorizada.

## 7. Leitura do exemplo

Ao revisar o código/configuração, responda em ordem:

## 9. Como defender / corrigir

Valide Origin, autentique no handshake, autorize cada operação e encerre conexões quando sessão/tokens forem revogados.

A correção deve agir sobre a causa. Evite controles cosméticos como esconder IDs, renomear rotas, desativar mensagens sem corrigir a decisão ou confiar somente no frontend.

## 10. Como detectar / investigar

Registre abertura/fechamento de sockets, ações privilegiadas e conexões mantidas após expiração de sessão.

Uma detecção útil combina:

```text
identidade/host
+ ação
+ recurso/destino
+ horário
+ resultado
+ contexto
```

## 11. Troubleshooting

- Se o laboratório não reproduzir, confirme primeiro **versão, porta, rota e estado inicial**.
- Não mude várias variáveis ao mesmo tempo; compare um cenário por vez.
- Salve request/output/log antes de corrigir. Sem “antes”, o reteste perde valor.
- Diferencie erro de configuração do laboratório de comportamento de segurança.
- Se uma ferramenta gerar um finding, trate como hipótese até entender a evidência.

## 12. Erros de raciocínio comuns

- Confundir ferramenta com conhecimento.
- Considerar ausência de erro como prova de segurança.
- Testar sem baseline.
- Classificar severidade antes de provar alcance/impacto.
- Pular o reteste.
